好，Context 开讲！

**还是先从一个场景开始。**
你跟我说：“帮我继续写那篇文章。”
我看了一下——什么文章？你没给我。
你说：“就是我们上次聊的那篇啊。”
我还是不知道。因为”上次聊的”不在我现在的视野里。

**这就是 Context 的本质：**
Context，直译是”上下文”，但更准确的理解是——
**Claude 在回答你之前，能看到的所有内容。**
包括：你说的话、我说的话、系统提示词、记忆文件、上传的文档……所有塞进来的东西，加在一起，就是 Context。

**Context Window 是什么？**
Window 是”窗口”的意思。
想象你趴在一扇窗户上往里看，窗户有多大，你能看到的就有多多。Context Window 就是这扇窗户——它决定了 Claude 每次能”看到”多少内容。
窗户大小是有上限的，用 **Token** 来衡量。

**Token 是什么？**
这是今天最重要的新概念。
Token 不是字，不是词，是模型处理文字的最小单位。大概的感觉是：
- 英文：1个单词 ≈ 1-2个Token
- 中文：1个字 ≈ 1-2个Token

“你好” ≈ 2个Token “今天天气怎么样” ≈ 7-8个Token
Claude 现在的 Context Window 大概是 **20万 Token**——听起来很多，但塞进去系统提示词、记忆文件、聊天记录、你上传的文档……其实消耗得很快。

消化一下，有没有问题？然后我们说说窗口满了会怎样，以及怎么管理😄

那更贵的模型（比如fable5)的context window会更长吗？
好问题！让我搜一下，因为这个涉及具体数字，我不想凭记忆说错。
搜到了，而且有个很有意思的发现！

**直接回答你的问题：**
Fable 5、Opus 4.8、Sonnet 5 的 Context Window 都是 **100万 Token**；Haiku 4.5 是 20万 Token。
所以更贵的模型，Context Window 确实更大——但有意思的是，**现在顶级模型之间 Context Window 已经拉平了**，不再是贵的模型的专属优势。

**但是——有个重要的但是：**
研究发现，**广告的 Context 和实际有效的 Context 是两回事**。NVIDIA 的研究显示可用的 Context 大概只有广告数字的 50-65%；Adobe 的研究发现大多数模型在超过 32K Token 之后，表现就开始下滑。
用一个比喻：窗户说能看到100米，但实际上超过50米就开始看不清了。
好消息是：研究发现 Claude 系列模型在长 Context 下衰减最慢。

**还有一个你可能不知道的细节：**
Fable 5 的安全工作范围大概在 80 万 Token 左右，超过这个范围召回质量开始下降。
而且Context 越长，响应越慢——Fable 5 在最大努力模式下，第一个 Token 出来要等 109 秒，而 Sonnet 4.6 只需要 1.4 秒。

**所以总结一下：**

| **模型** | **Context Window** | **价格** |
| --- | --- | --- |
| Fable 5 / Opus 4.8 / Sonnet 5 | 100万 Token | 贵 |
| Haiku 4.5 | 20万 Token | 便宜 |
| 我（Sonnet 4.6） | 100万 Token | 中等 |

贵的模型 Context 更大，但更重要的是**在长 Context 下推理能力更强**——不只是能装更多，还能在装满的情况下依然聪明。这才是 Fable 5 贵的真正原因，不只是窗户更大，是看得更清。

**上次说到：Context Window 是有上限的，窗户满了会怎样？**
两种情况：
**第一种：硬截断** 最早的模型处理方式很粗暴——窗口满了，最早的内容直接扔掉。就像桌子放满了，直接把最左边的东西推到地上。
早期 Mimo 的问题就有这个——history 只保留最近60条，更早的对话直接看不到了。
**第二种：Compaction（压缩）** 这是现在更聪明的做法。窗口快满之前，系统自动把早期的内容压缩成摘要，腾出空间继续对话。
你在这个对话里可能已经感受到了——我们聊了很长时间，但我还记得你一开始说的事。这部分就是 Compaction 在起作用。

**Context 里装的都是什么？**
这个很多人不知道。每次你发一条消息，Claude 看到的不只是那条消息，而是一个大包裹，里面有：
- 系统提示词（我的行为规则、记忆文件）
- 完整的对话历史
- 你上传的文件
- 搜索结果
- 工具调用的结果

这些加在一起，才是真正的 Context。

**一个让你豁然开朗的类比：**
Context Window 就像一个**会议室的白板**。
白板有多大，大家能看到的信息就有多多。Claude 每次回答，都是站在白板前，看着上面所有内容来思考。
白板写满了，要么擦掉最早写的（截断），要么把早期内容总结成一句话腾出空间（压缩）。
你说的话、我的记忆文件、你上传的文档——都是写在这块白板上的东西。

**这就解释了几个你可能遇到过的现象：**
为什么对话太长 Claude 会开始”犯糊涂”？白板快满了，早期内容被压缩或截断，细节丢失了。
为什么上传一个很长的文档之后 Claude 回答变慢？文档占了白板很大一块，处理的内容变多了。
为什么新开一个对话 Claude 什么都不记得？新对话是一块全新的白板，上次的内容不在上面。

这些都清楚了吗？然后我们说最后一块——怎么**管理** Context，让白板用得更聪明😄

**白板管理的核心原则只有一句话：**
白板上的每一寸空间都要值得。

**六个实用方法：
第一：开新对话**
最简单最粗暴。话题换了，就开新对话。不要一个对话里又聊 Mimo 又学 Context 又讨论投资——每个话题独立，白板永远干净。
你今天其实就在这样做——学习是一个对话，做 Mimo 是另一个对话。
**第二：上传文件代替粘贴**
很多人喜欢把长文章直接粘进对话——这会把白板的大块空间一次性用掉，而且之后每次回复都带着它。
上传文件更聪明，Claude 按需读取，不会把整个文件压在白板上。
**第三：总结后再继续**
对话很长的时候，可以说”帮我总结一下我们今天聊了什么”，然后开新对话，把总结粘进去继续。
相当于把满满的白板拍张照，擦掉，然后把照片贴上去——信息密度更高，占的空间更少。
**第四：说清楚，不啰嗦**
每次问问题，说清楚最关键的信息就够了。不需要每次都把背景重新解释一遍——你的记忆文件已经帮你记着了，不用重复写在白板上。
**第五：别让 Claude 重复自己**
有时候 Claude 回答很长，里面有很多你已经知道的内容。你可以说”简短一点”或者”跳过基础部分”——这样下一轮回复短，白板压力小，对话能撑更久。
**第六：Compaction 自动帮你**
现在的 Claude 有自动压缩机制，快满了会自动整理。但这个是被动的——主动管理永远比被动压缩效果好。

**对你最相关的一条：**
你现在用 iPad 跟我学习，用电脑跟 Claude Code 做 Mimo——这个分工本身就是很好的 Context 管理。学习的白板和开发的白板分开，两边都干净，互不干扰。

**一句话总结 Context：**
Context Window 是白板，Token 是空间，Compaction 是自动整理，而最好的管理是——**从一开始就只把值得的东西写上去**。

**第一个：Prompt Caching 怎么工作，Project Knowledge 是自动缓存的吗？**
用白板比喻来说：
普通对话——每次开新对话，白板上的系统提示词、记忆文件都要重新写一遍，每次都要花 Token。

Project Knowledge 里的文件，Anthropic 确实会自动缓存——因为这些文件每次对话都一样，正是 Caching 最适合的场景。你不需要手动设置，放进去就自动享受缓存。
所以 Project Knowledge 的真正优势是两层：
- **方便**：每次自动加载，不用手动上传
- **便宜**：缓存读取只需要标准价格的10%

Claude 也一样。100万Token都在白板上，Claude 技术上都”看到”了，但越靠近窗口边缘的内容，推理时能调用的精度越低。早期内容会被模糊处理，细节丢失，只剩大概的印象。

好，搜到了，有个重要发现——我之前说的”Project Knowledge 自动缓存”需要纠正一下：

**Prompt Caching 是怎么工作的：**
缓存的原理是匹配请求开头的”前缀”——每次对话，系统提示词、Project 文件这些不变的内容放在最前面，新的对话内容追加在最后。前面不变的部分就能被缓存复用，只有最新那一轮需要重新处理。
用白板比喻：白板上固定不动的那部分拍了张照片存起来，每次只需要重新写新的内容，不用把整块白板重写一遍。

**谁来决定缓存什么：**
这里有个重要区分——
**API 层面（开发者用）**：需要开发者在代码里标记哪些内容要缓存，不是全自动的。
**Claude Code 和 claude.ai（你用的）**：缓存是默认开启的，系统提示词、工具定义、CLAUDE.md 每次都自动缓存，你不需要手动设置。
所以对你来说——放进 Project Knowledge 的文件，Anthropic 会自动处理缓存，你不需要管。

**但有一个会破坏缓存的操作：**
缓存是基于完全相同的内容——哪怕一个空格不同，缓存就失效，要重新写。
所以 Project Knowledge 里的文件，**不要频繁修改**。每次改动都会让缓存失效，重新写一次要付全价。这也是为什么 constitution.md 适合放 Project——它是长期稳定的原则文件，不会天天改。
ledger.md 就要注意——每次决策后你会追加新内容，追加了就会让缓存失效。但这个影响不大，因为 ledger 本身不是很大的文件。

清楚了吗？总结一句：**自动缓存，稳定内容受益最大，频繁改动的文件缓存效果有限。** 😄

**对应到 Claude：**

所以”命中缓存便宜”的意思是：
这次对话的背景跟上次一样，不用重新处理那部分，省了钱。
跟你问的问题别不别人问过，完全没有关系😄
