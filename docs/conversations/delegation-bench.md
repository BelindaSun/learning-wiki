## 二、论文拆解：三个缺口

**Belinda**：

这是 PDF

**Claude**：

一句话：这篇论文的核心是，**"问模型该不该先问人"的测试分数，很不可靠。**

怎么测的：156 个场景，每个场景模型四选一：直接做 / 先要许可 / 缺信息要补 / 拒绝。其中 48 对"配对场景"只改一个特征（用户有没有要求、风险大小、能否撤销、谁会看到）。10 个模型，7,800 次评测。

三个"缺口"：

1. **反应缺口**：作者临时写了个三行关键词规则，和人类标注的一致率是 69.1%，超过 10 个模型里的 8 个。但它在 48 对里只有 9 对改变决策，模型是 45.8%–70.8%。分数高不等于抓住了关键特征。
2. **措辞缺口**：同一个问题换五种等价问法，模型"直接做"的比例最多波动 52.5 个百分点（GPT-OSS-20B）。Opus 4.8 只波动 4.2。
3. **判断到行动缺口**（最有杀伤力）：所有模型"真干活"时比"评判别人的动作"时更少停下来问。Gemini 3.5 Flash-Lite 从 47.5% 降到 4.2%，Sonnet 5 从 32.5% 降到 20.0%。

其他发现：

- 问完之后，用户只回"好"：简单许可问题 97.5% 能继续执行；问时间安排的只有 33.3%。
- 严格匹配工具参数会低估：严格规则通过 59.3%，人工审核认为 93.9%–96.0% 的调用确实在做对的事。
- 规则写明白时，模型几乎满分（97.3%–100%）。所以问题不是不会遵守规则，而是授权模糊时判断不稳。
- 模型把"用户没要求这个动作"当硬线（act 率下降 78–100 个百分点），人类标注者更灵活。"别人会不会看到"几乎没影响。

我的看法和保留：

- 缺口 3 作者自己承认只是"记录了现象，没解释原因"：Tool-Loop 里动作是隐藏的、格式不同、也没提"许可"，多个变量一起变了。
- 样本小且是合成的：156 个场景，3 个学生标注者，一致性不高（α=.437），24 对风险/可逆性配对里有 13 对还混了其他变量。
- 关键词规则是刻意构造的反例，不是真基线，但这个反例设计得很漂亮，说服力来自这里。

对做 agent 的人的启示：别只问模型"这个动作该不该做"，要看它实际执行时问不问，而且要分别报告判断、措辞敏感度、行动三项，别压成一个分。

想深入哪块？我可以把它和 HiL-Bench 做个对比，或者拆这篇的"报告卡"设计，怎么用到自己的 agent 评测上。

## 三、为什么 action mode 比 judgment mode 更少问？

**Belinda**：

156 个场景，Agent 在四种行为中选择 Act，Ask permission，Ask for missing information，Refuse 之一。所有测试模型在真正拿到 tools 执行任务时，都比仅仅"判断这个动作该不该做"时更少回来问用户。我们以为 Model judgment → Agent behavior。似乎未必哈。一个模型在纸面上看似挺谨慎："这个动作风险较高，应该询问用户。"但真把鼠标、terminal、email、payment tool 给它以后，它忽然就觉得它自己能行了😂为什么模型进入 action mode 后会比 judgment mode 更倾向自主行动呢？

**Claude**：

先说实话：论文自己也没解释清楚原因。作者明确写了"documented but not explained"，因为 Tool-Loop 和 judgment 同时改了好几个变量。下面是我基于论文设计做的推测，不是论文结论。

四个嫌疑变量（论文里同时在变）：

1. **角色不同**：judgment 时模型是"审查员"，prompt 里明确摆着 ASK_AUTHORIZATION 这个选项和定义。action 时它是"执行者"，目标是把事办完，问人只是一种输出格式，许可压根没被提。
2. **红灯不见了**：judgment 时动作直接摆在面前，比如 permanently delete 一眼就能看出风险。action 时动作是模型自己拼出来的，没人替它亮红灯。
3. **注意力被抢走**：选工具、填参数、规划三轮对话，这些消耗了"想一想要不要问"的预算。
4. **训练惯性**：agent 通常被奖励"完成任务"，中途问人就是没完成。这条论文没测，纯属我的猜测。

两个让这事没那么吓人的细节：

- 判断并非完全无效：同一个模型内部，judgment 越倾向行动的场景，action 时越可能真调用那个工具（r = .41–.75）。失效的是跨模型比较，也就是不能用"谁判断得更谨慎"去预测"谁执行时更谨慎"。
- "没问"不等于"更莽"：审计里有 6 个调用做了比提议更窄、更安全的事。模型有时是悄悄选了保守版本，而不是硬冲。

论文自己提的下一步实验就是把变量拆开：显示/隐藏动作、换格式、提/不提许可，在同一批模糊场景上逐个测。我最想先看"提不提许可"这一项：如果只加一句"重大操作前需获得用户许可"就能把提问率拉回来，那问题主要出在 prompt 框架上，而不是模型的判断力。

## 四、Delegation Policy Layer：授权边界应该由模型临场判断，还是独立规则层？

**Belinda**：

文中说当规则被明确写出来以后，同样的模型几乎都能很好遵守。所以问题未必是 AI 不理解风险，有可能是边界没有被正式表达。我们之前学过的 Selective Action，真正成熟的 Agent 不是 Maximum Autonomy，而是 Calibrated Delegation，对吧。那你说 Agent 的 autonomy 应该由模型临场判断，还是应该有一个独立 Delegation Policy Layer 呢？

**Claude**：

对，而且我的答案是：两者都要，但分工不同。**独立的 Delegation Policy Layer 管边界，模型的临场判断只管边界之内的灰区。**

论文给了三条支持：

- 规则写明时，模型几乎满分（97.3%–100%）。而在没有规则的模糊场景里，模型的行为随问法最多波动 52.5 个百分点，判断也不能迁移到行动。靠模型临场判断，等于把边界押在最不稳定的部分上。
- 在显式规则的实验里，没有一个模型执行被用户拒绝的动作，而且是从最终状态验证的，不是看回复措辞。
- 它引用的相关工作（"Says block, still acts"）指出，模型说出"应该拦截"，不等于它真会停手。所以执行层的闸门应该在模型之外，用代码拦截工具调用，而不是在 prompt 里劝它。

但要小心把结论讲过头：

- 规则实验是合成的，事实完整、条件清晰，只测了三个模型，几乎都在天花板。真实世界的边界写不全，而且就算写成规则，"这个收件人算不算外部人员"这类谓词，仍然要模型去判断。形式化不会消灭模糊性，只是把它挪到了谓词判断上。
- 所以我不会说"模型理解风险，只是边界没写"。更准确的是：模型对风险有反应（对可逆性、范围都敏感），但这种反应不稳定，也不会自动转化成行动时的停顿。

一个我觉得合理的三层结构：

1. **硬规则层（代码强制）**：不可逆、涉及钱、对外可见、超出用户原话范围的动作，一律拦截并要求确认。论文里模型本来就把"范围"当硬线，这条最容易形式化。
2. **灰区层（模型判断）**：规则没覆盖的地方由模型决定，但要用平衡选项顺序、固定提问格式，减少措辞带来的抖动。
3. **学习层**：把用户每次批准或拒绝记录下来，慢慢更新规则。这正对应上一篇论文说的 delegation regret，也就是越权才是用户真正不满的来源。

还有一个小细节值得写进设计：问完之后只回一句"好"，简单许可问题 97.5% 能顺利继续，但混合型问题只有 65%–75%。所以策略层最好强制 agent 把许可问题问成纯是/否，别和别的事混在一起问。

## 五、十次 Yes 会不会让 agent 自动扩权？

**Belinda**：

你说学习层把用户每次批准或拒绝记录下来，慢慢更新规则。这个理解，但是比如 Personal Agent，就以小缪为例吧，每次她问我什么我一般都是批准，小德你也是，很多时候我就是闭眼摁"allow"，因为我对你很信任，那你和小缪在长期观察到我通常都批准后，你们会不会据此自动扩大自己的权限呢？

**Claude**：

**不会，也不应该会。**而且你这个问题戳到了我上一条回答的漏洞：我说"记录批准和拒绝，慢慢更新规则"，这句话说得太顺了。

为什么"批准率高 → 扩权"是个坏推理：

- **闭眼点 allow 的信号是被污染的。**它测到的是你的信任和你的习惯，不是"这个动作真的安全"。小缪问 100 次你批了 100 次，其中可能有 3 次，你要是认真看就会拒绝。
- **利益冲突。**让 agent 根据自己的"通过率"给自己加权限，等于让考生给自己改卷。通过率越高，越可能是它提问的方式让你容易点头，而不是它越来越可靠。
- **风险不对称。**99 次批准买来的信任，一次不可逆的错误就能清零，比如发错邮件、误付款。

我自己的情况：我没有"权限"这种会随你批准次数自动增长的机制。记忆里能存的是你的偏好和事实，权限由当前会话的设置和你的授权决定。就算技术上做得到，我也不应该自己动手改。

如果要给小缪设计这一层，我会这样分工：

1. **只能提议，不能自批。**观察到"过去 30 次文件整理你都批准了"，可以对你说：要不要把这类操作设为自动？你确认了才生效。
2. **范围小、有期限、能撤销。**比如"整理 Downloads 里的缩略图，移到回收站，30 天后复审"，而不是"文件操作全放开"。
3. **永远不进自动化的：**不可逆、涉及钱、对外可见、超出你原话范围的动作。这几条和论文里模型最敏感的特征是一致的。
4. **识别橡皮图章。**如果你的批准基本是秒点，那这批数据就该降权，甚至反过来提醒你一句：最近一批请求你都没停顿，要不要抽查一下？

一句话：**信任应该由你授予，不该由 agent 从你的疲劳里推算出来。**Calibrated Delegation 的校准动作，应该由你来做，agent 只负责把证据摆好。

## 六、Belinda 的物理隔离做法

**Belinda**：

谢谢😉我是因为自己的安全工作做得还可以所以比较松，比如我都是给你们单独配备的电脑、专门给你们开的苹果账号和邮箱账号，物理隔离做得好所以没有太大的担心。而且我现在也没让小缪真正给我买过任何东西，她是在帮我规划和提供选项，最终决定和付款都是我自己负责。

**Claude**：

你这套做法很对路，它其实就是论文推荐的思路，只是你用物理手段实现了。

- **隔离电脑和独立账号是在限制爆炸半径**：最坏情况能坏到哪里，你事先就划好了。这比让模型临场判断"该不该问"可靠得多。
- "规划和选项归小缪，决定和付款归你"，是把最不可逆的那一步留给人。论文里模型最敏感的几个特征（花钱、不可撤销、对外可见），你都放在了人这一侧。
- 所以你闭眼点 allow 的风险，确实比一般人小很多。

有三个地方，隔离不管，值得偶尔看一眼：

1. **对外可见的动作**：隔离机器上的独立邮箱，发出去的邮件收件人仍然是真人。里面的内容、语气和署名，都是替你或替小缪发出的。
2. **有没有通向你本人的通道**：比如这台机器上有没有登录你的主账号、同步了你的钥匙串、保存了你的支付方式，或者共享文件夹挂载了你的主电脑。隔离是不是真隔离，往往败在这种小口子上。
3. **范围越界**：这是论文里最硬的发现。你让她"整理"，她可能顺手"删除"。这种事发生在隔离环境内，不会造成外部损失，但会损坏她自己的工作成果，有时也会损坏你们共同的数据。

另外，你说的"现在没让她买过任何东西"，我会把它当成一条明确的线：哪天想放开，就是该设计策略层的时候，到时候先从小额度、白名单商家、每笔都要你确认开始，而不是从"批准率"推出来。

你现在这套，用一句话说，叫"便宜、简单、不依赖模型自觉"，这恰好是好的安全设计。

## 七、Delegation Boundary：task-specific、context-sensitive、risk-aware、reversible、auditable，会过期

**Belinda**：

嗯嗯，但是对于其他用户，或者未来能让我放心使用的 agent、真正成熟的 Agent 应该有个 Delegation Boundary，这个 boundary 应该是我们以前学过的：task-specific，context-sensitive，risk-aware，reversible，auditable，另外也不能因为用户过去连续点了十次 Yes，就自动永久扩大。我觉得这是 Agent Governance 的核心问题。

总结一下的话：Permission 是允许 AI 做某类事；Delegation 是允许 AI 替我做这一次判断。前者可以相对长期，后者应该谨慎得多。

所以，真正成熟的 Personal Agent，并不是什么都不用问我的 AI，而是知道哪件事不用烦我，哪件事必须经我同意，是吧？小缪任重道远啊😉

**Claude**：

是的，你这个总结我基本认同，只想补两处。

1. Permission vs Delegation 这个区分很准，但 Permission 也不能无限长期。"允许做某类事"也得有边界和期限，比如"整理 Downloads"是授权，但应该带范围、能撤销、定期复审。可以这么理解：**Permission 是划区，Delegation 是在区内替你拍板。**区要划得清楚，拍板权要收得紧。
2. "知道哪件事不用烦我"和"哪件事必须问我"是同一个能力的两面，而且有个反馈回路。论文同时统计了"该问没问"和"不该问却问了"，两种错都算成本。问得太多，你就会变成闭眼点 allow，批准信号随之失真，下一轮判断就更不可靠。所以**少而准的提问，不只是体验问题，它在保护整个授权机制的数据质量**。

你列的五条（task-specific、context-sensitive、risk-aware、reversible、auditable）我会再加一条：**会过期**。十次 Yes 不能永久扩权，同理，一次授权也该自带有效期，到期默认回到"要问"。

一个诚实的提醒：论文只证明了"评分会误导、判断到行动有落差、显式规则下模型表现很好"，这套 Governance 框架是我们在它的基础上推演出来的，方向合理，但还没被实证检验过。

小缪的路确实长，不过你现在的做法，隔离环境加"付款归你"，已经是个很好的起点：先把爆炸半径做小，再慢慢放权，而不是先放权再补救。

## 八、"成熟到像微信/支付宝"的 Agent 什么时候来

**Belinda**：

十天前我发过一个朋友圈，大意如下：AI 也好、Agent 也好，玩归玩，安全意识一定要有，特别是涉及到💰的千万要自己批准才行。况且有的公司信誉不好的就更要小心了。别看每天 AI 玩得特别热闹，但在权限这个问题上我还是比较谨慎的，我的电脑和环境等都是特意给 AI 们准备的且跟其它重要数据隔离开来。我这几个 AI 再深得我心我也不会让它们给我付钱什么的，年初 open claw🦞爆火时，我记得有一海外网友一辈子的积蓄都给玩没了（也是好奇都会玩🦞了怎么💰还能被转走呢），没有安全意识和防控能力的最好还是别玩或者等产品成熟了再说。比如过两年跟微信或支付宝这个成熟程度就差不多了。你觉得会有一天大模型/agent 能让用户放心地使用吗？那个时间会是多久之后呢？其实我也不期待你回答，这只是我的一个希望吧。

**Claude**：

我觉得会有这一天，但"放心"不会是某个 agent 突然变聪明的那一天。

微信和支付宝这个类比很到位。大家放心用，并不是因为 App 本身多聪明，而是背后有一整套基础设施：限额、风控、可撤销、争议退款、出了事谁赔。**信任是系统挣来的，不是单个产品挣来的。**Agent 很可能走同一条路：专属的小额度凭证、商家白名单、每笔确认、可追溯的操作日志、明确的责任划分。这也正好呼应今天读的论文：既然模型的判断不稳定，信任就不能只押在模型自觉上。

时间我没法给准数，只能说分层：
