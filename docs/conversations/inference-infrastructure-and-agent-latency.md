**核心概念（Cerebras 那篇）**：

大模型推理其实分两个性质完全不同的阶段：

- Prefill（预填充）：并行处理输入 prompt，构建 KV cache，是算力密集型（compute-bound）
- Decode（解码）：逐 token 生成，只能串行，是内存带宽密集型（memory-bandwidth-bound）

传统 GPU 用同一块芯片扛两种负载，本质上是"一个厨子既要备菜又要现炒"，互相干扰。解构式推理的做法是把这两个阶段拆到不同硬件上跑：计算优化型硬件专门做 prefill，内存带宽优化型硬件专门做 decode，中间靠 KV cache 传递。

**商业落地（AMD 那篇，2026 年 7 月发布）**：

AMD 和 Cerebras 正式宣布合作——AMD Helios（机柜级方案，负责高吞吐量的 prompt/prefill 处理）+ Cerebras 晶圆级引擎 WSE（负责超低延迟的 decode/token 生成），两者组成单一解构式工作流。声称能带来高达 5 倍的每瓦每秒 Token 数（T/s/W）提升，2026 年下半年先通过 Cerebras Cloud 提供。

**为什么这两篇对你有意义**：

这其实是 Agent 系统架构层面的一个关键变量——你在学的"tool selection 和决策机制"背后，有一个经常被忽略的物理约束：Agent 的多步骤链条（tool call → 观察 → 下一步决策）对延迟极其敏感，而不只是对吞吐量敏感。Cerebras 文章里那个例子很说明问题：10 步 Agent 链条在 50 tok/s 下要 30+ 秒，在 1200 tok/s 下不到 3 秒——这不是同一个体验。

换句话说，Agent 能不能"感觉起来像实时"，未来 18 个月内会越来越多取决于基础设施层的解构化，而不只是 prompt 或 orchestration 层的优化。这条线值得记进你的 Wiki 的 "AI Core" 分类——可以叫"推理基础设施与 Agent 延迟"这类条目。

你给我稍微展开了讲讲为什么 Prefill 与 Decode 的计算特性不同。

值得展开讲清楚，因为这是理解整个"硬件竞赛"叙事的根基——两个阶段的差异不是工程实现细节，而是数学结构本身决定的。

**Prefill：一次性的并行矩阵运算**

处理输入 prompt 时，N 个 token 是已知的、摆在那里的。模型对这 N 个 token 同时做前向计算——这在数学上是一次矩阵乘矩阵（GEMM）运算：一个 [N × d] 的输入矩阵，乘以权重矩阵。矩阵越大，每次从内存读取一份权重后能重复利用的次数越多（这个比值叫"算术强度"，FLOPs / 读取字节数）。GPU 的计算核心可以被喂得很饱，因为数据搬运一次、计算做很多次——这就是"compute-bound"。

**Decode：被迫串行的内存读取**

生成阶段完全不同。第 t 个 token 必须先生成出来，才能作为输入去算第 t+1 个——这是自回归模型的因果约束，没法并行化。每一步，你只处理 1 个新 token，但为了算它对之前所有 token 的注意力，你必须把已经缓存好的全部历史 K、V（KV cache）从内存里重新读一遍。计算量很小（矩阵乘向量），但数据搬运量很大，而且随对话变长，KV cache 越来越大，每步要读的数据也越来越多。算术强度极低——大量时间花在"等数据从内存搬过来"，而不是"算"。这就是"memory-bandwidth-bound"。

我画一张图直观对比一下这两种模式：

```
Prefill（并行）                    Decode（串行）
[token1 token2 ... tokenN]         [token_t] → 生成 → [token_t+1] → 生成 → ...
      ↓ 一次性                            ↓ 每步都要
   矩阵乘矩阵 (GEMM)                  重新读一遍 KV cache
   算力被喂饱                          矩阵乘向量 (GEMV)
   compute-bound                     memory-bandwidth-bound
```

**再往下一层，为什么这决定了硬件选型**：

- Prefill 阶段，GPU 的大量并行计算核心是被喂饱的，所以传统 GPU（本质上是为大规模并行矩阵运算设计的）在这个阶段表现很好。
- Decode 阶段，瓶颈从来不是"算得快不快"，而是"内存搬得快不快"。这就是为什么 Cerebras WSE 这种把 SRAM 直接堆在芯片上（不走 off-chip HBM）的架构，在 decode 阶段能有巨大优势——它绕开了内存带宽这个物理瓶颈。

这也解释了为什么 AMD+Cerebras 的方案分工是"AMD Helios 管 prefill、Cerebras WSE 管 decode"——本质上是让每种硬件去做它数学结构上天生擅长的那一半。而昨天那篇 xPU-athalon 论文提醒你的地方在于：这种"专用化"要在利用率足够高的前提下才划算，否则专用芯片的空闲功耗劣势会把理论增益吃掉。

明白了，我之前听播客的时候听到一句话，GPU 在训练时代形成的优势未必可以原封不动复制到 inference，原因就是你刚刚解释的。

说得精准。而且可以再往前推一步说明白"为什么训练时代不会遇到这个问题"：

训练时的前向传播，本质上跟 prefill 是同一种运算模式——大批量数据（batch）、完整序列一起进矩阵乘法，加上反向传播也是稠密的矩阵运算。训练从头到尾都是 compute-bound，GPU 的强项（海量并行 FLOPs）被完全用上，这也是为什么 NVIDIA 靠训练打下的护城河那么深。

但训练根本不存在 decode 这种东西。训练不需要一个 token 一个 token 地、串行地、依赖上一步结果地往外吐——那是推理服务给用户用的时候才有的场景。所以训练时代积累的优势，全部押注在"如何把矩阵乘法做得更快更并行"这一件事上，而这件事恰好是 decode 阶段完全不需要的能力。

这也是为什么这轮硬件竞争格局会松动：不是说 NVIDIA 的芯片不好了，而是推理这个新战场里，胜负手换了——从"谁的并行算力强"变成"谁能用最低延迟把内存里的东西搬出来"。这是两种截然不同的工程优化问题，训练时代积累的优势不能自动平移。

这条逻辑链其实挺适合写进你的 Wiki 里，可以叫"训练优势为何不能平移到推理"——从数学结构（GEMM vs GEMV）→ 硬件含义（compute-bound vs memory-bound）→ 商业含义（NVIDIA 护城河为何在推理侧变浅）这三层串起来，会是一篇很扎实的条目。

行，先记下来。我还有一个具体问题，如果未来一个 Agent 一次任务要产生几十万甚至几百万 token，tokens/sec、latency、tokens/$、tokens/watt 中究竟哪个指标最重要？

这个问题问到点子上了，答案不是单选题，但有主次之分——关键在于先把"一次任务几十万到几百万 token"拆开看：这几乎不可能是一次性生成，而是一个 agent 循环里几十次、几百次的连续调用（观察 → 决策 → 工具调用 → 观察……）。这个结构决定了哪个指标真正卡脖子。

**Latency 是第一位的，但不是你想的那种 latency**

对单次巨大输出（比如一次性吐出十万字报告），latency 影响很小——反正你要等它跑完，TTFT（首 token 延迟）占比可以忽略。但 agent 任务不是这样：它是几十上百个串行、互相依赖的小步骤。第 N 步的输出是第 N+1 步的输入，不能并行。这正是 Cerebras 那篇文章举的例子——10 步链条，50 tok/s 要 30 秒以上，1200 tok/s 只要 3 秒。这里的关键是，tokens/sec 和 latency 在这个场景下其实是同一件事：每一步的生成速度，直接决定了这一步的延迟，而延迟又会在几十个步骤上复利式累加。所以对 agent 而言，真正卡住任务能不能在可接受时间内跑完的，是"单步延迟能不能压到最低"，本质就是小 batch 下的 decode 速度。

**tokens/$ 决定这件事能不能规模化做**

一个任务消耗几十万到百万 token，如果你要跑成千上万次（多用户、多次迭代、失败重试），成本是线性累加的。这不是"跑得动跑不动"的问题，是"划不划算"的问题。tokens/$ 决定了你的 agent 产品有没有商业上的生存空间——哪怕速度够快，如果每次任务成本几十美元，大部分应用场景直接死在门口。

**tokens/watt 其实不是你要直接优化的指标**

除非你自己在运营硬件（数据中心那个层面），否则 tokens/watt 对你来说是间接的——它是芯片厂商和云厂商成本结构的底层驱动力，最终会体现在他们卖给你的 tokens/$ 价格里。作为一个用 API 的 agent 构建者，你感知不到瓦特，你只感知到账单。所以这个指标重要，但重要性是"传导"给你的，不是你直接面对的。

**结论排序（针对你这种 agent 构建者的视角）**：

1. 单步 latency / 小 batch 下的 tokens/sec —— 决定任务能不能在合理时间内跑完，尤其是链条越长，这个影响越是指数级累加
2. tokens/$ —— 决定这件事能不能规模化、能不能商业化
3. 聚合 tokens/sec（大 batch 吞吐量）—— 这更多是服务商（比如 Cerebras、AWS）关心的指标，决定他们能同时服务多少用户，间接影响你能拿到的价格和排队情况
4. tokens/watt —— 上游物理约束，通过价格传导给你，不是你直接优化的对象

一句话总结你播客里那句话背后的逻辑：训练时代大家比拼"谁能堆更多卡训得更快"，这个赛道上吞吐量和成本是主角；但 agent 推理时代，比拼的是"谁能在长链条的每一步都做到低延迟同时不把你吃穷"——latency 和 cost 变成一对绑在一起的双主角，而算力堆叠反而成了配角。

这个问题问得很准，因为"workload"这个词在论文里其实是个容器，装的是好几个维度，值得拆开说。

**核心思路：workload 描述的是"这个任务的 token 消耗形状长什么样"**

同样是大模型推理，不同应用场景里 prefill 和 decode 的比例、请求节奏、延迟容忍度完全不同。这些差异合起来就是"workload"，它跟前面说的 batch size、sequence length、model size 是相互交织的，但更侧重"这个任务的使用场景本身是什么样子"。

拿几个具体场景对比一下你会立刻有感觉：

**1. 输入输出比例（prefill 与 decode 谁占大头）**

- 长文档摘要：输入几万字，输出几百字。几乎全是 prefill，decode 很轻。这种场景，compute-bound 的硬件（比如传统 GPU）很吃香。
- 创意写作 / 聊天续写：输入几十个字，输出几千字。几乎全是 decode。这种场景，内存带宽型硬件（比如 Cerebras WSE）优势巨大。
- Agent 多步任务（你自己在做的 Mimo、Mivo 这类）：这是最复杂的一种——每一步输入都不长（几百到几千 token 的上下文），但要循环几十次，每次都要重新读一遍不断增长的 KV cache。这既不是纯 prefill 也不是纯 decode，而是"反复的短 decode + 频繁的小 prefill"交替出现，这种混合形状对硬件的要求最挑剔。

**2. 延迟容忍度（SLA 要求）**

- 离线批处理（比如你半夜跑一批分析报告）：没人在等，几分钟出结果都行。这时候你要的是吞吐量（tokens/$），可以把很多请求塞进一个大 batch，慢慢跑，便宜就行。
- 实时交互（用户在打字框里等你回复，或者 agent 在做实时决策）：每一秒延迟都会被用户感知到。这时候你要的是低延迟，哪怕成本贵一点，也得让单次请求跑得快。

同样的模型、同样的硬件，一个拿来做离线批处理和一个拿来做实时聊天，最优配置策略是完全相反的——前者你会故意攒大 batch 提高利用率，后者你会尽量减小 batch 换取响应速度。

**3. 请求到达模式（并发形态）**

- 稳定的、可预测的请求流（比如某个固定时间跑的定时任务）
- 突发的、不规律的并发（比如很多用户同时在线聊天，高峰期一拥而上）

这决定了硬件在低利用率时段会不会"空转浪费"——回到你昨天问的那篇论文，Cerebras/SambaNova/Gaudi 空闲功耗比 GPU 高 10-60%，如果你的 workload 请求是稀疏、不规律的，这些专用芯片的能效优势就会被大量空闲时间吃掉。

串回你的问题本身：论文说"最优硬件随 workload 变化"，翻译过来就是——没有一个芯片能同时在"长文档摘要"、"实时聊天"、"agent 多步任务"、"离线批量生成"这四种完全不同的 token 消耗形状里都拿第一。因为每种 workload 对 prefill/decode 比例、延迟容忍度、利用率模式的要求都不一样，而硬件架构本身就是在这些维度上做取舍设计出来的。

对你来说最实用的推论是：如果以后要为 Mimo 或 Mivo 这类 agent 系统选择底层模型/API 服务商，第一件要搞清楚的事不是"哪家最快最便宜"，而是"我的 agent 任务的 workload 形状是什么样"——是频繁小步骤的交互式 agent，还是偶尔跑一次的长文档处理？这个问题的答案会直接决定哪家的解构式推理架构最适合你。

是的，这个判断方向对，而且可以把"有多大"和"变在哪"说得更具体一点。

**这不是一次硬件换代，而是一次产业结构重排**

过去十几年 AI 计算的默认答案就是"买更多 GPU、堆更大集群"——这是单一垂直供应链：NVIDIA 设计芯片，云厂商买卡，大家在同一套架构上竞争谁的集群更大。这个格局的护城河建立在"通用计算 + 规模优势"上。

解构式推理这条路一旦成立（而且从 Cerebras/AMD/AWS 这几家都在同时推进来看，方向已经比较确定），意味着推理这个环节从"整块蛋糕归 NVIDIA"变成"每个阶段可以分给不同专长的玩家"——prefill 归擅长并行计算的、decode 归擅长内存带宽的、还可能有专门做路由调度、专门做 KV cache 传输网络的公司插进来。这在结构上更像是从"垂直整合"走向"分层竞争"，跟当年 PC 产业从"IBM 一家包圆"走向"Intel 做 CPU、微软做系统、别人做外设"是同一种模式转移。

**几个具体会被撬动的地方**：

1. NVIDIA 的护城河会变窄，但不会消失。训练侧的优势短期内很难被替代，但推理侧（现在已经是更大的收入池，因为模型训练一次、被查询几十亿次）会出现真正的多强格局。这也是为什么 NVIDIA 自己花 200 亿美元收购 Groq——它自己也在赌"如果不能靠通用 GPU 通吃推理，那就直接买一个专精的"。
2. 云厂商的角色在变化。AWS 把 Trainium 和 Cerebras CS-3 拼在一起卖，这本质上是云厂商在做"混合基础设施编排"，而不是单纯转卖别人的芯片。这个能力本身会成为新的竞争壁垒——谁能把异构硬件调度得最顺，谁就有议价权。
3. 对你这种 agent 应用开发者来说，选型会变得更专业化。以前"用哪个模型"是唯一要决策的事；未来"用哪个模型 + 跑在哪种基础设施上 + 针对我的 workload 形状怎么配"会变成一个组合决策。这也意味着，懂 workload 特征、懂怎么匹配硬件的人（哪怕不是芯片工程师，而是像你这样理解 agent 系统架构的人）会有更强的判断力优势。

**但要泼一点冷水，呼应你之前看的那篇论文**：

这个变化目前还处于"技术方向确立，商业格局未定"的阶段。xPU-athalon 那篇论文测出来的结论——软件栈成熟度参差不齐、空闲功耗劣势明显——说明现在下"专用硬件必然赢"的结论还太早。真正决定这次产业重排走多深、走多快的，是编译器和软件生态能不能跟上（Dynamo、SGLang、vLLM 这些框架现在都在支持解构式部署，这是个好信号），以及利用率能不能做到足够高，把专用硬件的效率优势兑现成实际的成本优势。

那我看有人说 AI infrastructure 正在从 homogeneous computing（同构计算）走向 heterogeneous computing（异构计算），这么说对吗？也有点为时过早吗？

这个说法基本准确，但"为时过早"这个直觉也是对的——准确地说，方向已经清晰，但"异构计算"这个词现在被用得有点超前于现实。可以分两层说。

**"方向对"的部分：这个转变确实在发生，而且逻辑是自洽的**

同构计算的逻辑是："一种硬件，通用到能处理所有工作负载"——这是 GPU 过去十年的定位。异构计算的逻辑是："不同的计算特性交给不同的专用硬件"。你我们这几天聊的内容，从 prefill/decode 的数学差异，到硬件厂商实际的产品动作（AWS+Cerebras、AMD+Cerebras），到 workload 形状决定最优硬件——这条逻辑链每一环都在支持"异构化正在发生"这个判断。而且这不是孤例：NVIDIA 自己收购 Groq，本质上也是在为异构化做准备（哪怕它嘴上仍然主打通用 GPU）。所以说"方向对"，是因为多个独立行为者（芯片厂商、云厂商、甚至 NVIDIA 自己）都在用真金白银的商业动作指向同一个方向，这比单纯的技术论文更有说服力。

**"为时过早"的部分：现实和口号之间还有几道坎**

1. 规模。目前真正跑在解构式/异构架构上的推理流量，占全球 AI 推理总量的比例还很小。AWS+Cerebras 这类方案是"率先在 2026 下半年提供"，还处于早期商用阶段。大部分企业的实际推理负载，今天依然老老实实跑在同构的 GPU 集群上。
2. 软件栈没跟上。xPU-athalon 那篇论文已经点出来了——异构硬件之间的编译时间、软件成熟度差异很大。理论上硬件能异构，但如果调度、路由、KV cache 跨设备传输这些软件层没有足够成熟，异构反而会带来额外的复杂度和故障点。现在 vLLM、SGLang、Dynamo 这些框架才刚开始支持解构式部署，生态还在早期。
3. "异构"本身现在更多是巨头间的合作，不是普遍基础设施。目前看到的组合（AWS Trainium + Cerebras、AMD Helios + Cerebras）是几家头部公司之间的定制化合作，不是一个中小开发者今天就能拿到的标准化产品。对大多数 AI 应用开发者（包括你）来说，实际能接触到的接口依然是"调用某个模型的 API"，底层是不是异构，很大程度上被云厂商屏蔽掉了，你感知不到。

**更准确的表述，可能是这样**：

与其说"AI 基础设施正在从同构走向异构"（这句话听起来像是已经发生的既成事实），不如说**"AI 基础设施的架构共识正在从同构转向异构，但真正的异构化落地还处于头部玩家的早期试点阶段"**。技术判断已经形成，商业规模还没跟上。这个时间差本身，其实也是你这种关注 agent 系统与产业趋势的人值得持续追踪的地方——因为一旦软件栈成熟、成本曲线下来，从"少数巨头的定制方案"扩散到"人人可用的标准基础设施"，往往会是一个突然加速的过程，而不是匀速的。

OK，我这样简单总结合适吗：AI 计算的未来可能不是寻找一块更强的万能芯片，而是让不同计算架构在最适合自己的 workload 上协同工作。

这个总结准确，而且抓住了核心——从"找一块最强的芯片"转向"让架构去匹配工作负载"，这正是我们几天聊下来的主线。
