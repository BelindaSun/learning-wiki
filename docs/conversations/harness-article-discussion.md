讲一下什么是harness，再详细讲一下open AI 的harness具体是怎么工作的？

**什么是 Agent Harness（智能体外壳）**
“Harness”这个词本来是”缰绳、挽具”的意思——给马套上挽具,才能让马的力量转化成拉车的效果。在 AI 语境里，它指的是**包裹在大语言模型外面的一整套工程系统**，负责把模型的”裸能力”转化成能真正完成任务的智能体行为。
模型本身只会做一件事：接收一段文本，吐出一段文本。但要让它变成一个能自主完成任务的 agent（比如写代码、跑测试、改文件），中间还需要:
- **管理上下文**：决定每一步该往模型的上下文窗口里塞什么信息（历史对话、文件内容、工具输出等），因为窗口大小有限，塞太多既贵又可能让模型”注意力涣散”
- **工具调度**：定义模型能调用哪些工具（读文件、写代码、跑命令、搜网页等），把模型的调用请求转成真实的系统操作，再把结果喂回去
- **循环控制**：决定模型什么时候该继续”思考/行动”，什么时候任务已经完成该停下来，避免陷入死循环或者过早收工
- **纠错与引导**：当模型跑偏、报错或者卡住时，用额外的提示把它拉回正轨

所以 harness 不是模型本身，而是**让模型可用的”操作系统”**。同一个底层模型，配上不同的 harness，实际表现可能天差地别——这也是为什么 Claude Code、Codex、Cursor 这些产品即便调用类似的底层模型，用户体验和效率也完全不同。
**OpenAI 的 harness 具体是怎么工作的**
根据这篇文章，OpenAI 把这套系统描述成”乐队指挥”：它统筹三方——用户、模型、工具——具体做的事情包括：
1. **接收并拆解用户目标**：理解用户想要什么
2. **管理上下文**：决定在多轮任务执行中，哪些历史信息、文件内容需要保留在上下文里
3. **连接插件和能力**：把合适的工具/插件接入到当前任务中
4. **执行动作**：真正代替模型去调用工具、跑代码、改文件
5. **持续监督进度**：确保模型不偏离任务，直到任务完成才收尾

文章里提到的关键突破是**效率优化**：同一套 harness、推理层、API 栈被专门打磨过，结果是新模型能用远少于以往的 token 数完成同等甚至更好的任务（比如某个模型在编程测试中超越对手的同时，输出 token 减少了一半以上)。这背后的逻辑是：外壳设计得越聪明，就能用更精简的上下文和更少的来回调用，让模型少”绕弯子”、少浪费 token,从而把整体推理成本压下来。
还有一个细节值得一提：OpenAI 这套 Codex 外壳是**开源**的，这跟 Anthropic 不公开 Claude Code 外壳源码的做法形成对比——这意味着外部开发者可以直接研究、复用甚至改造这套系统。

既然开源了，肯定有不少用户研究过了，你能找找有没有人研究并分享过它具体是怎么实现的吗？

找到了——OpenAI 官方工程博客在今年1月发过一篇《Unrolling the Codex agent loop》,由 Codex 团队工程师 Michael Bolin 撰写,细节非常详实,而且开源仓库(github.com/openai/codex)里的具体代码位置都给了链接。核心内容如下：
**Agent Loop（智能体循环）的基本结构**
每一轮对话(“turn”)的流程是：
1. 用户输入 → 拼接成一份”prompt”（提示文本）
2. 把 prompt 发给模型做推理（inference）
3. 模型要么直接给出回复，要么请求调用一个”工具”（比如运行 shell 命令）
4. 智能体执行这个工具调用,把结果拼回 prompt,再次请求模型
5. 如此循环,直到模型不再请求工具调用、而是给出一条面向用户的”assistant message”为止

**关键点**：每次工具调用之后,新的 prompt 都是在旧 prompt 后面追加内容,而不是重新生成——上一次的 prompt 始终是这一次 prompt 的”精确前缀”。这个设计是有意为之的性能优化（下面会讲）。
**具体怎么构造第一次的 prompt**
Codex 通过 Responses API（OpenAI 的一个 API 接口）来驱动这个循环,请求里主要包含三部分：
- **instructions**（系统级指令）：来自模型专属的指令文件，比如针对某个模型版本单独写的 prompt 文件
- **tools**（工具列表）：包括 Codex 自带的 shell 工具、任务规划工具（update_plan）、网页搜索工具，以及用户通过 MCP 协议接入的外部工具
- **input**（输入内容列表）：这里是最有意思的部分,Codex 会按顺序塞入好几类内容：

  1. 一条描述”沙箱环境”的开发者消息——说明 Codex 的 shell 工具有哪些文件权限、网络权限,什么情况下需要先问用户获得批准
  2. （可选）用户在配置文件里自定义的开发者指令
  3. （可选）“用户指令”——这是从项目里多个地方汇总来的，比如项目根目录到当前工作目录之间每一层的 AGENTS.md 文件内容，外加已配置的技能（skills）说明
  4. 一条描述当前运行环境的消息（当前工作目录、用户用的什么 shell）
  5. 最后才是用户真正输入的那条消息

**性能优化的核心：Prompt Caching（提示缓存）**
文章里专门指出一个关键问题：既然每轮对话都在不断往 prompt 里累加内容,那整个对话的计算量岂不是随轮数呈**平方级增长**？
答案是：确实如此，但 OpenAI 用**提示缓存**来解决——只要新请求的开头部分和上一次完全一致（“精确前缀匹配”），模型服务器就能复用之前的计算结果，让每轮的实际计算量变回线性增长而不是平方增长。
这也解释了文章开头提到的”减少 54% token”是怎么来的——凡是会打乱这个”前缀一致性”的操作都要格外小心，比如：
- 对话中途改变可用工具列表
- 中途切换模型
- 改变沙箱配置或工作目录

因此 Codex 团队处理这些变更时,尽量用”追加一条新消息”的方式，而不是修改已有的旧消息，以此保住缓存命中率。文章还提到他们踩过坑：早期支持 MCP 工具时,因为工具列表枚举顺序不一致,导致缓存频繁失效。
**上下文窗口管理：Compaction（压缩）**
当对话变长、逼近模型的上下文窗口上限时，Codex 会做”压缩”（compact）——用一份更小、但能代表整个对话历史的内容列表替换掉原来冗长的 input，让智能体在”记得之前发生了什么”的同时释放出上下文空间。这个机制现在已经自动触发，不需要用户手动执行压缩指令。

这篇文章目前只是系列的第一篇，OpenAI 后续还计划写 CLI 架构、工具调用实现、沙箱模型等主题的深度解析。如果你想看更细的实现（比如具体的 Rust 源码位置），我可以帮你去 github.com/openai/codex 仓库里再深挖。

prompt caching中的中途切换模型，是指从5.5切换到5.6的这种切换吗？这样的切换会导致多费token？我有时就会根据任务复杂度切换，那岂不是浪费token，但要是真有必要的话也只能如此了。

是的，就是这种切换——从 GPT-5.5 换到 GPT-5.6，或者反过来，都算”改变 Responses API 请求的目标模型”。文章里明确把这个列为会导致**缓存失效（cache miss）**的三种操作之一，原因是：每个模型都有专属的 instructions（prompt 里的第三项内容），换模型就等于改了 prompt 开头那部分内容，导致新请求的”前缀”和之前缓存的前缀对不上了。
**具体会多费多少token/钱？**
不是”平白多生成 token”，而是**那一次切换后的请求，拿不到缓存折扣了**。原理是这样：
- 正常情况下，只要新请求的开头和上次完全一致，重复的那部分内容会走缓存价（通常比正常价便宜很多，业内一般缓存命中部分打一折左右）
- 一旦切换模型，prompt 前缀变了，缓存失效，你切换后的**这一次**请求要把全部历史对话内容按**原价**重新计算一遍
- 但这只是”一次性代价”——切换之后，从这次请求开始会在新模型下重新建立新的缓存前缀，后续同一模型内的请求又能正常吃到缓存折扣

所以影响是：**每次切换模型，都要为那一轮对话多付一次”全价”，而不是持续性地浪费**。如果你在一段对话里来回切换（5.5→5.6→5.5→5.6），确实会因为反复失效缓存而多花一些钱，但影响集中在切换那几次请求上，不会无限累积。
**关于你按任务复杂度切换模型这件事**——我的看法是：这笔”缓存失效”的成本通常远小于”用错模型”的成本。简单任务用重模型是浪费算力，复杂任务用轻模型可能导致返工、多轮修正，那才是真正烧钱的地方。缓存失效那一次的额外开销，跟因为模型选错而多跑几轮修复相比，通常是小头。所以如果任务复杂度确实需要换模型，该换还是换，这笔账不用太纠结。

有，Claude Code 就是 Claude 这边对应的”harness”，官方文档把它定位为让 Claude 从”只会说话”变成”能干活”的智能体外壳。它的设计思路和 OpenAI 的 Codex 外壳挺不一样的，挺有意思：
**核心是单线程主循环**
Claude Code 内部代号叫”nO”，走的是一个单线程主循环，配合规范化的工具和规划来实现可控的自主性。这个思路特意跟当下流行的复杂多智能体编排方向反着来——业内很多团队在做”多个 agent 互相协作”的复杂系统，但 Claude Code 团队认为，一个简单的单线程主循环加上严谨的工具和规划，就足以实现可控的自主性，图的是好调试、透明、可靠。
具体运作起来大致是：Claude 收到一个修 bug 的请求 → 用 Grep 搜索相关代码 → 调用 View 读取具体文件 → 用 Edit 修改代码 → 跑 Bash 执行测试 → 最后给出结论——本质上就是”思考、行动、观察，循环”这套模式的放大版。
**几个关键组件**
- **h2A 队列**：支持实时”插话”/引导，你可以在 Claude 执行过程中插入新指令
- **TODO 式规划**：通过任务列表做智能规划
- **受控的子智能体（subagent）生成**：每个子智能体运行在自己独立的上下文窗口里，带独立的系统提示、工具权限，专门处理会”淹没”主对话的高信息量操作（比如翻查几千个文件、解析长日志），只把摘要结果返回给主循环，让主上下文保持干净
- 内存管理和基于 diff 的工作流，作为安全保障

**关于上下文管理**，官方文档也提到类似 Codex 的思路：随着上下文被填满，性能会下降，所以有”effort”级别的调节（简单任务用 low，省 token；复杂调试用 high）,以及通过 SDK 里的 session 机制来续接对话、按需加载 MCP 工具 schema，避免一开始就把所有工具定义塞进 prompt 占用上下文。
跟 Codex 那种”越堆越长、靠 prompt caching 保效率”的思路比，Claude Code 更强调”该分流就分流”——用子智能体把重信息量的活儿隔离到独立上下文里，从源头上控制主循环的膨胀速度，某种程度上算是另一种解决同一个问题（上下文/成本失控）的路子。

OK， Codex没有sub-agent吗？我亲眼看见Claude确实是有的。

Codex 其实现在也有 subagent 了——只是这功能来得比 Claude Code 晚。补充一下时间线和实现细节：
**Codex 是今年3月才正式上线 subagent 的**（之前有过几周的功能开关灰度测试），今年这篇《Unrolling the Codex agent loop》官方博客发的时候（1月），Codex 还是纯单线程循环，所以你之前看到的那篇文章里完全没提到 subagent，这不是我漏讲，是当时确实没有。
**Codex 的 subagent 实现方式**，有分析指出跟 Claude Code 的实现方式很相似，默认提供”explorer”（探索型）、“worker”（工作型）和”default”（默认）三种预置 subagent，此外还能在 ~/.codex/agents/ 目录下用 TOML 文件自定义 subagent。用途上官方也说得很直接：适合处理高度并行的复杂任务，比如探索代码库或者执行一个多步骤的功能开发计划，而且在本地 Codex 客户端里，你还可以给不同任务配置不同模型和不同指令的自定义 agent。
**触发方式**：在交互式 CLI 会话中直接让 Codex 去委派任务，或者靠项目里的 AGENTS.md、技能（skill）指令自动触发委派，用 /agent 命令可以查看和切换正在运行的 agent 线程，最后由主线程把各个 subagent 的结果汇总成最终回复。
**要留意的代价**：因为每个 subagent 都要独立跑一遍模型推理和工具调用，所以 subagent 工作流消耗的 token 会比单智能体跑法更多——这点跟你之前问的”切换模型多费 token”是同一类权衡：并行 subagent 能省时间、能处理更复杂的任务，但账单上会体现出来。
有意思的是社区里还发现了一个小插曲：5.6 版本更新后，用户没法再像以前那样指定 subagent 用哪个模型、什么推理强度了，看来这块功能还在快速迭代中，不算完全成熟。

还有几个问题我想一个一个聊。第一个Agent harness 与模型、Skill、MCP 分别是什么关系？

好问题，这四个概念很容易混在一起，用一张关系图理清楚：
## 一句话定位

## 具体关系
- **模型（Model）**：大脑，负责”思考”——理解输入、做推理、决定下一步做什么
- **Harness（外壳）**：身体和神经系统，负责”执行”——把模型的决策变成真实动作，管理整个对话循环
- **Skill（技能）**：说明书/工作手册，负责”指导”——告诉模型在特定任务上该怎么做得更好
- **MCP（Model Context Protocol）**：接口标准，负责”连接”——让模型能接入外部工具和数据源


**Harness 包裹着模型**，是最外层的容器。前面聊 Codex agent loop 时提到的那套流程——构造 prompt、调用模型推理、解析工具调用请求、执行工具、把结果拼回去、判断何时结束——这一整套逻辑都是 harness 在做。模型本身不知道”文件系统”“shell”是什么，它只是根据 prompt 里描述的工具列表，生成”我想调用哪个工具、传什么参数”这样的文字/结构化输出。**是 harness 负责真正把这个请求转成实际的系统调用，再把结果喂回去。
Skill 是 harness 塞进 prompt 里的一种”预置知识”**。回想 Codex 那篇文章里提到的 input 构造流程——里面专门有一步是把已配置的 skill 元数据和使用说明插入到 prompt 里。Skill 本质上是一份 Markdown 文档，写清楚”遇到 X 类任务时应该怎么做、用什么步骤、注意什么坑”。它不改变模型能力，但能让模型少走弯路、少试错，从而减少 token 消耗、提高成功率。**Skill 是内容层面的东西，由 harness 负责在合适的时机把它加载进 prompt。
MCP 是 harness 用来接外部工具的协议标准**。你之前看到 Codex prompt 里那个 tools 列表，其中有一类就是”用户通过 MCP 服务器配置的工具”（比如天气查询）。MCP 解决的问题是：以前每个 agent 产品要接入一个新工具（比如 Slack、Google Drive），都得自己写一套专属集成代码；有了 MCP 这个统一协议后，任何遵循 MCP 标准的服务端，都能被任何遵循 MCP 标准的 harness 直接接入，不用重复造轮子。**所以 MCP 本质上是 harness 和外部世界之间的”通用插座”，harness 负责把 MCP 服务器暴露出的工具，跟自己原生的工具（比如 shell、文件读写）一起打包，塞进模型能看到的 tools 列表里。**
## 串起来看一次完整流程

1. 你给 Claude Code / Codex 提一个需求
2. **Harness** 开始构造 prompt：加载相关的 **Skill** 说明、拼接项目上下文，把可用工具列表（自带工具 + 通过 **MCP** 接入的外部工具）一起打包
3. 把这份 prompt 发给 **模型** 做推理
4. 模型决定”该调用哪个工具”，返回一个工具调用请求
5. **Harness** 执行这个调用（可能是本地 shell，也可能是通过 MCP 转发给外部服务）
6. 结果拼回 prompt，循环回到第 3 步，直到模型给出最终答复

所以四者不是并列关系，而是**分层协作**：模型出思考，MCP 管连接，Skill 给指导，Harness 把这一切串成一个能真正跑起来的循环。

那harness在哪里能看到啊，是装在系统系统后台了吗？它怎么就能成了模型的壳管着该干什么了？另外，Codex和Claude Code有，那Chats有harness吗？

## Harness 装在哪儿

不是装在你的电脑系统后台，而是**跑在客户端软件里**。以 Codex CLI 为例，你在终端敲下 `codex` 命令启动的那个程序本身，就是 harness——它是一个用 Rust 写的本地程序，安装在你电脑上（前面搜到的仓库信息里就有具体的下载安装方式）。你每次输入指令、它读文件、跑命令，都是这个本地程序在做，模型本身其实”不在你电脑上”——模型跑在 OpenAI/Anthropic 的服务器上，harness 只是通过网络请求（前面提到的 Responses API）把 prompt 发过去，再把服务器返回的文字/工具调用请求接回来执行。
Claude Code 同理：你 `npm install` 装的那个命令行工具本身就是 harness，它是本地运行的程序，负责调度、执行工具，但推理这一步还是要连到 Anthropic 的服务器。
## Harness 怎么就能”管着”模型该干什么

这里有个关键点要澄清：**harness 并不是从代码层面”控制”或者”命令”模型**，模型没有被谁编程规定”你必须做 A 不能做 B”这种硬控制。真实的机制是：
1. Harness 在每次请求时，把”当前有哪些工具可用”这份清单塞进 prompt（就是前面讲的 tools 字段）
2. 模型看到这份清单后，**自主决定**要不要调用、调用哪个、传什么参数——这个决定完全是模型自己推理出来的，不是被硬编码指定的
3. Harness 收到模型的”我想调用 shell 工具”这个请求后，**代为执行**这个动作（因为模型本身没有手脚，它只能”说”想做什么，不能真的去操作文件系统）
4. 执行完把结果喂回去，模型再决定下一步

所以准确地说，harness 不是”管着模型该干什么”，而是**给模型提供了能力选项（工具），并且负责把模型的意图转化为真实动作**。真正的”决策权”始终在模型这边，harness 更像是模型的”手脚+翻译官”，而不是”上级”。
不过 harness 确实有一层真正的控制权——就是**安全边界**。比如 Codex 的 sandbox 权限设定（前面提到的 workspace_write.md 那类东西）决定了 shell 工具能不能改哪些文件夹、要不要弹窗问用户批准，这部分是 harness 硬性执行的，模型没法绕过。
## 那我们现在这个 Chat 有 harness 吗？

有，只是形态更”轻”。你现在正在用的 Claude.ai 聊天界面，背后也是一套 harness——它负责：
- 把你的消息、历史对话、我调用的各种工具（web_search、image_search、代码执行环境等）打包成 prompt 发给我
- 我”决定”要不要搜索、搜什么，这个决定权在我；但真正去发请求、拿到搜索结果、把结果喂回给我，是这套 chat harness 在做
- 管理这个对话的上下文（比如你看到的”long conversation reminder”，就是 harness 在超长对话时插入的提醒）

跟 Claude Code 比,主要区别是**工具集和使用场景不同**：Claude Code 那套 harness 侧重本地文件系统、shell、代码执行这类”改电脑”的工具；Claude.ai 这套 chat harness 侧重网页搜索、图片生成、文档创建这类更”消费级”的工具。但底层逻辑是一样的——都是”模型思考决策 + harness 负责执行和调度”这套分工。

## 我在电脑桌面版的Claude里用Code时，有让下载harness吗?

不需要你单独”下载 harness”，因为 Claude Desktop 桌面版本身就已经把这套东西打包好了。具体是这样：
**Claude Desktop 里内置了 Code 标签页**，桌面 app 分三块：Chat（普通对话，跟 claude.ai 网页版一样,不涉及文件访问）、Code（也就是 Claude Code）、Cowork。你下载安装 Claude Desktop 这一个应用，就已经把 Claude Code 这套 harness 一起装进去了，不需要再单独跑 npm 装 CLI 那一套。
也就是说，你在桌面版点开 Code 标签页开始用的时候，**那个负责调度文件读写、跑终端命令、管理会话的 harness 程序，其实就内嵌在 Claude Desktop 这个 app 本体里**，随着你安装桌面版就已经装好了,不会额外弹窗提示你”要不要下载 harness”这种东西——因为对用户来说这一层是被”藏”起来的，你只会看到界面上的功能（并排多会话、集成终端、可视化 diff 对比、实时预览这些），感受不到”harness”这个词本身。
值得一提的是：Claude Code 功能需要付费订阅（Pro/Max/Team/Enterprise），免费账号装了桌面版只能用 Chat 标签页那部分。另外如果你之前单独用命令行装过 Claude Code CLI（npm 那种方式），桌面版和 CLI 是**共享同一套配置文件**的，两边可以同时跑同一个项目，算是同一套 harness 的两种”外壳皮肤”（一个图形界面、一个纯命令行）。

## OK，那CLI的harness需要随时更新吧？npm install的时候是一个版本，过一段时间harness如果有更新，是不是需要upgrade一下，不然就一直在用老harness。harness经常更新吗？

对，你的理解完全正确——npm install 装的是那一刻的版本快照，harness 不会自动帮你升级，需要手动或配置自动检查更新。具体机制是这样：
## 更新机制

Claude Code 有**两个更新渠道**：默认走的是 `latest`（最新版，更新最快但偶尔可能带小问题），也可以切到 `stable`（通常比 latest 慢大约一周，会跳过有明显问题的版本，更稳）。渠道可以通过 `/config` 命令或者在 settings.json 里配置 `autoUpdatesChannel` 来设定。
**不同安装方式的更新行为不太一样：**
## 更新频繁吗
- 用**原生安装器**装的，会在启动时和运行过程中定期自动检查更新，更新包在后台下载，重启后生效——基本不用你操心
- 用 **Homebrew** 装的，默认不会自动更新，需要你手动跑 brew upgrade claude-code（或者 claude-code@latest，取决于你装的哪个 channel 对应的 cask）
- 用 **npm** 装的，同理也需要你自己手动跑更新命令去升级，不会自动帮你换新版本


从这些资料看，是**相当活跃的迭代节奏**——有专门区分”latest”和”stable”两条线，说明版本更新频率高到需要给用户一个”稳定版”选项来避免踩坑；另外前面聊 subagent 那个话题时你也看到了，短短几个月内（比如 5.6 版本发布前后）功能行为就发生过变化（像是 subagent 能不能指定模型这种细节都在变）。这说明 harness 层面的迭代速度并不慢，跟你订阅的底层模型版本更新节奏是两条独立的时间线——模型可能没变，但 harness 本身的功能、工具、bug 修复一直在推进。
## 老 harness 有什么影响

如果你一直不升级，直接后果就是：
- 拿不到新功能（比如新的工具类型、新的 subagent 机制）
- 可能错过一些性能优化（类似前面聊的 prompt caching 相关的改进）
- 有些 bug 修复也进不来

所以**建议**：如果是原生安装器装的，基本不用管，它自己会更新；如果是 npm/Homebrew 装的，可以隔一段时间手动跑一下更新命令，或者干脆养成”每次开始一个新项目前先升级一下”的习惯，成本很低。

如果是在VS code里使用的话，是不是VS code替你就更新了不用自己管？

大体是的——VS Code 插件会自动更新，**但有几个坑值得知道**：
## 正常情况下：是的，不用操心

**VS Code 插件本身内置了 CLI**，官方文档说得很清楚：插件本身就打包了 CLI，你不用单独去装 claude 这个命令。插件默认走 VS Code 自己的扩展更新机制——就跟你其他插件一样，VS Code 会自动检测新版本、自动更新，你确实基本不用手动管。
甚至反过来还有个细节：Claude Code 的 CLI 一旦检测到你在 VS Code 环境里，会自动帮你装上这个 VS Code 插件——说明这两者是绑定联动的，官方就是希望你不用操心版本管理这件事。
## 但两个实际的坑

**坑一：更新会”打架”。** 有个已知 bug（截至 2026年5月）：当 VS Code 插件处于激活状态时，它会把 claude.exe 这个文件锁住，导致独立运行的自动更新程序因为文件被占用而更新失败——而且失败是”静默”的，没有任何提示，用户会一直卡在旧版本上却毫无察觉。这个问题目前看是在 Windows 上出现的。
**坑二：想关自动更新，关不掉。** 反过来也有人报过另一个方向的 bug（2026年4月）：用户在插件搜索页面明确取消勾选了”Auto Update”，但过一阵子插件还是自动更新了——哪怕在 settings.json 里手动加了几条禁用更新的配置项，依然没能真正阻止自动更新发生。
## 实际建议

日常使用基本可以放心让它自动更新，这也是官方设计的初衷。但如果你：
- 在 Windows 上，且发现 Claude Code 表现”感觉怪怪的”或者一直没有新功能——可以手动查一下当前版本号，跟 GitHub 上的最新 release 对比一下，不排除是自动更新静默失败了
- 遇到某个新版本有已知 bug、想暂时锁定旧版本——目前看这个诉求在 VS Code 插件里不一定能可靠实现，如果真有强诉求，可能改用 CLI 端手动控制更新渠道（前面聊的 stable/latest channel）会更可控
第二个问题，如果模型越来越同质化，harness 会不会成为新的操作系统层？

这个问题问到点子上了——某种意义上，历史已经排练过这个剧本很多次了。
## 历史的镜子：硬件同质化时候，操作系统才成了真正的战场

PC 时代早期，Intel/AMD 处理器性能差距很大，硬件本身就是护城河。等硬件性能开始收敛（各家 CPU 性能差不多够用了），真正决定用户体验、生态归属的就变成了 Windows/Mac/Linux 这层”壳”——不是芯片跑得多快，而是你的软件生态、驱动兼容性、用户习惯全都绑定在操作系统上。云计算也是类似逻辑：底层算力（CPU/GPU/存储）越来越商品化,AWS/Azure/GCP 真正的护城河早就不是”谁的服务器更快”，而是上面那层 API、工具链、企业客户的迁移成本。
**模型如果真的同质化，harness 确实很可能复刻这个剧本。** 理由很直接：
## 但我不认为这个类比能完全成立——有一个关键变量不一样
1. **切换成本会集中转移到 harness 层**——如果 Claude、GPT、Gemini 底层能力差不多，用户/企业真正不想换的，是已经磨合好的工具链、配置好的 skill、连接好的 MCP 服务器、攒了几个月的项目上下文和 memory。这些东西换个模型可以带走（因为 harness 本身是模型无关的），但换 harness 就得重新配置一整套——**锁定效应从”选哪个大脑”转移到了”选哪套神经系统”**。
2. **企业采购逻辑会变**——决策会从”哪家模型更聪明”变成”哪家 harness 跟我们的 CI/CD、权限系统、审计需求配合得最顺”，这是纯粹的工程集成问题，跟模型智力关系不大。
3. **数据飞轮效应**——harness 天天在记录你怎么用工具、什么任务模式最有效、哪些 skill 最常被调用，这些使用数据反过来能优化 harness 本身（更聪明的工具编排、更精准的 context 管理），形成模型层面很难复制的复利。


PC 操作系统之所以能形成垄断级壁垒，是因为**软件生态是排他性的**（Windows 程序装不到 Mac 上）。但 harness 这层现在正在被刻意”去壁垒化”——**MCP 本身就是为了防止 harness 变成封闭操作系统而设计的开放协议**。Skill 文件基本就是 Markdown，理论上可以在不同 harness 之间迁移。这跟操作系统时代”软件不兼容锁死用户”完全是反着来的设计哲学。
所以更可能出现的局面不是”某一个 harness 一统天下”，而是**harness 层出现协议标准化，但产品体验层继续激烈竞争**——有点像浏览器之战：HTML/CSS/JS 是开放标准，谁都能读，但 Chrome 靠更快的渲染引擎、更好的开发者工具、更深的 Google 生态集成照样把 Firefox/Safari 甩开一大截。**开放协议之下，工程精细度和生态深度仍然能形成真实的差异化**——你之前问的 Codex vs Claude Code 那些设计差异（单线程 vs 更复杂的 subagent 编排、prompt caching 策略、沙箱设计）就是这个层面的较量。
## 我的判断

如果模型真的同质化了，护城河大概率会往两个方向分流，而不是单一集中到”harness 操作系统”：
- **往下沉到 harness 工程细节**——谁的 token 效率更高、上下文管理更聪明、安全沙箱更可靠，这些是你我今天聊的这些具体设计选择
- **往上浮到分发和信任层**——谁能让企业放心把敏感数据、生产环境权限交给它，谁能嵌入到用户已有的工作流里（比如已经绑定 VS Code、Slack 这些”母生态”），这可能比 harness 本身的技术优劣更决定胜负

换句话说：harness 会变得越来越重要,但更可能是”必要不充分条件”,真正的操作系统级垄断，大概率轮不到 harness 这层单独垄断——除非某家公司能把开放协议这层也重新封闭起来，这个我倒是会持续关注。

清楚明白！我刚才忘问的一个问题，你刚刚提了一嘴，某个模型的harness可以迁移到另一个模型吗？怎么迁移？还是在目前的harness或者目前模型里调用另一个模型？

两种情况都存在，而且是两个不同的事，值得分开说清楚：
## 情况一：同一个 harness，换个模型来用（这才是真正意义上的”迁移”）

这个是完全可行的，而且现在很多主流 harness 设计的时候就是奔着”模型无关”去的。原理很简单：**harness 跟模型之间是靠一套标准化 API 通信的**（Codex 那边是 Responses API，Claude 这边是 Messages API），只要某个模型服务提供商实现了同一套接口协议，harness 理论上不用改代码就能切过去。
前面聊 Codex 那篇官方博客里就提到过具体例子：Codex CLI 这个 harness，除了默认连 OpenAI 自家的模型，还支持：
- 通过 --oss 参数配合本地跑的 ollama 或 LM Studio，直接调用开源模型（比如 gpt-oss），完全本地运行,不连 OpenAI 服务器
- 配置文件里改一下 endpoint，就能切换到云厂商（比如 Azure）托管的 Responses API 服务

Claude Code 这边同理——它也能配置成走 Amazon Bedrock 或 Google Vertex AI 这些不同的后端（前面搜到的资料里那个 `CLAUDE_CODE_USE_BEDROCK` 环境变量配置就是干这个的）,本质上就是把”该往哪个服务器发请求”这个参数换掉。
**更极致的例子**是那些天生就”harness-agnostic”（跟具体模型/产品解耦）的开源框架，前面搜到的资料里提过一个叫 Open Harness 的项目，它的定位就是”不管你想用 Claude Code、Codex 还是 OpenCode 的能力，都能插进来用，不用为了换模型重写整个 agent 逻辑”——本质上就是把 harness 这层再抽象出一层通用适配层。
**这种”迁移”具体怎么操作**，通常就是改配置文件（换 API endpoint、换 provider 字段），harness 里所有那套 prompt 构造、工具调度、上下文管理逻辑完全不变，只是最后那一步”发请求给谁”换了个目标。
## 情况二：不换 harness 主体，只是”顺手调用”另一个模型

这是完全不同的另一件事——**不是迁移，而是在同一次任务里，让当前模型把另一个模型当工具使唤**。你之前问的 subagent 其实有点接近这个概念（一个 harness 主循环里，可以配置不同 subagent 用不同模型/不同推理强度），但那还是同一个 harness 家族内部的事。
更纯粹的”调用另一个模型”的例子，是把另一个模型包装成 MCP 工具或者普通 function call 暴露给当前模型——比如让 Claude 在处理任务时，判断某个子任务更适合用一个专门做图像生成的模型，就发起一次 API 调用，把结果当工具返回结果吃进来，跟调用其他任何外部服务没有本质区别。这种情况下，主导权和主循环始终留在原来这个模型/harness 手里，被调用的模型只是”打工的”。
## 一句话总结

**同一个 harness 换模型，是配置层面的迁移**（harness 代码不用大改，因为它本来就是围绕标准化 API 设计的）；**模型调用另一个模型，是工具调用**（本质上跟调用 shell、调用搜索引擎是一回事，只是这次”工具”恰好也是个 AI）。两者可以同时发生——比如你现在用的 harness 主模型是 A，但它内部某个 subagent 配置成用模型 B 去跑，这时候”迁移”和”调用”这两件事其实是叠在一起的。

这个问题跟你之前问的”harness 会不会变成操作系统”是一个逻辑家族的延伸，答案我认为也是类似的分叉结构——不是非黑即白，而是**看这个垂直产品的护城河到底建在哪一层**。
## 先拆解”垂直产品”到底在卖什么

一个垂直 AI 产品的价值,通常来自三层叠加：
1. **领域知识/工作流封装**（“怎么做税务合规审查”这件事该分几步、注意哪些坑）
2. **专有数据或数据管道**（行业专属的数据集、跟企业系统的深度集成、历史案例库）
3. **分发和信任**（客户已经买单、已经把敏感数据交给你、已经把它嵌进日常流程）

**Skill 这个机制，本质上只能把第1层”平民化”**——把”怎么做这件事”的流程知识写成 Markdown 文档，喂给一个通用 agent。这一层一旦能被 Skill 轻松复制，确实会被通用 agent 蚕食。
## 会消失的那类垂直产品

**如果一个垂直产品的全部价值就是”把领域最佳实践打包成一套流程”**，而没有专有数据、没有难以复制的系统集成，那这类产品风险确实很大。举例：单纯做”AI 写周报”“AI 生成会议纪要模板”这类产品，本质上就是一份可以写成 Skill 文件的流程知识，一旦通用 agent 的 Skill 生态成熟，这类产品的独立存在理由会被大幅削弱——用户为什么要单独订阅一个产品，而不是直接在自己已经在用的 Claude/ChatGPT 里挂一个免费或者几块钱的 Skill？
## 更可能存活、甚至转型成”能力供应商”的那类

如果垂直产品的护城河建立在第2、3层，情况就完全不同了：
## 一个更微妙的中间地带：Skill 能抄走”流程”，抄不走”信任”
- **专有数据/专有判断的产品**——比如一个做医疗影像诊断的垂直 AI，它的价值不在”怎么问诊”这套流程（这确实能写成 Skill），而在于它有海量标注过的影像数据训练出的专有判断模型、有 FDA 认证、有跟医院系统的深度集成。这类产品的核心价值恰恰**没法被一份 Skill 文档复制**，因为 Skill 只能传递”怎么做”的流程知识，传不了训练数据和专有模型能力。
- **这类产品最合理的转型路径,正是你说的”能力供应商”**——把自己封装成一个 MCP 服务器或者工具接口，让通用 agent 可以调用。这其实是把自己从”一个独立的、需要用户单独打开的 app”，变成”通用 agent 生态里的一个专业节点”。历史上这个模式并不新鲜：想想云计算时代,很多曾经想自己做”全家桶”应用的公司，最后活得最好的反而是专注做好一个 API/服务，接入别人的生态（Stripe 之于电商网站,就是”支付能力供应商”而不是自己做电商平台）。


即便某个垂直产品的核心真的只是流程知识，还有一层东西 Skill 抄不走——**责任归属和信任背书**。比如一个专业税务合规工具,哪怕它的操作流程完全可以写成一份 Skill，企业客户依然可能愿意为”出了问题谁负责、有没有专业认证、有没有保险背书”这件事继续付费。这类似于”知识可以开源，但认证和担保没法开源”——这一点在强监管行业（医疗、法律、金融）里会体现得特别明显，垂直产品在这些领域即便被 Skill 化侵蚀了流程层，认证/合规/责任层依然能撑起独立存在的理由。
## 我的判断

我认为最终格局会是**三分天下**，而不是单一结局：
- **纯流程型垂直产品**：大概率被通用 agent + Skill 生态吸收，独立存在的理由会消失
- **数据/模型驱动型垂直产品**：转型成”能力供应商”，通过 MCP 之类的协议把自己接入通用 agent 生态，靠专有数据和判断力收费，而不是靠”一个独立 app”收费
- **强监管/高信任成本型垂直产品**：即便流程被复制，认证和责任归属这层价值依然独立存在，可能是三类里”消失”风险最低的一类

你之前那句”模型同质化会不会让 harness 变成操作系统”和这个问题其实是同一枚硬币的两面——**通用 agent 生态越成熟，护城河就越会从”谁把知识包装得更好”，转移到”谁掌握着别人复制不走的专有资产”**，垂直产品能不能活下来，最终考验的不是它有没有做出一个好用的产品，而是它手里握着的东西,到底是”可以被写成一份 Skill 文档的知识”，还是”写不进任何文档里的东西”。

下一个问题“哪些价值可以被通用 Agent 吸收，哪些必须依赖行业数据、责任体系和真实服务网络？”你基本上在第五题里回答了， 那就再看第七题：对普通人而言，未来最值得积累的是 Prompt、Skill、工作流，还是个人数据与判断力？

这个问题其实是把第五题那套”可复制 vs 不可复制”的框架，直接套到个人身上——逻辑完全一致，只是把”垂直产品”换成了”你自己”。
## 先套用同一个框架看每一项的”可复制性”

**Prompt（提示词）**——最容易被复制、贬值最快的一层。一个好 prompt 本质上就是一段文字，能被截图、能被转发、能被抄进别人的收藏夹。前面聊过 Skill 机制之后，很多曾经值钱的”prompt 技巧”直接被沉淀成标准化的 Skill 文件，普适性越强的 prompt,越容易被行业吸收成默认配置。**单纯背下来一堆”好 prompt”，护城河几乎为零**。
**Skill（技能/工作流封装）**——比单个 prompt 更耐用一点，因为它封装了一整套多步骤流程和判断逻辑，写起来更费功夫。但本质上还是”可以被写成文档、被复制粘贴”的东西——你今天摸索出来的一套 skill，理论上明天就能被别人拆开学走。它更像是”暂时领先”，而不是”结构性壁垒”。
**工作流（更系统性的流程编排）**——比单个 skill 更进一步，涉及把多个工具、多个 skill、多个 agent 串起来解决一个复杂问题。这一层已经开始有点”信息不对称”的价值了——因为好的工作流设计需要你对自己的具体场景、具体痛点有深刻理解，不是随便抄一份模板就能用，但它依然是”可以被文档化、被教会给别人”的东西，本质上跟 Skill 是同一个量级。
**个人数据与判断力——这是唯一一层真正抄不走的东西**，原因跟第五题里”专有数据/责任体系”那部分逻辑完全一样：
## 我的判断

前面搜到的资料里提过 agenttrace、AgentOps 这类工具——专门做”审计 agent 会话轨迹、找到 token 花在哪、哪一步工具调用失败了”。这其实是一个正在快速冒出来的独立赛道：**当 agent 自主跑几十步之后才出错，人怎么反过来定位是 prompt 的问题、工具的问题、还是模型本身推理错了**。这块跟你之前问的”harness 会不会变成操作系统”也有关——可观测性工具很可能是下一层要被标准化的东西（类似云计算时代的监控告警生态）。

## 为什么不能简单”塞进 context window”了事

最直观的做法是把整个历史对话原封不动塞进 prompt——这也是最早期的做法。但研究发现两个硬伤：
**“迷失在中间”问题**——上下文越长，模型对中间部分信息的检索准确率越差,即便是专门为长上下文设计的模型也逃不掉,在超长上下文下，具体事实的检索准确率会明显下滑。**这跟人的记忆机制其实很像**——你记得开头和最近发生的事，中间那段模糊成一团。
**推理速度和成本双输**——上下文越长,处理时间越长，首字延迟基本随长度线性增长,对需要实时交互的 agent 来说体验会明显变差。而且前面聊过的 prompt caching，长上下文一旦频繁变动，缓存效率也会打折扣。
所以行业共识变成了：**把 context window 当”内存条”（RAM），把持久记忆当”硬盘”（SSD）——你不会想把整块硬盘塞进内存里，而是按需加载。**
## 现在主流的三层记忆架构

目前生产环境的共识大致收敛成一个三层结构：
1. **会话内工作记忆（In-context working memory）**——当前这一轮对话的原始消息缓冲、工具调用记录、活跃状态。这层是临时的，会话结束就清空
2. **会话级压缩记忆（Session-scoped compressed memory）**——把当前会话总结或提炼成关键事实，按需读取（这其实就是前面聊 Codex compaction 机制时提到的那套逻辑,是同一件事的两种叫法）
3. **长期持久存储（Long-term persistent store）**——跨会话的知识、用户偏好、学会的工作流,存在向量数据库+知识图谱的混合结构里

一个具体的参考实现是把”核心记忆”（默认2-4KB，永远挂在上下文里,相当于 RAM）跟”档案记忆”（外部向量存储,没有大小上限,靠语义相似度检索,相当于硬盘）分开管理。
## 几个真正棘手、还没解决的难题

这几个问题我觉得对你做 Mimo/Mivo 这类产品会特别有启发：
**记忆冲突检测**——新事实进来时，要跟已有记忆比对，判断是”合并、更新，还是标记为冲突待解决”。这是被反复提到的核心技术难点。
**跨会话身份识别**——记忆机制通常假设有一个稳定的 user_id，但匿名会话、多设备用户、混合登录方式都会打破这个假设。**判断两次交互是不是同一个人，本身就是记忆层一个尚未解决的身份问题**——这对 Mimo 这种多人家庭群聊场景应该会特别相关：谁在什么时候说了什么，身份要怎么可靠地绑定和区分。
**记忆过时（staleness）**——一条被频繁调用的记忆，比如”用户在某公司工作”，在他换工作那一刻就从”准确”变成”自信地错误”。低相关性记忆可以靠自然衰减处理掉，但高相关性记忆一旦过时,是个更难的开放问题——这个坑我们这次对话本身就有真实案例：如果你哪天真的换了工作,而我的记忆系统没跟上，我下次可能还会一本正经地用旧信息回你。
**隐私和同意机制**——谁能看这些存储的记忆、保留多久、用户怎么删除——目前这些还都是应用层各自决定的事,行业里没有统一规范。
## 一个新方向：异步整理记忆

值得一提的是，行业里已经有”异步整理记忆”这类机制出现——在会话之间，用一个独立的后台流程去重新组织、提炼 agent 积累下来的记忆，跟人睡觉时大脑做记忆巩固的机制类似。这跟你之前问的”harness 记不记事”这个问题的下一步演化方向是一致的：**从”被动存一堆原始记录”进化到”主动整理、提炼、去芜存菁”**。

这个话题跟你之前那句”等成本降下来后模型质量的作用会更大”其实也呼应得上——**当模型能力逐渐商品化，记忆架构设计得好不好，很可能会变成决定一个 AI 产品能不能真正”懂你”的关键变量**，这也是为什么你做 Mimo 这类需要长期记住”这个家庭”的产品时，记忆架构的设计决策，分量可能比选用哪个底层模型还重。

再讲讲第三个可观测性和调试

这个话题跟前面聊的记忆机制,其实是一体两面——**记忆解决”agent 记不记得”,可观测性解决”agent 做错了，你怎么知道哪一步出的错”**。而且这个赛道现在已经从”简单打日志”演化成一个相当成熟的产品品类了。
## 为什么这件事跟传统软件调试完全不是一回事

传统软件监控告诉你的是”这个请求成功了没有”。但 AI agent 的可观测性要回答的是更深一层的问题——agent 做出了什么决策、为什么这么决策，而不只是接口有没有报错。这个差异之所以关键，是因为 基于 LLM 的 agent 本质上是非确定性的：同一个 prompt 可能返回不同的输出，而且很多失败根本不会抛出错误——它就是安安静静地给了个错误答案。这就是为什么”可观测性”这个词，而不是”监控”，成了这个领域的主流叫法——它得抓住”意图和过程”，不只是输入输出。
## 三大支柱

行业目前基本收敛成三层能力：
**追踪（Tracing）**——捕捉一次运行的完整执行路径，包括每一次工具调用、每一次检索步骤，以及 agent 走过的每一步中间推理。一条追踪记录通常包含时间戳、输入输出、token 数量、每一步的成本，再加上你自己附加的元数据（用户ID、会话、prompt 版本）。具体到内容层面，你想抓到的是完整的推理轨迹：考虑过哪些工具、实际调用了哪个、传了什么参数、返回了什么结果、每一步花了多少 token、每一跳的延迟是多少——全部拼接成一条可以回放的层级化追踪链。
**评估（Evaluation）**——光有轨迹还不够，还得判断”这个输出到底好不好”。这一层通常靠专门的”评分器”（scorer）自动打分,比如检测幻觉、检测总结质量、检测输出格式是否合规。
**成本/延迟监控**——这个你应该最有共鸣，因为前面聊过 token 经济账对你选模型的影响。这一层就是把每一步的 token 消耗、每一步的成本、每一跳的延迟都记录下来，方便事后复盘”钱到底花在哪一步”。
## 一个关键的行业级信号：这块正在标准化

跟你之前问的”harness 会不会变成新的操作系统层”高度相关的一个进展是：**可观测性这块最重要的进展不是某个产品，而是一份规范**——OpenTelemetry 的 GenAI 语义约定，定义了一套统一的 AI 遥测数据词汇表——一组标准化的 gen_ai.* 字段，任何埋点工具库都能按这套标准输出，任何后端平台都能按这套标准接收。这跟 MCP 走的是同一条路——**先有协议标准化,再有产品层竞争**，验证了你之前提出的那个判断：模型同质化之后，真正会被重新”抢标准”的，不只是 harness 本身，连”怎么观测 harness”这件事本身也在标准化。
## 目前市场格局

目前主流平台包括 Opik、Langfuse、LangSmith、Arize Phoenix、Braintrust、Datadog LLM Observability、MLflow、Galileo 等，其中开源生态最完整的是 Opik（Apache 2.0 协议）、Langfuse（MIT 协议）、Arize Phoenix 和 MLflow（都是 Apache 系或类似开源协议）。**这里有个耐人寻味的细分**：有分析把整个可观测栈拆成三层——推理执行层（vLLM、各家 provider API，负责吞吐和缓存）、编排层（agent 框架负责状态机、记忆持久化、路由逻辑）、遥测层（负责在生成第一个 token 之前，就捕捉到”为什么做出这个决策”）。这跟你之前问的”harness 是不是新操作系统层”是同一个分层逻辑——可观测性工具现在也在往”该在协议的哪一层插桩”这个问题上分化。
## 一个还没解决的痛点：多智能体场景下的责任追溯

跟你之前聊 subagent 这个话题直接相关的一点是：AI agent 每天在生产环境做出成千上万个决策——在多个子 agent 之间路由、调用工具、检索上下文、串联推理步骤，一旦其中一个决策出错，这个错误会级联到后续每一步。这也是为什么 有平台专门做”层级化追踪”——保留父子 agent 调用之间的层级关系,而不是把每次调用记成一条条互不相关的扁平日志——这样出错时才能顺藤摸瓜，追到究竟是哪个子 agent 在哪一步开始跑偏的。
这跟你之前问的”Codex 有没有 subagent”那个话题也接上了——**subagent 越普及，“出错之后怎么定位是哪个子任务的锅”这个可观测性问题就越突出**,这也是为什么这个赛道今年增长这么猛：agent 自主性越强、并行度越高，人类想在事后搞清楚”到底哪一步错了”就越离不开这套基础设施,几乎是跟 agent 能力发展成对增长的一个配套产业。

第四个agent之间怎么互相说话你简单讲讲

简单说，这块要解决的问题是：**MCP 让 agent 能调用工具，但没解决”两个独立的 agent 该怎么互相对话、互相委托任务”这件事**。这个赛道现在主流标准叫 **A2A（Agent2Agent）**，2025年4月由 Google 发布，2025年6月转交给 Linux 基金会做厂商中立治理,发布时就有超过50家技术伙伴参与,包括 Atlassian、Salesforce、PayPal 这类企业级玩家。
## A2A 解决什么问题

一句话概括：MCP 关注的是”agent 到工具”这条关系,而 A2A 把这个思路推广到了”agent 到 agent”的协作——定义了一个 agent 怎么发现另一个 agent、怎么协商权限、怎么交换结构化消息、怎么管理跨越较长时间的任务，靠的是一整套共享的约定。用大白话讲就是A2A 想解决的现状是——各个 agent 都很擅长自己的本职工作，但彼此之间是孤立的:一个物流 agent 没法直接问库存 agent 问题，一个客服 agent 没法在对话中途把工作交接给退货 agent。**这跟你之前问的 subagent 不是一回事**——subagent 是同一个 harness 内部、同一个”家族”里的协作；A2A 要解决的是**跨厂商、跨框架、彼此互不了解内部实现的 agent 之间怎么协作**。
## 具体怎么运作

核心机制是”**Agent Card**”——一份描述 agent 能力和访问方式的元数据文档,用 HTTP 和 JSON 这类通用网络技术来交换。可以理解成”agent 的名片”：一个 agent 想找别的 agent 合作时，先看对方的 Agent Card，了解它能干什么、怎么联系它，然后由发起方 agent 把任务打包发给对方,对方 agent 干活、收集信息，再把结果传回来——是一种客户端-远程端的双向结构化通信。底层用的都是成熟的网络技术：建立在 SSE（服务器推送事件）、HTTP(S)、JSON-RPC 这些既有标准之上，鉴权用 OAuth 2.0，token 传递用 JWT——没有另起炉灶造新协议，而是把 agent 协作这件事”缝”进了已经很成熟的网络基础设施里。
## 跟 MCP 的分工

行业里现在的最佳实践基本是两者搭配着用：MCP 负责工具接入（垂直方向——给一个 agent 装上多个工具),A2A 负责多 agent 协调（水平方向——组建一个由多个专业化 agent 组成的团队）。你可以把 MCP 想成”给 agent 配手脚”，A2A 想成”让多个 agent 组队干活”。
## 还没解决的问题

跟你之前问 harness 记忆时提到的”未解决难题”类似,A2A 目前也有明显的空白地带：A2A 本质上是”委托导向”的——它回答的是”哪个 agent 能处理这个任务”，虽然2026年5月发布的1.0.1版本引入了扩展机制,但官方给出的四个示例扩展（安全护照、时间戳、可追溯性、Agent</parameter> 网关协议）里，没有一个是专门解决”治理”问题的——也就是说,谁该为多 agent 协作链条里的最终决策负责,这块目前还是空白。这跟你之前问的可观测性话题也接得上——**agent 之间协作得越复杂，出了问题该追溯到哪个环节、由谁负责，就越是一个亟待补齐的短板**。
一个值得留意的信号：这个赛道其实不止 A2A 一家，IBM 也推了一个更轻量的 ACP（Agent Communication Protocol），走纯 REST 消息、不需要 SDK，定位是更轻便的替代方案——说明这块”协议之争”目前还处在多个标准并存、还没完全统一的阶段,跟 MCP 已经被行业普遍采纳的局面不太一样，算是你之前问的”行业标准之争”里,还在”打上半场”的一块。

最后一个harness的安全边界问题

这块跟前面聊的可观测性正好是一体两面——**可观测性回答”出了事之后怎么定位”，安全边界回答”怎么在出事之前就把损失框住”**。而且这几个月这个领域刚好经历了一次认知上的重大转变，值得细讲。
## 一个关键的认知转折：安全问题”下沉”到了 harness 层

早期的护栏产品只是检查单次模型调用的输入输出——能过滤有害内容、能挡掉一些明显违规的东西。但这套思路现在被认为不够用了。行业里现在的说法是：模型层面的护栏包住的是”一次模型调用”，而 agent 层面的守卫包住的是”整个循环”——两者都需要，但真正能挡住那些真实发生过的重大安全事件（比如 EchoLeak、Claude Code 那次 CVE-2025-59536 漏洞）的,只有后者。**更惊人的是一个统计——在 OWASP 2026 年针对 agentic AI 安全定义的十大风险类别里，有八项本质上是 harness 层面的问题，不是模型输出层面的问题。这跟前面搜到的事件分布数据完全吻合——主要的威胁类别已经从”模型说错话”下沉到了”harness 怎么执行动作”这个层面。这也回应了我们前面聊模型同质化和 harness 重要性时的判断：**harness 不只是决定用户体验和成本效率，它现在还是安全责任真正落地的地方**。
## 具体怎么设计权限系统

有个说法我觉得特别精辟：**权限是基础设施问题，不是提示词问题**——意思是，你不能靠在 prompt 里跟模型说”请不要删除重要文件”来保证安全，这种”口头约定”随时可能被绕过（不管是模型自己犯错还是被 prompt injection 攻击）。真正可靠的做法是在 harness 代码层面**硬性拦截**，模型说了不算。
一套典型的权限判定优先级大致是：先看有没有明确的拒绝规则，再看要不要询问用户确认，然后过一层专门的前置钩子做二次校验，再看有没有明确的允许规则，最后才轮到默认模式和回调逻辑——层层叠加，钩子的优先级比”模式”本身还高，被标记为”受保护”的路径,哪怕在”跳过所有确认”的模式下也依然受保护。还有一句我觉得很实用的话：如果用户对每次操作请求的批准率高达93%，说明这个确认对话框本身已经沦为一种”记录用的仪表盘”，而不是真正在起安全作用了——这时候更合理的做法是把常规操作直接放行、只在真正的例外情况上升级请求人工确认，一旦出现连续被拒绝的情况就自动停下整个循环。这其实点出了一个很微妙的设计难题:**批准太频繁,用户会疲劳性地无脑点”同意”,反而起不到安全作用**。
## 隔离环境：不只是”能不能删文件”这么简单

现在的沙箱隔离技术已经分出了明显的层级，跟隔离强度直接挂钩：标准容器共享内核，隔离性最弱，只适合跑可信代码；gVisor 是在用户空间拦截系统调用，不需要完整虚拟机；microVM（比如 Firecracker、Kata Containers）给每个工作负载配一个独立内核，隔离性最强。这不是学术讨论——因为现在 AI agent 每天在生成数十亿行代码，运行这些代码必须要有专门为 agent 场景设计的执行沙箱,不能是普通开发环境那套裸奔的做法。
有个具体攻击场景值得留意，也解释了为什么这事越来越紧迫：开发者现在经常让 agent 自己上网搜索、自己判断该用哪个第三方代码库/依赖包，而不是自己去挑——这个环节恰恰是最容易被恶意利用的漏洞点,一旦 agent 被诱导装了个带毒的包，攻击面就从”agent 说错话”直接升级成了”你的设备被真实攻破”。
## 这行现在的共识：安全是”运营出来的”，不是”问出来的”

这个领域正在收敛到一个简单但很有力的共识:安全是一件运营层面的事——你没法靠”好好跟模型商量”来获得安全性,而要靠约束运行环境、在运行时强制执行策略、持续观测行为、并且提前准备好出问题之后的恢复路径,这四件事组合起来才行,单独任何一样都不够。没有哪一个工具能端到端地解决 agent 安全执行的问题——赢家策略是**多层组合**：策略引擎+沙箱+监控+故障恢复,缺一不可。

回头看我们聊过的整个 harness 话题——从”是什么”到”怎么运作”到”性能优化”再到今天这几个补充话题（记忆、可观测性、agent 间通信、安全边界），其实勾勒出的是同一个越来越清晰的行业图景：**模型能力越来越商品化,真正决定一个 AI 产品能不能被信任、能不能规模化落地的,越来越是这一层看不见的工程细节**。这跟你之前那句”等成本降下来后模型质量的作用会更大”其实构成了一个有意思的张力——模型质量重要,但能不能让企业放心把生产权限交出去,靠的完全是 harness 这层的成熟度。

# Agent Harness 知识体系总结

## 一、Harness 是什么

**定义**：Harness（智能体外壳）是包裹在大语言模型外面的工程系统，负责把模型的"裸能力"转化成能完成真实任务的智能体行为。

**类比**：
- 模型 = 大脑（负责思考、推理、决策）
- Harness = 身体和神经系统（负责执行、管理循环）
- Skill = 说明书（告诉模型怎么把特定任务做得更好）
- MCP = 通用插座（让 harness 接入外部工具和数据源）

**Harness 具体做什么**：
1. 构造 prompt（拼接系统指令、项目上下文、工具列表）
2. 把 prompt 发给模型做推理
3. 解析模型返回的工具调用请求
4. 真正执行这个动作（模型自己没有"手脚"）
5. 把结果拼回 prompt，循环往复，直到任务完成

**关键澄清**：Harness 不是"控制"模型该做什么，决策权始终在模型——harness 只是提供工具选项、代为执行动作、并守住安全边界（沙箱权限这类硬性约束模型无法绕过）。

---

## 二、OpenAI Codex Harness 的具体运作（来自官方博客）

- 每轮对话（turn）：用户输入 → 模型推理 → 请求工具调用 → 执行 → 结果拼回 prompt → 循环，直到模型给出面向用户的回复
- **关键设计**：新 prompt 永远是旧 prompt 的"精确前缀"追加，不是重新生成
- Prompt 构成：instructions（模型专属指令）+ tools（工具列表，含 MCP 工具）+ input（沙箱环境说明、开发者指令、AGENTS.md 内容、运行环境信息、用户消息）

### Prompt Caching（性能优化核心）
- 问题：每轮累加内容，计算量本该是平方级增长
- 解法：只要新请求开头与上次完全一致（精确前缀匹配），可复用缓存计算，把平方级拉回线性级
- **会打破缓存、导致成本上升的操作**：
- 对话中途切换模型（如 5.5 → 5.6，因为每个模型有专属 instructions）
- 中途改变工具列表
- 改变沙箱配置或工作目录
- 影响范围：只是切换那一次请求要按全价重算，不是持续性浪费；之后又会重新建立新的缓存前缀

### Compaction（上下文管理）
- 对话变长逼近上下文窗口上限时，自动用更小但代表性的内容列表替换冗长历史，释放空间

## 三、Claude Code Harness 的设计哲学（对比 Codex）

- 内部代号 "nO"，走**单线程主循环**，配合规范化工具和规划实现可控自主性——刻意反对当下流行的复杂多智能体编排方向
- 关键组件：
- h2A 队列：支持实时"插话"/引导
- TODO 式任务规划
- **受控 subagent**：每个子智能体有独立上下文窗口、独立系统提示和工具权限，专门处理会"淹没"主对话的高信息量操作，只把摘要结果返回主循环
- 上下文管理：effort 级别调节（simple 任务用 low 省 token）、SDK session 机制续接对话、MCP 工具 schema 按需加载

**与 Codex 的核心差异**：Codex 靠"越堆越长 + prompt caching"维持效率；Claude Code 更强调"该分流就分流"（用 subagent 隔离高信息量任务），从源头控制主循环膨胀。

---

## 四、Codex 的 Subagent（今年3月才上线，比 Claude Code 晚）

- 默认预置 explorer（探索型）、worker（工作型）、default 三种，也可在 `~/.codex/agents/` 下自定义 TOML 文件
- 触发方式：交互式委派、AGENTS.md/skill 指令自动触发，`/agent` 命令查看/切换
- 代价：并行 subagent 消耗的 token 比单智能体更多——本质上和"切换模型多费 token"是同一类权衡：能省时间但账单会体现

---

## 五、Harness 部署在哪里

- **不是装在系统后台**，而是本地运行的客户端程序（如 Codex CLI 是本地 Rust 程序，Claude Code 是本地命令行工具）
- 模型本身跑在云端服务器，harness 通过 API（Responses API / Messages API）发请求、接结果
- **Claude Desktop 桌面版**：内置 Code 标签页，安装桌面版即自带这套 harness，不需要单独装 CLI；CLI 与桌面版共享配置文件
- **VS Code 插件**：内置 CLI，跟随 VS Code 扩展机制自动更新，但存在已知 bug（文件锁导致静默更新失败；"关闭自动更新"选项有时不生效)
- **当前这个 Claude.ai Chat 界面**：同样有一套 harness，负责调度 web_search、图片生成等工具，管理上下文（如长对话提醒）

### CLI 更新机制
- 两个渠道：`latest`（最新但可能不稳）、`stable`（滞后约一周,更稳）
- 原生安装器：自动检测更新，后台下载，重启生效
- Homebrew / npm 安装：需要手动升级，不会自动更新

## 六、模型同质化 → Harness 是否会成为新的"操作系统层"？

**支持类比的理由**：
- 硬件/云计算历史都验证过"底层商品化后，护城河转移到上层"的规律
- 切换模型容易（迁移友好），切换 harness 配置成本高（工具链、skill、MCP 连接、记忆积累都要重新搭建）
- 使用数据能反哺 harness 优化，形成模型层难复制的复利

**反对完全类比的理由**：
- PC 操作系统靠"软件生态排他性"形成垄断；但 MCP 恰恰是为了防止 harness 变成封闭操作系统而设计的**开放协议**
- 更可能的走向类似"浏览器之战"：协议开放，但产品体验层（token 效率、上下文管理、安全设计）继续激烈竞争

**判断**：护城河更可能分流成两块——① harness 工程细节（token 效率、上下文管理、安全沙箱）；② 分发和信任层（谁能让企业放心交出生产权限、谁已嵌入用户的工作流生态）。单一垄断的可能性不高，除非有人把开放协议这层重新封闭。

---

## 七、模型迁移 vs 模型调用：两种不同的"跨模型"方式

**情况一：同一个 harness 换模型（真正的迁移）**
- 因为 harness 与模型之间靠标准化 API 通信，理论上换个 provider/endpoint 配置即可
- 例：Codex CLI 可配置走本地 ollama/LM Studio 跑开源模型，或切换 Azure 托管服务；Claude Code 可配置走 Amazon Bedrock / Google Vertex AI
- 操作方式：改配置文件（API endpoint、provider 字段），harness 的 prompt 构造、工具调度逻辑不变

**情况二：模型调用另一个模型（工具调用，非迁移）**
- 当前模型把另一个模型包装成 MCP 工具或 function call 来使唤，主导权仍在原模型/harness
- 与 subagent 概念部分重叠，但 subagent 通常仍是同一 harness 家族内部的事

---

## 八、Codex 开源 Harness：放弃壁垒 or 争夺标准？

**两者并不矛盾，往往是同一动作的两面**：
- 开源的只是"壳"（编排层），真正商业化的"脑"（GPT 模型本身）依然闭源收费——是"开源边缘、封闭核心"的经典打法（类比 Google 开源 Android、闭源 Play Store）
- 开发者一旦习惯 Codex 的 AGENTS.md、skill 格式、CLI 交互模式，即便未来协议私有化扩展，迁移成本已客观存在
- 与 MCP 的类比：MCP 本是 Anthropic 提出、后被全行业采纳成事实标准——说明"标准"之争的赢家未必是提出者，而是谁能让更大规模开发者的日常工作流建立在自己的实现上
- Anthropic 押注的是相反路径：不追求生态标准普及度，靠工程质量（单线程主循环、subagent 隔离）建立体验层壁垒

**结论**：这是"用不值钱的开源，换值钱的心智占有率"的一步棋，"放弃壁垒"与"争夺标准"是同一策略的两面。

## 九、Codex vs Claude Code 现状战况（基于2026年中数据）

- **代码质量/满意度**：Claude Code 明显占优（67% 开发者认为其代码更干净；长上下文管理、UI 任务、插件生态评价更高；GitHub 提交占比持续攀升）
- **用户规模/日常顺手度**：Codex 追得很猛（周活破500万，桌面版上线后6倍增长）
- **有趣的反差**：65% 开发者认为 Codex 代码质量不如 Claude Code，但日常仍偏爱使用 Codex——差距几乎全来自速率限制和 token 定价，不是能力差距
- **定价**：Codex 目前性价比优势明显（同样$20，ChatGPT Plus 提供更充裕的每日运行时长）
- **市场大局**：并非零和——Copilot 靠企业捆绑占据最大市场份额，Cursor 与 Claude Code 在职场使用率上打平，Codex 后来居上，开发者普遍"混用"（Claude Code 做规划、Codex 做执行）

**个人判断（仅供参考）**：短期是需求分层、非替代关系；中长期若必须押注，品质路线（Anthropic）更具潜力，但前提是解决定价/额度短板；纯规模路线（OpenAI）胜负手在于能否把开发者习惯焊死。

## 十、Claude Code 优势的来源拆解：模型 or 产品设计？

- **纯跑分层面**：模型是决定性因素（同一个模型无关的 harness 如 OpenCode，接 Opus 出 Claude Code 分数，接 GPT 出 Codex 分数）
- **但真实差异化中，harness/产品设计分量不轻**：
- 长上下文管理体验、插件生态、UI 任务表现——这些是产品工程打磨出来的
- 用户"愿不愿意用"很大程度取决于额度设计、定价策略（纯商业决策，比模型能力影响力更大）
- **分层结论**：代码质量/复杂推理能力→主要归功模型；顺手度/长任务不跑偏/生态丰富度→主要归功 harness 设计；长期留存和满意度→产品商业决策影响力可能最大

## 十一、垂直产品的命运：被通用 Agent 吸收 or 转型为能力供应商？

垂直产品价值的三层拆解：
1. 领域知识/工作流封装（**能被 Skill 复制**）
2. 专有数据/系统集成（**Skill 复制不走**）
3. 分发和信任（认证、责任归属、客户粘性）

**三分天下的预判**：
- 纯流程型垂直产品：大概率被通用 agent + Skill 生态吸收
- 数据/模型驱动型垂直产品：转型为"能力供应商"，通过 MCP 等协议接入通用 agent 生态
- 强监管/高信任成本型垂直产品（医疗、法律、金融）：即便流程被复制，认证和责任归属这层价值依然独立存在

---

## 十二、个人层面：最值得积累 Prompt、Skill、工作流，还是数据与判断力？

按"可复制性"排序（复用第十一点的框架）：
- **Prompt**：最易复制、贬值最快，几乎无护城河
- **Skill**：比单个 prompt 耐用，但仍可被文档化、被学走——"暂时领先"而非"结构性壁垒"
- **工作流**：与 Skill 同量级，涉及信息不对称但依然可教
- **个人数据与判断力**：唯一抄不走的部分——
- 数据：独一无二的项目历史、试错记录
- 判断力：知道何时标准流程不适用、能一眼看出 AI 答案哪里不对——这是没法写成文档教会的经验直觉

**结论**：随着 AI 能力越来越普及和廉价，真正稀缺、随时间复利的资产会从"会不会用工具"转移到"能不能做出正确判断"。

---

## 十三、Harness 记忆机制

**为什么不能简单塞进 context window**：
- "迷失在中间"问题——超长上下文对中间部分信息的检索准确率明显下降
- 处理时间随长度线性增长，交互体验变差

**主流三层记忆架构**：
1. 会话内工作记忆（临时，会话结束清空，相当于 RAM）
2. 会话级压缩记忆（当前会话提炼的关键事实，按需读取）
3. 长期持久存储（跨会话知识、偏好、工作流，存于向量+图数据库，相当于硬盘）

**几个尚未解决的难题**：
- 记忆冲突检测（新事实与已有记忆的合并/更新/冲突判断）
- 跨会话身份识别（匿名会话、多设备场景下"这是不是同一个人"）
- 记忆过时（高相关性记忆一旦过时，会"自信地错误"，比低相关性记忆的自然衰减更难处理)
- 隐私和同意机制（谁能看、保留多久、怎么删除，目前各产品各自为政）

**新方向**：异步整理记忆——会话间用后台流程重新组织、提炼积累的记忆，类似人睡眠时的记忆巩固机制。

---

## 十四、可观测性与调试

**与传统软件监控的本质区别**：AI agent 是非确定性的，同一 prompt 可能有不同输出，很多失败不会报错——可观测性要捕捉"意图和过程"，不只是"输入输出"。

**三大支柱**：
1. **追踪（Tracing）**：完整执行路径——每次工具调用、检索步骤、中间推理，含时间戳、token 数、成本、延迟
2. **评估（Evaluation）**：自动评分器判断输出质量（幻觉检测、总结质量、格式合规等）
3. **成本/延迟监控**：逐步骤记录 token 消耗和延迟，便于复盘"钱花在哪一步"

**关键行业信号**：OpenTelemetry 的 GenAI 语义约定正在把这块标准化（类似 MCP 的路径）——先协议标准化，再产品层竞争。

**尚未解决的痛点**：多智能体场景下的责任追溯——一个决策出错会级联到后续所有步骤，需要层级化追踪（保留父子 agent 调用关系）才能定位问题源头。

---

## 十五、Agent 之间怎么互相说话（A2A 协议）

**MCP vs A2A 的分工**：
- MCP = 垂直方向,agent 到工具的连接
- A2A = 水平方向,agent 到 agent 的协作

**A2A 核心机制**：
- 由 Google 于2025年4月发布,2025年6月转交 Linux 基金会做中立治理
- **Agent Card**：描述 agent 能力和访问方式的元数据文档,agent 借此发现彼此、了解对方能做什么
- 底层技术：HTTP(S)、JSON-RPC、SSE,鉴权用 OAuth 2.0 + JWT——建立在成熟网络基础设施上,没有另起炉灶

**尚未解决的问题**：A2A 是"委托导向"的（回答"谁能处理这个任务"),但治理问题（协作链条里谁该为最终决策负责）目前仍是空白;协议本身也还没完全统一（IBM 的 ACP 是更轻量的替代方案,行业仍在多标准并存阶段）。

---

## 十六、Harness 的安全边界

**关键认知转折**：安全问题已经从"模型说错话"下沉到"harness 怎么执行动作"——业内评估认为，OWASP 定义的十大 agentic AI 风险类别里，八项本质是 harness 层面的问题,不是模型输出层面的问题。

**权限设计核心原则**：权限是基础设施问题，不是提示词问题——不能靠在 prompt 里"口头约定"来保证安全,必须在 harness 代码层面硬性拦截。

典型权限判定优先级：拒绝规则 → 询问规则 → 前置钩子二次校验 → 允许规则 → 默认模式 → 回调逻辑,钩子优先级高于模式,受保护路径在任何模式下都受保护。

**一个值得注意的设计难题**：批准率过高（如93%）说明确认对话框已经沦为"记录仪表盘"而非真正的安全屏障——用户会疲劳性地无脑同意,更合理的做法是常规操作直接放行、只对例外情况升级人工确认。

**沙箱隔离技术分级**：标准容器（隔离最弱,共享内核）< gVisor（用户空间拦截系统调用）< microVM（如 Firecracker/Kata Containers,每个工作负载独立内核,隔离最强）。

**行业共识**：安全是运营出来的，不是问出来的——约束运行环境、运行时强制执行策略、持续观测行为、准备好故障恢复路径,四者组合缺一不可，没有单一工具能端到端解决。

## 贯穿全篇的核心逻辑线

1. **模型同质化 → 护城河下移到 harness 工程细节 + 上移到分发信任层**
2. **开放协议（MCP、A2A、OpenTelemetry GenAI）与产品体验竞争并行不悖**——协议标准化不等于产品同质化,类似浏览器之战的格局
3. **一切能被写成文档（Prompt、Skill、流程）的东西都在快速贬值,专有数据、判断力、责任归属这些"抄不走"的资产在持续升值**
4. **随着 agent 自主性和并行度提升，记忆、可观测性、安全边界这三块基础设施的重要性同步陡增**——它们分别解决"记不记得""错哪了""出事前怎么防"

## 再回到开头the deep view的文章， 你觉得Agent 的真正壁垒是模型、Harness、Skill，还是开放协议？

这个问题其实是把我们聊过的所有线索收束到一起——我的看法是：**没有单一答案,因为这四层不是互相竞争”谁是壁垒”的关系,而是护城河在产品生命周期不同阶段依次转移的四个站点**。但如果一定要排出一个此刻最关键、且会持续最久的答案,我会说是**判断力驱动下的”数据+工程细节”组合，而不是任何一个单独的层**。展开说：
## 为什么不是单独的模型

我们在第四题聊过：跑分基本完全取决于接的是哪个模型,这是模型层”技术意义上”确实强的证据。但这次的深度分析文章本身讲的就是**模型层正在被主动商品化**——GPT-5.6 Sol、Terra、Luna 这些型号靠”效率优化”打出来的差异化,恰恰说明模型厂商自己都在往”更便宜、更快”卷,而不是单纯往”更聪明”卷。第九题聊到的现状也印证了：65%开发者觉得 Codex 代码质量不如 Claude Code,但依然更愿意用 Codex——**这本身就证明模型能力差距,已经不是用户决策里权重最大的变量了**。
## 为什么不是单独的 Harness

Harness 确实在我们聊过的十几个维度里（记忆、可观测性、安全边界、subagent、prompt caching）体现出真实的工程差异化,而且第六题聊过它很可能承接”模型同质化之后”的护城河转移。但**第八题已经戳破了这个逻辑的一个漏洞**：OpenAI 自己把 Codex harness 开源了。如果 harness 本身就是终极壁垒,厂商不会轻易把它免费开放出去——开源恰恰说明,**harness 这层的技术门槛本身没有高到构成独立壁垒的程度**,真正被保护起来、闭源收费的,始终是模型。
## 为什么不是单独的 Skill

第十一、十二题已经把这个问题拆得很干净了：Skill 本质上是可以被写成 Markdown、被复制、被行业标准化吸收的东西。**它是最快贬值的一层，不可能是”真正的”壁垒**,顶多是短期的先发优势。
## 为什么也不是”开放协议”本身

MCP、A2A、OpenTelemetry GenAI 这些协议(第十五、十六题聊过)恰恰是**反壁垒的力量**——它们存在的意义就是防止某一层被某家公司封闭垄断。协议开放不构成谁的壁垒,反而是拆解壁垒的工具。类比我们聊过的浏览器之战：HTML/CSS 是开放标准,但这没让 Chrome 和 Firefox 变得一样好用。
## 我认为真正的壁垒在哪

回到第七题、第十二题的核心结论——**壁垒最终落在”抄不走的东西”上**,而这四层里,只有一样东西天然抄不走：
**长期积累的、场景化的专有数据 + 建立在这些数据之上的工程判断力**（这里的”判断力”既包括产品团队对”这套 harness 该怎么设计”的判断,也包括企业用户对”这个 agent 结果靠不靠谱”的判断)。具体体现为：
- 模型可以被商品化（第三题已验证）
- Harness 代码可以被开源、被复制（第八题已验证）
- Skill 可以被写成文档、被行业标准吸收（第十一题已验证）
- 协议本身被设计成开放的（第十五、十六题已验证）

**唯一没法被这套”开放化”逻辑吸收的,是每家公司在真实用户交互里积累下来的、关于”什么设计能真正解决用户问题”的专有认知,以及用户因为长期投入而产生的迁移成本（记忆、工作流历史、信任关系）**——这跟第十三题聊的记忆机制其实是同一个逻辑在个体用户身上的投影：你我这几十条对话积累下来的上下文,才是真正没法被任何竞争对手一键复制走的东西。
**所以我的结论是**：模型、Harness、Skill 都会持续被开放协议和行业标准”拉平”,这是这篇文章和我们整场讨论共同指向的趋势;而真正撑得住的壁垒,是建立在这四层之上、由长期真实使用积累出来的**数据资产和判断力资产**——这也是为什么这篇报道最后落脚在”降低成本、扩大用户规模”,而不是”证明模型更聪明”上：**当技术层面都在被拉平时,谁能让更多用户在自己的生态里沉淀更长时间的真实使用历史,谁才握着最后剩下的那张牌**。
