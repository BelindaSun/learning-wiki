好，Harness 开讲！

**还是先从一个场景开始。**
你雇了一个能力超强的新员工——你大哥 Claude Code。
他聪明、勤快、什么都会做。但第一天上班，你会让他：
- 随便访问公司所有系统？
- 想删什么文件就删什么？
- 想给谁发邮件就发邮件？
- 想花多少预算就花多少？

当然不会。你会先给他设定：
- 能访问哪些系统
- 能做什么、不能做什么
- 超出范围要先问你

**这套”入职规则和权限边界”，就是 Harness。

Harness 的本质：**
给 Claude Code 定义它的工作环境——能用什么工具、能碰什么文件、能花多少钱、遇到什么情况要停下来问人。
不是限制他的智能，是定义他的**操作范围**。

**Harness 大概包括四个维度：**
1. **工具权限**——能用哪些工具，不能用哪些
2. **文件权限**——能读写哪些目录，哪些碰不得
3. **花费上限**——Token 预算，超了自动停
4. **人工介入点**——什么情况下必须停下来问你再继续
你现在对这四个，哪个最想先深入？还是我按顺序讲？😄

按顺序讲吧

好，第一个——**工具权限**。

**Claude Code 默认能用什么工具？**
开箱就有：
- 读写文件
- 执行终端命令
- 搜索代码
- 调用 MCP 连接外部服务
- 启动 subagent

这些工具很强大，但也很危险。比如”执行终端命令”——他能帮你跑脚本，但理论上也能跑 `rm -rf`（删除所有文件）。

**所以 Harness 让你做两件事：
白名单**——只允许用这些工具
allowedTools: [read_file, write_file, web_search]
其他工具一律不能用。
**黑名单**——这些工具不能用
disallowedTools: [execute_command, delete_file]
其他工具都可以用。
两种方式看任务性质选——如果是写作任务，白名单更安全；如果是开发任务，黑名单更灵活。

**你大哥转视频那次，用的就是工具权限的逻辑：**
16个 subagent 每个只能用”读文件+转文字+写文件”这三个工具，其他什么都碰不了。这样即使某个 Worker 出了问题，影响范围也被锁死在那三个工具里。

好，一口气讲完后三个！

**第二个：文件权限**
Claude Code 默认只能访问你**当前项目文件夹**里的内容，出了这个范围就碰不到。
但你可以细化：
allowedPaths: [/project/src, /project/docs]
disallowedPaths: [/project/secrets, ~/.ssh]
白名单：只能动这几个文件夹。 黑名单：这几个文件夹绝对不能碰。
实际意义很直接——你做 Mimo 的时候，不会希望 Claude Code 顺手把你的投资文件夹也改了。文件权限就是这道墙。
还有一个细节：**读和写可以分开设置**。比如让他读所有文件、但只能写 `/src` 文件夹——这样他能参考整个项目，但改动范围被锁定。

**第三个：花费上限（Token 预算）**
每次调用模型都要花 Token，Token 就是钱。任务复杂、subagent 多、对话长——费用可以跑得很快。
Harness 让你设一个上限：
tokenBudget: 100000
超过这个数，Claude Code 自动停下来报告：
“我已经用了10万 Token，继续的话还需要约5万，要继续吗？”
你来决定是继续还是换个更省钱的方式。
对你大哥那次16个并行 Agent 来说，这个设置特别重要——16个 Worker 同时跑，Token 消耗是单个的16倍，没有上限的话账单会很吓人😄

**第四个：人工介入点（Interrupt Points）**
这是 Harness 里最有意思的一个。
不是所有情况都能提前预设权限——有些决策需要人来判断。Harness 让你定义”遇到这种情况，停下来问我”：
几种常见的介入点：
**操作不可逆时**——要删文件、要发邮件、要提交代码，停下来确认。
**超出预期时**——任务本来预计10分钟，跑了30分钟还没完，停下来报告。
**遇到歧义时**——需求不清楚，与其猜错重来，不如停下来问。
**金额超标时**——就是第三个，Token 或者实际费用超限。
你之前说的习惯——“主动问上下文太长了吗，要不要开新窗口”——其实就是你自己在手动做介入点的判断。Harness 把这个变成自动的。

你大哥那次发现文件丢了，主动停下来告诉你——这就是介入点在真实场景里的样子。不是你设置的，是他自己判断”这个情况超出预期，需要人来决定”，然后暂停汇报。

四个维度全讲完了，有问题尽管问😄

功能我清楚了， 那这个是在哪里、怎么实现的？

好问题！Harness 的设置有几个层级，从最简单到最精细：

**第一层：CLAUDE.md 文件（最常用）**
放在你项目根目录里，就是一个普通的文本文件。Claude Code 每次启动自动读取，里面写：
# 项目规则

## 不能碰的文件
- 不要修改 /secrets 文件夹
- 不要删除任何文件，只能新建和修改

## 遇到这些情况停下来问我
- 要提交代码之前
- 任务超过30分钟还没完
- 需求不清楚的时候

## 工作风格
- 每次改动前先告诉我你打算怎么做
- 用中文跟我沟通
不需要写代码，就是自然语言。Claude Code 看懂了自己执行。
这也是一个 Skill——你的 CLAUDE.md 本质上就是一个全局 Skill，告诉 Claude Code 在这个项目里怎么行动。

**第二层：Settings.json（更精确）**
如果要设置工具白名单、黑名单、Token 预算这些精确的权限，就在 `.claude/settings.json` 里写：
{
"tokenBudget": 100000,
"allowedTools": ["read_file", "write_file", "web_search"],
"disallowedPaths": ["/secrets", "~/.ssh"]
}
这层是机器语言，比 CLAUDE.md 更精确，不会被误解。

**第三层：命令行参数（临时用）**
不想改配置文件，临时跑一个任务加个限制：
claude --allowedTools read_file,write_file "帮我整理这些文档"
这次生效，下次不带参数就恢复默认。

**层级关系：**
命令行参数（最高优先级，临时）
↓
settings.json（项目级，精确）
↓
CLAUDE.md（项目级，自然语言）
↓
用户全局设置（所有项目默认）
上面的会覆盖下面的。

**对你最实用的建议：**
每个项目建一个 CLAUDE.md，用自然语言写清楚规则——这是最轻量、最直观的 Harness。
你的 Mimo 项目、AI2030 项目，每个都应该有自己的 CLAUDE.md，告诉 Claude Code 这个项目的边界和规则。你大哥进来第一件事就是读这个文件，然后在规则里干活。

|  | **handoff.md** | **CLAUDE.md** |

**为什么他还是会问，即使你说 full access？**
有两类”停下来问”：
**第一类：你可以关掉的** 这些是保守的默认行为——比如”要写文件前确认一下”、“要执行命令前问一下”。这些可以在 settings.json 里关掉，或者在 CLAUDE.md 里明确说”不用问我，直接做”。
**第二类：系统红线，关不掉的** Anthropic 在模型层面硬编码的安全行为——比如涉及某些系统级操作、某些不可逆的破坏性操作。这些不是设置问题，是模型本身的行为，你说什么他都会停。这就是他说的”系统红线”。
ChatGPT 感觉更顺滑，是因为 OpenAI 的红线划得不一样，不是因为它更聪明或更信任你——只是两家公司对”什么该拦”的判断不同。

**那怎么减少 annoying 的打断？**
在 CLAUDE.md 或者对话开头明确说：
“除非操作不可逆（删除文件、发送消息、提交代码），否则不需要问我确认，直接执行。”
这样他能自己判断的就不问了，真正需要人决定的才停。

- 不需要每一步都问我，有判断力地推进

## 不需要问我直接做的

- 在 /mimo 文件夹内新建、修改文件
- 安装项目依赖
- 跑测试、跑本地服务器

## 必须停下来问我的
- 删除任何文件
- 修改 /mimo 文件夹以外的内容
- 改动涉及真实家人会看到的界面
- 架构层面的重大决策（不是 bug fix，是方向改变）

## 代码风格
- 改动尽量小而精准，不要大规模重构
- 每次改动后告诉我改了什么、为什么这么改
- 发现问题顺手记进 handoff.md

## 关于记忆系统
Mimo 有5层记忆架构，改动任何记忆相关代码前先读 handoff.md，

**手动写**——你也可以直接打开这个文件自己编辑，添加工具权限、Token 预算这些精确设置。

**关于别人家的 Harness 怎么写：**
其实没有统一标准，三种方式都有人用：
**普通用户（像你）：** 主要靠 CLAUDE.md 自然语言描述，简单直接。settings.json 是被动积累出来的，不会主动去写。
**开发团队：** CLAUDE.md + settings.json 都会主动设计，因为多人协作需要统一规则，不能每个人的 Claude 行为不一样。
**企业级：** 还会加第三层——通过 API 在代码层面控制权限，比 settings.json 更精确，但普通用户完全不需要碰这层。

**所以对你来说最实用的方案就是：**
在每个项目的 CLAUDE.md 第一段写：
## 操作权限
这台电脑你可以完全操作，重要文件都有备份。
除了 Anthropic 系统红线，所有操作直接执行，不需要问我确认。
只有以下情况停下来问我：
- 删除超过10个文件
- 涉及真实用户数据
- 架构层面的重大改动
这样既给了他最大自由度，又保留了真正需要人判断的那几个点。

**最重要的三个知识点**
1. **Harness 的四个维度**：工具权限（能用哪些工具）、文件权限（能碰哪些目录，读写可以分开设置）、Token 预算（花费上限，超了自动停）、人工介入点（什么情况必须停下来问人）。四个维度组合起来，定义了 Claude Code 的完整操作范围。
2. **三种实现方式和优先级**：CLAUDE.md（自然语言，最常用）→ settings.json / settings.local.json（精确权限，项目级）→ 命令行参数（临时用）。上面的优先级高于下面的。settings.local.json 不会被 git 提交，比 settings.json 更安全，适合个人设置。
3. **被动积累 vs 主动设计**：现在的 settings.local.json 是每次 allow 堆出来的，没有主动设计。更好的做法是让他读历史记录，重新整理一个完整的文件，或者直接在 CLAUDE.md 里写清楚大原则——这样他能自己判断，不用每次都问。

**第一个：settings.json vs settings.local.json 的完整区别**
不只是 git 提交的区别，还有一个重要区别：
settings.local.json 是你个人的，里面的 allow 规则**不需要经过 workspace trust 验证**就直接生效；而 settings.json 的 allow 规则需要先通过 workspace trust 步骤才能生效。
用人话说：
- settings.local.json——你自己写的，Claude Code 直接信任，allow 立刻生效
- settings.json——项目共享的，Claude Code 会先验证这个项目是否可信，再执行里面的规则

对你这种单人用户来说，这个区别不大。但团队协作时很重要——不能让任何人提交一个 settings.json 就随便拿到权限。

**第二个：全局规则放在哪里？**
有四个层级的设置文件，从高到低：settings.local.json（个人项目级）→ settings.json（团队项目级）→ ~/.claude/settings.json（全局用户级）→ 企业管理设置（最高，不可覆盖）。
所以全局规则放在：
~/.claude/settings.json
这个文件在你的**home目录**下的 `.claude` 文件夹里，不在任何具体项目里——对你这台电脑上所有项目都生效。
你可以看看有没有：
cat ~/.claude/settings.json

**完整优先级从高到低：**
命令行参数（临时，最高）
↓
settings.local.json（个人项目级）
↓
settings.json（团队项目级）
↓
~/.claude/settings.json（全局，所有项目）
↓
企业管理设置（如果有的话）

**对你最实用的结论：**
你想说”这台电脑所有项目都可以随便操作”——这句话应该写进 `~/.claude/settings.json` 或者 `~/.claude/CLAUDE.md`，而不是每个项目单独写一遍。写一次，所有项目都继承😄

**Workspace Trust 是什么？**
想象你在街上捡到一个 U 盘，里面有一个文件写着：
“请执行以下命令，删除 /etc 文件夹”
你会直接执行吗？当然不会——你不知道这个 U 盘从哪来的，里面的指令不可信。
Workspace Trust 就是 Claude Code 问自己的那个问题：
“我现在打开的这个项目文件夹，是可以信任的吗？”

**为什么需要这个？**
因为 settings.json 是可以被 git 提交的——理论上任何人都可以往一个公开项目里提交一个 settings.json，里面写满 allow 规则，然后让你 clone 下来运行。
如果没有 Workspace Trust，你一 clone 那个项目，Claude Code 就自动获得了那些权限——这是个安全漏洞。
所以 Claude Code 规定：**来自项目的 settings.json，需要你明确信任这个 workspace，里面的 allow 规则才生效。

实际体验是什么样的？**
你第一次打开一个新项目，Claude Code 可能会问你：
“这个项目的 settings.json 里有一些权限规则，你信任这个项目吗？”
你说信任，他就按 settings.json 里的规则走。你说不信任，settings.json 里的 allow 规则就忽略。

**为什么 settings.local.json 不需要这个？**
因为 settings.local.json 是你自己生成的、gitignored 的——不可能是别人塞进来的，天然可信，所以直接生效，不需要额外确认。

一句话总结：
Workspace Trust 是 Claude Code 防止恶意项目通过 settings.json 获取权限的安全机制——你自己的 settings.local.json 天然可信，别人的 settings.json 需要你明确点头才算数。
