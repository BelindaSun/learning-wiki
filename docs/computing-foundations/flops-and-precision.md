# FLOPS 与精度：为什么降精度能提速

**核心概念**: 上一篇 [CPU vs GPU](cpu-vs-gpu.md) 已经讲了 GPU 为什么靠"海量核心并行"赢过 CPU。这篇接着往下问：同一块 GPU，为什么把数字的精度调低，速度还能再快一截？原因不止一个——数字更小，同样宽的硬件能同时塞下更多；数字更小，搬运也更快；硬件还专门为低精度运算开了快车道。三条加在一起，效果不是"快一点点"，而是**数量级的差距**。

---

## FLOPS 是什么

**FLOPS**（Floating-point Operations Per Second，每秒浮点运算次数）是衡量"这块硬件一秒钟能做多少次数学运算"的单位——不是"这块芯片有多聪明"，纯粹是"手有多快"。

**最简单的心智图像**：FLOPS 像一条流水线一秒钟能装配多少个零件——流水线越宽（核心越多，见 [CPU vs GPU](cpu-vs-gpu.md)）、每个零件越小（数字精度越低），单位时间能装配的零件就越多。

### 真实硬件的 FLOPS 长什么样

以 NVIDIA H100 SXM（目前 AI 训练/推理的主力 GPU）为例：

| 精度 | 峰值 FLOPS | 相对 FP32 |
|------|-----------|-----------|
| FP32（CUDA 核心） | ~67 TFLOPS | 1× |
| FP16 / BF16（Tensor Core） | ~990 TFLOPS | ~15× |
| INT8（Tensor Core） | ~1,979 TOPS | ~30× |

同一块芯片，精度从 FP32 降到 INT8，峰值吞吐量差了 **~30 倍**——不是线性的"位宽减半、速度翻倍"，而是三个加速因素叠加在一起的结果（下面展开讲）。

（TFLOPS = 万亿次浮点运算/秒；TOPS = 万亿次整数运算/秒。这些具体数字会随硬件迭代而变，记住数量级的关系比记具体数字更有用。）

## 精度是什么，为什么它能换速度

一个数字要占多少"位置"，取决于用几个 bit 去表示它——这就是**精度（Precision）**。同样一条比如说 256 bit 宽的计算通道：

```
如果每个数字用 32 bit 表示 → 一次能塞下  8 个数
如果每个数字用 16 bit 表示 → 一次能塞下 16 个数
如果每个数字用  8 bit 表示 → 一次能塞下 32 个数
```

**数字越"粗略"，硬件同一条通道里能同时塞下的数字就越多**——这是降精度能提速的一个原因，但不是唯一原因。降精度从三个方向同时帮上忙：

1. **塞得下更多**（上面这条）：同样宽的计算通道，一次能同时处理更多数字。这跟 [CPU vs GPU](cpu-vs-gpu.md) 里"GPU 靠海量核心并行"是同一个逻辑的另一层——并行是"同时用多少个核心干活"，精度是"每个核心一次能处理多宽的数字"，两个维度都在把"同时能干的量"堆上去。
2. **搬得更快**：数字变小了，占的存储空间也变小，同样的内存带宽单位时间能搬运更多数字。一个 70B 参数的模型，FP32 存储需要 ~280 GB，BF16 只需要 ~140 GB，INT8 只需要 ~70 GB，INT4 只需要 ~35 GB——不只是存储空间省了，每次推理时要从内存搬到计算单元的数据量也相应减少，对 memory-bound 的推理场景（见 [内存墙](memory-wall.md)）这一条的提速效果尤其显著。
3. **硬件专门为它开了快车道**：[CPU vs GPU](cpu-vs-gpu.md) 已经讲过 Tensor Core——Tensor Core 对低精度运算有专门优化的计算路径，不只是"数字变小了顺便塞得下更多"。上面 H100 的 FLOPS 表里，FP16 相对 FP32 差了 ~15 倍，如果只是"位宽减半"应该只差 2 倍——剩下的倍数就来自 Tensor Core 本身为低精度做的专用加速。

这三条加在一起，才是"降精度能提速"背后更完整的原因，也解释了为什么 H100 上 FP32 → INT8 能差 ~30 倍而不是简单的 4 倍（32÷8=4）。

代价也在这——精度降低，数字表示得没那么精确，模型算出来的结果可能有偏差。什么时候这点偏差可以接受、什么时候不行，是 [Quantization（量化）](../ai-research/models-deep-dive.md#技术-3量化quantization) 要回答的问题（那篇讲的是"精度换了多少准确率"，这篇讲的是"精度为什么能换速度"——两个不同的问题）。

## 常见的精度格式

FP32、FP16、BF16、INT8、INT4 是"精度"这个概念在实际硬件/框架里的具体名字。不用死记每一种的编码细节，但 BF16 值得单独说一句：

| 格式 | 位数 | 大致用途 |
|------|------|----------|
| FP32 | 32 bit | 训练时的"高精度"基线；通用计算的默认精度 |
| FP16 | 16 bit | 推理里常见的折中 |
| BF16 | 16 bit | 训练里越来越常用的折中（Google 专门为深度学习设计） |
| INT8 | 8 bit | 推理加速，整数运算 |
| INT4 | 4 bit | 更激进的推理压缩 |

### 为什么 BF16 会存在——FP16 不够用吗？

FP16 和 BF16 都是 16 bit，但这 16 bit 的"分配方式"不同：

- **FP16**：5 bit 指数 + 10 bit 尾数——数字精细度高，但能表示的**范围**比 FP32 小得多
- **BF16**：8 bit 指数 + 7 bit 尾数——数字精细度降了，但指数位跟 FP32 一样多，**范围**跟 FP32 一样大

训练深度学习模型时，梯度的数值范围波动很大——有些梯度极小，有些极大。FP16 的范围太窄，极端值容易"溢出"（数字大到表示不了）或"下溢"（数字小到被当成零），导致训练不稳定。BF16 牺牲了一点精细度，换来了跟 FP32 一样的范围——训练时更不容易"炸"。这就是为什么 BF16 是 Google 专门为深度学习训练设计的格式，不是 FP16 的简单替代品。

**位数越少不代表准确率一定掉得越多**——具体损失多少，取决于模型、任务和量化方法，没有一条"到 INT8/INT4 就开始明显变差"的通用门槛，实际效果要具体测。这也是为什么 [Models 深挖](../ai-research/models-deep-dive.md#技术-3量化quantization) 会把"8-bit 量化"和"更激进的量化"分开讨论，而不是套一个固定标准。

## 混合精度：不是"全高"或"全低"的二选一

实际系统里，很少会全程只用一种精度。更常见的做法是**混合精度（Mixed Precision）**——在同一次训练或推理过程中，不同的计算步骤用不同的精度：

- 矩阵乘法这类"重活"用低精度（FP16/BF16）做，速度快
- 累加、梯度更新这类对精度敏感的步骤用高精度（FP32）做，结果准
- 两种精度之间按需转换

混合精度不是"牺牲一半准确率换一半速度"——设计得好的混合精度方案，最终模型的准确率跟全 FP32 训练几乎没有区别，但训练速度快了一大截、显存占用也低了。这也是为什么现在主流的训练框架（PyTorch 的 AMP、DeepSpeed 等）默认就开启混合精度，而不是让用户自己选"用 FP32 还是 FP16"——答案是"都用，但用在不同的地方"。
