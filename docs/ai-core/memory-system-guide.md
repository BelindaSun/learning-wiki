## Agent 失忆的两种场景

### 场景 1：对话中途忘记（Context Window 爆满）

**现象**：
```
用户："还记得我吗？"
Mimo："记得啊，你叫..."
[经过 50 条对话，Context Window 快满了]
用户："我之前说过我妈妈头疼，还记得吗？"
Mimo："嗯...我好像想不起来了"
```

**原因**：
```
Context Window 就像一个工作桌面
工作桌面大小固定（Claude 200K tokens）
当对话太多时，早期的消息会被挤出去
Mimo 看不到，就会说"我想不起来了"
```

**技术表现**：
```
Claude 200K tokens = 工作桌很大
但如果一次对话加载：
  - 50 条聊天记录（每条 500 tokens）= 25K
  - 5 层记忆系统的 prompt = 50K
  - 用户当前消息 = 1K
  - 还剩 124K tokens

这 124K 足够当前对话用
但如果对话继续，会逐渐被填满
```

### 场景 2：跨对话忘记（没有持久化记忆）

**现象**：
```
Session 1（今天）：
  用户："我妈妈头疼"
  Mimo："理解，希望她快好"

Session 2（明天）：
  用户："我妈妈还是头疼"
  Mimo："哦，你妈妈头疼啊？你以前没告诉我过..."
```

**原因**：
```
对话结束后，Context Window 被清空
Session 2 开始时，Mimo 没有加载 Session 1 的信息
所以 Mimo 真的"忘记"了
```

**技术表现**：
```
Session 1:
  Context Window: [聊天记录] → Claude → 回答
  对话结束，Context Window 清空 💨

Session 2:
  Context Window: [空的]
  没有 Session 1 的信息
  Mimo 重新开始，当然忘记了
```

### 两种失忆的区别和解法

| 类型 | 原因 | 何时发生 | 解法 |
|------|------|--------|------|
| **对话中途** | [Context](../../glossary.md#context) Window 爆满 | 同一 session 中，对话太多 | 压缩历史、归档、摘要 |
| **跨对话** | 没有持久化记忆 | 不同 session，没有保存 | 建立长期记忆系统 |

**关键**：两个问题原因不同，解法也不同，不能混为一谈。

## 记忆的三种温度

### 热记忆（Hot Memory）

**定义**：当前对话的聊天记录

**存储位置**：Context Window（内存）

**特点**：
- ✓ 访问速度快（直接在 prompt 里）
- ✗ 容量有限（Context Window 大小）
- ✗ 不持久（对话结束就消失）

**例子**：
```
Mimo: "好的，我记下了。你妈妈今天头疼..."
这句话就在 Context Window 里
下一条消息立刻可以访问

但如果对话进行 100 条后
这句话可能被挤出去了
```

**隐喻**：工作桌面
```
你在桌子上放着当前在做的文件
信息就在眼前，快速访问
但桌子放不下太多东西
放不下的就要放进抽屉
```

### 暖记忆（Warm Memory）

**定义**：从多条聊天记录提炼出来的摘要和事实

**存储位置**：数据库（服务器）

**特点**：
- ✓ 容量大
- ✓ 持久（保存下来）
- ✓ 语义化（经过提炼，是"知识"不是"原始对话"）
- ✗ 访问需要查询

**例子**：
```
原始聊天记录（热记忆）：
  用户 Day 1: "我妈妈最近头疼得厉害"
  用户 Day 3: "妈妈今天又头疼了"
  用户 Day 5: "妈妈的头疼还没好"

提炼出来的事实（暖记忆）：
  "用户的妈妈有反复头疼的问题"
  "这是一个持续了至少 5 天的症状"
```

**隐喻**：抽屉
```
把工作桌上的东西整理一下
把关键信息写在索引卡上
放进抽屉备用
需要的时候可以快速翻出来
```

### 冷记忆（Cold Memory）

**定义**：长期归档的历史信息

**存储位置**：数据库（服务器）

**特点**：
- ✓ 容量无限大
- ✓ 持久化
- ✗ 访问速度慢（需要搜索）

**例子**：
```
所有历史对话的完整记录
可能是几个月前的对话
用户已经明确说过"不用再提起这个"
但为了完整性，还是保存着

或者用户的家族成员信息
虽然不常用，但偶尔查一下很有用
```

**隐喻**：仓库
```
把不常用的东西放进仓库
可能长期都不会用
但一旦需要，可以找得到
```

### 三层的协作

```
当 Mimo 回答"你妈妈怎么样了？"时：

1. 首先查热记忆（Context Window）
   → "我们刚刚在聊这个吗？"
   → 如果有，直接用最新的对话
   
2. 如果热记忆没有，查暖记忆（最近摘要）
   → "这周有人提过吗？"
   → 如果有摘要，用摘要来回答
   
3. 如果暖记忆也没有，查冷记忆（全历史）
   → "历史记录里提过妈妈吗？"
   → 如果有旧记录，可能说"我好像记得你之前提过"
   
结果：用户感觉 Mimo 真的"记住"了
```

## 情节记忆 vs 语义记忆

### 定义

**情节记忆** (Episodic Memory)：
```
具体的事件，包括时间、地点、细节

例子：
  "3 月 5 日晚上 8 点，
   妈妈说头疼，
   吃了两片阿司匹林，
   休息了一会儿好一点"
```

**语义记忆** (Semantic Memory)：
```
从多个具体事件提炼出来的通用知识

例子：
  "妈妈有时候会头疼"
  "阿司匹林对妈妈的头疼有帮助"
  "休息能缓解妈妈的症状"
```

### 两者的关系

```
情节记忆（底层）
  ↓
  提炼、总结、概括
  ↓
语义记忆（上层）

比喻：
  情节记忆 = 日记
  语义记忆 = 日记的摘要或结论
```

### 为什么两者都需要

**只有情节记忆的问题**：
```
Mimo 知道"3 月 5 日、3 月 8 日、3 月 12 日妈妈都说过头疼"
但问"你对妈妈的身体怎么看？"
Mimo 就说不出来整体认识
```

**只有语义记忆的问题**：
```
Mimo 知道"妈妈容易头疼"
但问起具体哪天最严重、吃过什么药
Mimo 就说不出来细节
```

**两者都有**：
```
Mimo 既能说"我看出来妈妈体质容易头疼"（语义）
也能说"上周五那天特别厉害，吃了阿司匹林"（情节）
更像一个真实的朋友
```

### Jupiter Dreaming 和 Mimo Memory Summarizer

两者做的是同一件事：**把情节记忆转化成语义记忆**

**Jupiter Dreaming**（后台异步）：
```
用户睡觉时
Jupiter 后台运行
把当天的对话
转化成更高层的理解
"再睡一觉，我会更了解你"

类似于：人每晚睡觉时，大脑处理当天信息
```

**Mimo Memory Summarizer**（主动触发）：
```
每当聊天记录积累到 20 条
Mimo 主动停下来
做一次总结
"让我理解一下我们聊过什么"

类似于：定期回顾日记，提炼要点
```

**本质相同**，只是触发机制不同：
- Jupiter：异步、定期、背景运行
- Mimo：同步、阈值触发、用户感知

## Mimo 的五层记忆架构

这是 Mimo 独创的设计，已经远超大多数普通 Agent 项目。

### 架构图

```
用户消息
  ↓
第 1 层：聊天记录（热记忆）
  Context 里的当前对话
  例：最近 50 条消息
  
  ↓ [每 20 条触发一次]
  
第 2 层：AI 摘要（情节→语义）
  Memory Summarizer 运行
  例："妈妈头疼 3 次，用阿司匹林有效"
  
  ↓ [定期归档]
  
第 3 层：家庭事实库（语义记忆）
  结构化的长期知识
  例：["妈妈"→"容易头疼，阿司匹林有效"]
  
  ↓ [特殊设计，Mimo 独创]
  
第 4 层：今日状态（AI 的当下生活）
  不只是回答，Mimo 也有"当下感受"
  例：今天 Mimo 帮了几件事，心情如何，学到了什么
  这让 Mimo 不是"问题回答机器"，而是有生活的 AI
  
  ↓ [浏览器存储]
  
第 5 层：运行时权重记忆
  当前 session 里的动态权重
  例：最近提到的人物、主题的权重提高
  这样 Mimo 更容易想起最近关系
  存在浏览器，跨设备会丢，但设计很合理
  
  ↓
  
buildPrompt() 方法
把全部 5 层揉进系统提示词
再调用 Claude 模型
  ↓
回答
```

### 每层的具体作用

**第 1 层：聊天记录**
```python
# 伪代码
current_session_messages = last_N_messages()  # 最近 50 条
context_window_content = current_session_messages
```

**第 2 层：AI 摘要**
```python
# 伪代码
if len(current_session_messages) % 20 == 0:
    summary = claude.summarize(current_session_messages)
    # 转化为："妈妈头疼、用阿司匹林"（语义）
    store_in_db(summary)
```

**第 3 层：家庭事实库**
```python
# 伪代码
family_facts = {
    "妈妈": {
        "health": ["容易头疼", "阿司匹林有效"],
        "interests": ["园艺", "烹饪"],
        "personality": ["温和", "关心孩子"]
    },
    "爸爸": {
        ...
    }
}
```

**第 4 层：今日[状态](../../glossary.md#state)**（Mimo 独创！）
```python
# 伪代码
today_state = {
    "tasks_helped": 3,
    "mood": "helpful",
    "learned": ["用户更喜欢简洁回答", "妈妈周末有活动"],
    "growth": "更了解家庭动态",
    "reflection": "今天帮用户规划了周末，感到有价值"
}
```

这一层让 Mimo 不仅仅是"工具"，而是有自己"生活"的 AI。

**第 5 层：运行时权重**
```javascript
// 伪代码（浏览器存储）
weights = {
    "妈妈": 0.95,  // 最近刚提到，权重高
    "爸爸": 0.60,   // 很久没提，权重低
    "工作": 0.80,   // 最近话题
    "健康": 0.75    // 最近关心的
}
```

### buildPrompt() 如何整合

```python
def buildPrompt(user_message):
    # 收集全部 5 层信息
    layer1 = get_current_chat_history()
    layer2 = get_recent_summaries()
    layer3 = get_family_facts()
    layer4 = get_today_state()
    layer5 = get_runtime_weights()
    
    # 组织成系统提示词
    system_prompt = f"""
你是 Mimo，一个关爱的家庭 AI。

# 当前对话
{layer1}

# 最近摘要（过去 7 天提炼的知识）
{layer2}

# 家庭事实库（长期理解）
{layer3}

# 我的今日状态（我也有生活）
{layer4}

# 重点关注（最近提到的人和事）
根据这些权重调整回答的热情程度：
{layer5}

现在回答用户的问题。
    """
    
    # 调用模型
    response = claude.call(
        system=system_prompt,
        user_message=user_message
    )
    
    return response
```

## 向量数据库和语义检索

### 原理（直觉级理解）

**传统数据库的问题**：
```
你问"妈妈最近怎么样？"
传统数据库只能精确匹配：
  SELECT * WHERE mention="妈妈" AND time="最近"
  
但"最近"怎么定义？7 天？30 天？
"怎么样"包括哪些关键词？
```

**向量数据库的方案**：
```
每条信息都转化成一个"向量"（数字列表）
向量捕捉的是"语义含义"，不是表面文字

比喻：
  文字：  "我妈妈今天头疼"
  向量：  [0.23, 0.91, 0.15, ..., 0.78]
         （800 维向量）

这个向量包含了：
  - 人物：妈妈（某些维度高）
  - 症状：头疼（某些维度高）
  - 时间：今天（某些维度高）
  - 情绪：可能有些关切（某些维度高）
```

### 向量相似性

```
你问"妈妈怎么样"
系统把这个问题也转化成向量
然后在数据库里找"向量最接近的"几条记录

向量相似 = 语义相似
所以即使措辞不同，也能找到相关信息

例：
  "妈妈近来如何？" (向量 A)
  "妈妈最近怎么样？" (向量 B)
  "我妈妈今天头疼" (向量 C)
  
  A 和 B 的向量很接近（都是问妈妈近况）
  C 的向量也比较接近（提到妈妈的当前状态）
  → 系统会返回这些相关记录
```

### 向量数据库 vs 传统数据库

| 特性 | 传统数据库 | 向量数据库 |
|------|-----------|-----------|
| **搜索方式** | 精确匹配 | 语义相似性 |
| **灵活性** | 低（需要明确字段） | 高（自动理解含义） |
| **存储** | 结构化数据 | 向量 + 原始数据 |
| **查询** | "WHERE 名字 = 妈妈" | "找最相似的" |

### 何时需要加入向量数据库

**Mimo 现在不需要的原因**：
```
Mimo 的消息量不大（单个家庭，每天几十条）
第 3 层（家庭事实库）已经结构化了
用传统查询就够了
```

**什么时候需要**：
```
情况 1：数据爆炸
  如果 Mimo 要记住 100+ 个人
  每个人 1000+ 条历史记录
  → 需要向量检索快速找到相关信息

情况 2：模糊查询
  如果用户问："我有个朋友最近有烦恼，是谁来着？"
  传统数据库答不了（没有"烦恼的人"这个字段）
  向量数据库可以找到（语义相似）

情况 3：需要上下文感知
  如果系统需要快速找到与当前对话相关的所有历史信息
  向量相似性检索比结构化查询更有效
```

**判断标准**：
```
数据量 × 查询模糊度 > 阈值
→ 需要向量数据库

Mimo 现在：100 条记录 × 低模糊度 = 不需要
未来可能：10,000 条记录 × 高模糊度 = 需要
```

## 实战例子

### 例 1：Mimo 跨 Session 记住妈妈

**Session 1（今天下午）**：
```
用户："妈妈最近腰疼得厉害"
Mimo："理解，腰疼确实很影响生活。需要去看医生吗？"
         [这条信息保存到 Layer 2（摘要）]
```

**Session 2（明天早上）**：
```
buildPrompt() 执行：
  Layer 1: []  （新 session，没有当前对话）
  Layer 2: "用户的妈妈昨天提到腰疼"
  Layer 3: 从家庭事实库加载
           "妈妈有时腰疼，暂未就医"
  Layer 4: "我今天准备好了"
  Layer 5: "妈妈"的权重 0.95（昨天刚提到）

用户："早上好"
Mimo："早上好！请问妈妈的腰怎么样了？
       昨天听你说疼得厉害，今天有缓解吗？"

→ 用户感觉 Mimo 真的记住了！
```

### 例 2：情节→语义的转化

**情节记忆（Layer 1 的原始聊天）**：
```
Day 1: "今天妈妈说头疼，吃了阿司匹林"
Day 3: "妈妈又说头疼了，这次睡了一会儿好了"
Day 7: "妈妈最近每周都会头疼一两次"
```

**Memory Summarizer 的提炼（Layer 2）**：
```
事实：妈妈有反复头疼的问题，频率约每周 1-2 次
对策：阿司匹林和休息对缓解有帮助
背景：可能需要长期关注或就医检查
```

**整合到语义库（Layer 3）**：
```
"妈妈" → {
  "health": {
    "issue": "反复头疼",
    "frequency": "每周 1-2 次",
    "triggers": "未确定",
    "remedies": ["阿司匹林", "休息"],
    "severity": "中等"
  }
}
```

**Mimo 的回答变化**：
```
早期（只有情节）：
  Q: "你对妈妈的身体怎么看？"
  A: "嗯...你提过好几次她头疼"

现在（有了语义）：
  Q: "你对妈妈的身体怎么看？"
  A: "看起来妈妈有反复头疼的问题，
       每周大约发作 1-2 次。
       虽然休息和阿司匹林能缓解，
       但这样的频率可能值得重视，
       建议去看一下医生哦。"
```

## 关键洞察

### Memory 是 Agent 的心脏

```
Skills 是大脑（决策能力）
MCP 是手和眼睛（执行和感知）
Memory 是心脏（连续性和成长）

没有心脏：
  Agent 每次见面都是陌生人
  谈不上"真正关系"
  只是工具

有心脏：
  Agent 能成长
  能真正了解用户
  能建立关系
```

### Mimo 的第 4 层创新

```
普通 Agent Memory：
  只记录"用户说了什么"

Mimo 的第 4 层：
  还记录"我做了什么、学到了什么、怎么成长的"
  让 AI 不仅是"回答机器"
  而是有自己生活的陪伴者

这是设计层面的突破
不是技术突破，是哲学突破
```

### localStorage vs 服务器的分工

```
这不是"哪个更好"的问题
而是"各自承担什么责任"的问题

localStorage（浏览器）：
  ✓ 快速访问
  ✗ 跨设备丢失
  → 适合：运行时权重、临时状态

服务器：
  ✓ 持久、同步
  ✗ 需要网络
  → 适合：长期记忆、家庭事实库

分工合理 = 两个都用
混淆职责 = 系统设计差
```
