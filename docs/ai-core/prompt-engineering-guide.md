# Prompt 工程完全指南

**核心概念**: Prompt 工程不是"背话术"，是理解一件事——[Inference 完全指南](inference-system-guide.md) 已经讲过，模型是在你给的文字基础上，一个词一个词预测最可能的下一个词。你写的每一个字，都是在收窄或放宽这个"最可能"的范围。写得越清楚具体，模型能预测的空间就越窄、越准；写得越模糊，模型只能靠猜，输出自然也越随意。

**关键洞察**: 好的 Prompt 技巧几乎都在做同一件事——**减少模型需要"猜"的部分**。给例子、说清楚格式、让它先想再答，本质上都是在替模型排除掉不该往那想的可能性，不是什么玄学。

**第一次接触这个主题？** 建议先了解：[LLM](../../glossary.md#llm) · [Inference](../../glossary.md#inference) · [Context](../../glossary.md#context)

## Prompt 到底是什么

**Prompt** 就是你给模型的文字——不神秘，它只是 [Context](../../glossary.md#context)（模型这次能看到的所有信息）里由你写的那一部分。模型不会"理解你的意图"再去满足它，模型做的事从头到尾都是同一件事：**根据到目前为止看到的所有文字，预测接下来最可能出现什么**。Prompt 工程的全部工作，就是想办法让"最可能出现的下一段文字"恰好是你想要的答案。

## 为什么"说清楚"有效

想象模型面前有一个巨大的"可能的下一句话"候选池。你的 Prompt 写得越模糊，候选池里合理的选项就越多，模型选中你真正想要的那个的概率就越低；你写得越具体（给背景、给约束、给格式要求），能留在候选池里的选项就越少，剩下的也越接近你想要的。

```
模糊的 Prompt："帮我写一段介绍"
  候选池里几乎什么"介绍"都说得通
  → 模型随便选一种风格、随便选一个长度

具体的 Prompt："帮我写一段 100 字左右、面向初中生的、
                介绍光合作用的科普文字，语气活泼"
  候选池被大幅收窄：长度、受众、主题、语气都定了
  → 模型能预测的空间接近你真正想要的那一个
```

这跟"AI 更聪明了才能懂你"没关系——同一个模型，把同一件事说清楚，输出质量往往立刻不一样，因为你实际上是在替它排除了大量它本来要"猜"的部分。

## 三个真正有杠杆的技巧

不需要记几十条"神级 Prompt 技巧"，绝大多数管用的技巧都能归到这三类里：

### 1. 给例子（Few-shot）

与其描述你想要什么风格，不如直接给一两个例子，让模型照着"续写"这个模式——这叫**上下文学习（In-context Learning）**：模型不是从例子里"记住"了新知识，是从例子里读出了"接下来应该是这种格式/风格"，然后按这个模式续写。

```
不给例子："帮我把这些反馈整理成结构化格式"
  → 模型不知道你要的"结构化"具体长什么样

给一个例子：
  "参考这个格式整理：
  反馈：'加载太慢了' → 分类：性能 | 优先级：高
  现在请你整理下面这些反馈：……"
  → 模型直接照着例子的形状续写，格式一致性高很多
```

### 2. 让它先想再答（Chain-of-thought）

[Inference 完全指南](inference-system-guide.md#thinking-模式的原理) 已经讲过"Thinking 模式"背后的原理：模型在草稿纸上多做几步推理，比直接吐出答案更准。你不需要开启特殊模式也能用上这个原理——直接在 Prompt 里要求"先一步步分析，再给结论"，本质上是在引导模型把中间推理过程也写出来，而不是一步跳到答案。复杂问题（数学、多步逻辑、需要权衡的决策）尤其明显。

### 3. 说清楚想要什么格式（结构化输出）

明确要求输出格式（"用表格""分成三段，每段一个小标题""只回复 JSON，不要多余的话"），能大幅减少你事后自己再整理的工作，也让模型更容易保持一致——这跟第一条"给例子"是同一个逻辑的另一种表现：格式要求本身就是在收窄候选池。

## System 和 User：两种不同的"说话身份"

[Context Window 完全指南](context-window-guide.md#第-1-层系统提示词不可见) 已经讲过系统提示词在 Context 里占多少空间，这里讲它扮演的角色：一次对话里，文字通常来自两种不同的"身份"——

- **System（系统）**：定好这次对话的背景规则——AI 扮演什么角色、有什么限制、语气怎么定——通常在对话开始前就设好，你后续每一句话都是在这个背景之下说的
- **User（用户）**：你在对话里实际打出来的每一句话

**为什么要分开**：把"长期不变的规则"放进 System、把"这次具体想要什么"放进 User，能让模型更清楚地区分"这是这次对话的底层设定"还是"这是当下这一步的具体请求"——同样一句话，出现在 System 里和出现在 User 里，模型对待它的方式不完全一样。

## 常见误区

- **以为模型记得你没说的事**——[术语表 Context](../../glossary.md#context) 已经讲过，模型只能看到这次放进 Context 里的信息，不会"猜"你脑子里想的背景，没写清楚的前提，等于没有
- **把"我要什么"和"为什么要"混在一起说不清**——多花一句话说清楚目的（"这段话是要发给客户的，要正式"），往往比堆砌形容词更有效，因为"目的"本身就是很强的约束条件
- **一次性塞进所有可能用得上的要求**——[Context Window](context-window-guide.md) 是有限资源，Prompt 也一样：太长、太多要求堆在一起，模型反而抓不住重点，不如分几轮对话逐步明确

## 这篇不讲什么

- 不讲某个具体产品的 Prompt 语法细节（比如 XML 标签、特定的系统消息格式）——这些因产品而异，不是"理解为什么某种写法更有效"所需要的
- 不讲 Prompt 注入攻击/安全防护——那是另一个话题，不属于"怎么写出好结果"
- 不讲采样参数（温度、Top-p）——那些是模型输出时的另一层控制，[Inference 完全指南](inference-system-guide.md#采样参数) 已经讲过，跟 Prompt 本身是两件事
