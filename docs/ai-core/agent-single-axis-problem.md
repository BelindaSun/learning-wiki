# Agent 的"单轴刻度"问题：Autonomy、Delegation、Memory、Exploration 为什么都不能只用一根尺子

**核心洞察**: 我们习惯用"一根轴"描述的 Agent 属性——自主性有多高、该给多少权力、记忆存多久、探索能力多强——拆开看往往是**至少两个独立维度被压扁成了一条刻度**。粗糙的单轴分类不只是不精确，它会**系统性地让人误判风险和瓶颈到底在哪**。

**第一次接触这个主题？** 建议先了解：[Agent](../../glossary.md#agent) · [Memory](../../glossary.md#memory) · [五维可信度框架](../career-impact/capability-to-trust.md)

## 一句话总结：一条隐藏的共同线索

四篇看起来不相关的论文，其实共享一条线索：**凡是我们习惯用一根轴去描述的 Agent 属性，拆开看都是至少两个独立维度被压扁了。**

这个方法论今天在四个不同场景里各验证了一遍——Autonomy、Delegation、Memory、Exploration。下面逐个拆。

---

## 场景一：Autonomy 不是一根刻度，是四维

**原来我以为**：Agent 的自主性用"低 / 中 / 高"一个刻度描述就够了。

**问题在哪**：一个刻度会把两件独立的事压在一起——"自己拿主意的频率"和"每次决定的杀伤力"。合并成一条线，就会把风险画像完全不同的系统混为一谈：

- **Waymo**：高自主、低通用（几乎每一步都自己决定，但只在"开车"这一件事上）
- **Claude + tool use**：中自主、高效能（不是每步都自己决定，但单次决定能触及的范围很广）

用同一个"高自主"标签贴这两个，等于把它们当同类风险处理——而它们其实完全不是一回事。

**现在我认为**：Autonomy 至少要拆成四个维度：

| 维度 | 问的问题 |
|------|----------|
| **Autonomy** | 多频繁地自己拿主意（而不是等人批） |
| **Efficacy** | 每次决定的"杀伤力"/能触及的范围有多大 |
| **Goal Complexity** | 目标本身有多复杂、多长链条 |
| **Generality** | 适用范围有多宽（专用 vs 通用） |

### 关键推论：Decisive risk vs Accumulative risk

把 Autonomy 和 Efficacy 拆开之后，一个原来问不出的问题就能问了——**"高 Autonomy + 低 Efficacy" 和 "低 Autonomy + 高 Efficacy" 哪个更危险？** 答案是：它们是**两种不同类型**的风险，需要**完全不同**的治理设计。

- **高 Autonomy + 低 Efficacy → 累积型风险（Accumulative）**
  单次影响很小，但高频自主，风险靠一点点堆积。比如"天天自己发一堆邮件"。
  → 护栏：**监控趋势、审计日志**。压住的是"量变到质变"。

- **低 Autonomy + 高 Efficacy → 决定型风险（Decisive）**
  很少自己拿主意，但一旦拿，单次就可能造成大后果。比如"审批后执行一笔转账"。
  → 护栏：**审批摩擦机制**。这里有个反直觉的点：人类在**低频、高赌注**的场景里会出现 **vigilance decrement（警觉衰减）**——正因为很少需要拦，真需要拦的那次反而容易走神放过去。所以护栏要靠"制造必要的摩擦"，不能指望人一直保持警觉。

用同一套"加个人工审核点"打包处理这两类风险，是不够的——它们要压制的东西根本不同。

## 场景二：Delegation 要在"给多少"之外加"给哪种"

**原来我以为**：[Delegation Framework](../career-impact/domain-expertise-and-org-design.md#3-管理-agent正在分化为四层能力) 按"给多少权力"分层（工具类 → 执行类 → 代理类）就能管住风险。

**现在我认为**：光有"量级"这一根轴不够，还要叠加"**给哪种**"（风险类型：decisive vs accumulative）。因为**同一个权力量级下**，"天天自主发邮件"和"审批后转账"需要的护栏完全不是一回事——前者是累积型，后者是决定型。

原来的三层分类是"量级"轴，今天补上的是"类型"轴，两者合起来变成一个**二维矩阵**：

```
                给多少权力（量级）
                工具类 → 执行类 → 代理类
                ─────────────────────►
风险    累积型 │  监控趋势 / 审计日志
类型          │
（哪种）决定型 │  审批摩擦 / 对抗警觉衰减
              ▼
```

同一格权力量级，落在累积型还是决定型，护栏设计就要换一套。

## 场景三：Memory 的关键轴是"时间朝向"，不是"持久度"

**原来我以为**：[Memory](memory-system-guide.md) 按"存多久"分 short-term / long-term 就是完整的分类方式。

**问题在哪**：有一类记忆在"存多久"这根轴上根本无处安放——**Prospective Memory（前瞻记忆）**，也就是"记得在未来某个时机去做某件事"（比如"下午三点提醒我改那个会")。它不是"过去存了多久"的问题，它面向的是**未来**。在旧分类法里，问它"是 short 还是 long term"是个无意义的问题。

**现在我认为**：Memory 更关键的分类轴其实是**时间朝向**：

- **Past（过去）**：发生过什么（情节 / 语义记忆）
- **Present（现在）**：当前状态是什么
- **Future（未来）**：将来要做什么（Prospective Memory）

"持久度"（短期/长期）是一根有用的轴，但它不是唯一的、也不是最能切中要害的那根。

### PM-Bench 发现：瓶颈不在"监控证据不够"

Prospective Memory 是"生活连续性"的地板——记不住"待会要做什么"，Agent 就没法在跨天、跨会话的任务里保持连贯。但目前**全行业都测不过 65% F1**。

PM-Bench 用认知科学的 **Virtual Week** 范式测试，发现一个反直觉结果：

- **多 Agent 分层监控**（约 1661 次查询）**反而不如**"单 Agent + 可选心跳"（约 130 次查询）。
- 瓶颈**不是**监控证据收集得不够，而是**不知道该什么时候停止监控、怎么把证据转化成行动**。
- 跨天任务、更新敏感任务（改期 / 取消）——全行业没有一种配置能突破 50% 命中率。

这条直接和 Orchestration 的成本逻辑打了一架，见下面[连接部分](#和以前哪些知识连起来了)。

## 场景四：开放性 ≠ 会探索

**原来我以为**：给 Agent 越大的自由发挥空间（两小时预算、随便改 kernel），它就越可能找到更好的方案。

**现在我认为**：**"开放性"不等于"会探索"。** 有开放的空间，不代表 Agent 会用探索纪律去填满它。

**InferenceBench 的证据**：让前沿 Agent 做开放式的推理优化任务，结果——

- **93.9% 的 run 收敛到同一个框架**；
- 两小时预算里，中位数**只测了一套非默认参数**；
- 反而**输给了** SMAC / TPE 这类**完全不懂领域知识、但机械地系统性搜索**的黑箱优化器。

Agent 有知识，但**严重缺乏探索纪律**。

### 根因：是训练目标，不是推理能力不足

零推理能力的黑箱搜索能打赢所有前沿 Agent，说明瓶颈**不是"想得不够深"**，而是：

1. **RLHF 系统性地奖励"看起来完整自信的答案"、惩罚"持续悬而未决"**——Agent 学会了尽快给一个像样的收尾。
2. **自回归生成的路径依赖**——一旦文本里写下了"用 vLLM"，后续 token 就很难反悔，早早把自己锁死在第一个还行的方案上。

### 真正的 Epistemic Curiosity 是一个显式终止条件，不是"性格"

关键的重构：不该把"好奇心"理解成一种性格特质，靠 prompt 鼓励"你要有好奇心"去解决。它应该是一个**可操作的终止条件**：

> 继续探索的**预期收益** vs **成本**——只有前者更大，才该继续探索。

这是一个显式的决策机制，不是氛围。这也引出一个开放问题：判断"要不要继续找"这件事，能不能指望**同一个 Agent 既提方案又当裁判**？还是必须有一个独立的"质疑者"角色？（见[没弄懂的问题](#仍然没弄懂的问题)）

## 心智模型：单轴刻度是危险的简化

> 凡是看到"Agent 的 X 有多高 / 多深 / 多强"这种**单一形容词**描述，都要下意识追问：**这个 X 是不是把两个独立的维度压扁了？**

反复出现的拆法：

- **量级（多少）** 和 **类型（哪种）** 要分开看 —— Autonomy、Delegation
- **时间朝向（过去/现在/未来）** 和 **持久度（短期/长期）** 要分开看 —— Memory
- **知识（懂不懂）** 和 **纪律（会不会执行）** 要分开看 —— Exploration

一根轴省事，但它省掉的往往正是"风险和瓶颈到底在哪"这个最关键的信息。

## 和以前哪些知识连起来了

- **和 [Orchestration 模式成本优化逻辑](workflow-orchestration.md) 直接冲突了一次**：分层多 Agent 在 Prospective Memory 任务上查询次数是单 Agent 的十倍，表现反而更差。说明"Orchestration 省成本 / 更强"这个结论**不能无条件套用到所有任务类型**——前瞻记忆这类任务，反而是简单心跳机制更优。
- **和 [五维可信度框架](../career-impact/capability-to-trust.md)（可预测 / 可解释 / 可审计 / 可控制 / 可恢复）精确对应上了**：可预测 + 可审计主要对付**累积型**风险，可控制 + 可恢复主要对付**决定型**风险，可解释横跨两者。
- **和 [Delegation Framework 三层分类](../career-impact/domain-expertise-and-org-design.md#3-管理-agent正在分化为四层能力)（工具类 / 执行类 / 代理类）构成升级关系**：原来的三层是"量级"轴，今天补上"类型"轴，变成二维矩阵。
- **和 [tool selection 机制](agent-architecture.md#工具调用机制) 呼应**：InferenceBench 说明就算工具选对了、知识也对了，Agent 依然会在**探索广度**上"偷懒"——这是 tool selection 框架没覆盖到的新盲区。

## 仍然没弄懂的问题

- Prospective Memory 现在卡在 65% 天花板，除了心跳机制、待办清单这类**外部脚手架**，有没有更根本的**架构性**解法（比如训练时专门优化这个能力）？
- Epistemic Curiosity 的"该不该停止探索"终止条件，具体怎么在 Agent 架构里实现——是不是**必须**靠一个独立于"提案 Agent"之外的"裁判 Agent"来负责质疑，而不能指望同一个 Agent 自己既提方案又判断要不要继续找？
