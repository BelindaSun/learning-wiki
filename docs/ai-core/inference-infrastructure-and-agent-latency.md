# 推理基础设施与 Agent 延迟：为什么 Prefill 和 Decode 要拆开跑

**核心概念**: AI 推理正在被拆成 Prefill（并行处理输入、算力密集型）和 Decode（逐 token 生成、内存带宽密集型）两种数学结构完全不同的运算，硬件设计也跟着从"一块 GPU 通吃"走向"不同架构各司其职"。这对 Agent 来说意味着：延迟不再只是模型和工具链设计的问题，基础设施层的物理约束（算力 vs 内存带宽）同样在决定 Agent"感觉起来像不像实时"。

**学习来源**: Cerebras Blog "The GPU Is Being Split in Half"（Mar 2026）、AMD 与 Cerebras 合作新闻稿（Jul 2026）、arXiv:2604.10852 "The xPU-athalon"（Golden, Wu, Wei, Brooks，Harvard/Meta FAIR，ISPASS 2026）
**最大收获**: "训练时代的 GPU 优势不能原封不动搬到推理时代"这件事背后有扎实的数学原因，不只是商业叙事。

## Prefill 和 Decode：两种数学结构完全不同的运算

一次 [LLM](../../glossary.md#llm) [推理](../../glossary.md#inference)，其实分成两个性质完全不同的阶段，差异不是工程实现细节，而是数学结构本身决定的。

**Prefill（预填充）**：处理输入 prompt 时，所有 [Token](../../glossary.md#token) 都是已知的、一次性摆在那里的。模型对这些 Token 同时做前向计算——数学上是一次矩阵乘矩阵（GEMM）运算。矩阵越大，每次从内存读取一份权重后能重复利用的次数越多，GPU 的并行计算核心可以被喂得很饱。这是 **compute-bound**（算力密集型）。

**Decode（解码）**：生成阶段完全不同。第 t 个 token 必须先生成出来，才能作为输入去算第 t+1 个——这是自回归模型的因果约束，没法并行化。每一步只处理 1 个新 token，但为了算它对之前所有 token 的注意力，必须把已经缓存好的全部历史 K、V（KV cache）从内存里重新读一遍。计算量很小（矩阵乘向量，GEMV），但数据搬运量很大，而且随对话变长，KV cache 越来越大，每步要读的数据也越来越多。这是 **memory-bandwidth-bound**（内存带宽密集型）。

```
Prefill（并行、compute-bound）
  输入 Token [N 个] → 一次性矩阵乘矩阵（GEMM）→ 构建 KV cache
  算力被喂饱，瓶颈是"算得快不快"

Decode（串行、memory-bandwidth-bound）
  第 t 个 token → 生成 → 作为输入算第 t+1 个（必须串行）
  每步都要重新读一遍不断增长的 KV cache（矩阵乘向量，GEMV）
  计算量小、数据搬运量大，瓶颈是"数据搬得快不快"
```

传统 GPU 用同一块芯片扛两种负载，相当于"一个厨子既要备菜又要现炒"，两种完全不同的工作节奏互相干扰。解构式推理（Disaggregated Inference）的做法是把两个阶段拆到不同硬件上跑：计算优化型硬件专门做 Prefill，内存带宽优化型硬件专门做 Decode，中间靠 KV cache 传递。2026 年 7 月，AMD 和 Cerebras 官宣了一个具体落地方案——AMD Helios（机柜级方案，负责高吞吐量的 Prefill）+ Cerebras 晶圆级引擎 WSE（直接把 SRAM 堆在芯片上、不走 off-chip HBM，负责超低延迟的 Decode），两者组成单一解构式工作流，双方称能带来最高 5 倍的每瓦每秒 Token 数（T/s/W）提升——这是厂商自己给出的数字，还没有独立第三方验证，第五节会展开为什么这类数字需要谨慎看待。

## 为什么训练时代的 GPU 优势不能平移到推理

训练时的前向传播，本质上跟 Prefill 是同一种运算模式——大批量数据、完整序列一起进矩阵乘法，加上反向传播也是稠密的矩阵运算。训练从头到尾都是 compute-bound，GPU 的强项（海量并行 FLOPs）被完全用上，这也是 NVIDIA 靠训练打下的护城河如此深的原因。

但训练根本不存在 Decode 这种东西。训练不需要一个 token 一个 token 地、串行地、依赖上一步结果地往外吐——那是推理服务给用户用的时候才有的场景。所以训练时代积累的优势，全部押注在"如何把矩阵乘法做得更快更并行"这一件事上，而这件事恰好是 Decode 阶段完全不需要的能力。

这也是为什么这轮硬件竞争格局会松动：不是 NVIDIA 的芯片不好了，而是推理这个新战场里，胜负手换了——从"谁的并行算力强"变成"谁能用最低延迟把内存里的东西搬出来"，是两种截然不同的工程优化问题，训练时代积累的优势不能自动平移。

## Agent 多步任务，四个指标怎么排序

如果一个 [Agent](../../glossary.md#agent) 一次任务要产生几十万甚至几百万 token，这几乎不可能是一次性生成，而是一个 Agent 循环里几十次、几百次的连续调用（观察 → 决策 → [工具](../../glossary.md#tool)调用 → 观察……）。这个结构决定了哪个指标真正卡脖子。

**Latency 是第一位的，但不是单次输出的 latency**：对单次巨大输出（比如一次性吐出十万字报告），latency 影响很小——反正要等它跑完。但 Agent 任务是几十上百个串行、互相依赖的小步骤，第 N 步的输出是第 N+1 步的输入，不能并行。Cerebras 的文章举了一个例子：10 步 Agent 链条，在 50 tok/s 下要 30 秒以上，在 1200 tok/s 下不到 3 秒——这不是同一种体验。tokens/sec 和 latency 在这个场景下其实是同一件事：每一步的生成速度直接决定了这一步的延迟，而延迟会在几十个步骤上复利式累加。真正卡住任务能不能在可接受时间内跑完的，是单步延迟能不能压到最低，本质就是小 batch 下的 Decode 速度。

**tokens/$ 决定这件事能不能规模化**：一个任务消耗几十万到百万 token，如果要跑成千上万次（多用户、多次迭代、失败重试），成本是线性累加的。这不是"跑得动跑不动"，是"划不划算"——哪怕速度够快，如果每次任务成本几十美元，大部分应用场景直接死在门口。

**tokens/watt 不是 Agent 开发者要直接优化的指标**：除非自己在运营硬件，否则 tokens/watt 是间接的——它是芯片厂商和云厂商成本结构的底层驱动力，最终会体现在卖给你的 tokens/$ 价格里。作为一个用 API 的开发者，感知不到瓦特，只感知到账单。

排序（针对用 API 构建 Agent 的开发者视角）：

1. **单步 latency / 小 batch 下的 tokens/sec** —— 决定任务能不能在合理时间内跑完，链条越长，影响越是指数级累加
2. **tokens/$** —— 决定这件事能不能规模化、能不能商业化
3. **聚合 tokens/sec（大 batch 吞吐量）** —— 更多是服务商关心的指标，决定他们能同时服务多少用户，间接影响拿到的价格和排队情况
4. **tokens/watt** —— 上游物理约束，通过价格传导给使用者，不是直接优化的对象

一句话总结：训练时代比拼"谁能堆更多卡训得更快"，吞吐量和成本是主角；但 Agent 推理时代，比拼的是"谁能在长链条的每一步都做到低延迟同时不把你吃穷"——latency 和 cost 变成一对绑在一起的双主角，算力堆叠反而成了配角。

## Workload 形状：没有全能冠军，只有场景冠军

arXiv:2604.10852《The xPU-athalon》实测对比了 Cerebras CS-3、SambaNova SN-40、Groq、Gaudi、TPUv5e 等推理芯片，以及 NVIDIA（A100、H100）和 AMD（MI-300X）GPU，从延迟、吞吐量、功耗、能效四个维度做了独立评测。三个跟前面内容直接相关的发现：

**没有"全能冠军"，只有场景冠军**：最优硬件平台会随 batch size、序列长度、模型大小而变化——这给 Cerebras 博客那类"比 GPU 快 1000-2000 倍"式的宣传数字泼了一盆冷水。真实世界里没有单一最优解，选型本质上是一个多维优化问题。

**"专用硬件更省电"这个假设要打折扣**：Cerebras、SambaNova、Gaudi 的空闲功耗比 NVIDIA 和 AMD GPU 高 10-60%。这些芯片只有在高利用率下才能兑现效能承诺——如果负载有大量空闲/低利用率时段（很多 Agent 工作流恰好如此：等 API 返回、等工具执行），专用芯片的能效优势可能被空转损耗吃掉。

**软件成熟度是被低估的成本**：论文评估了跨平台的可编程性，比较了达成承诺性能所需的编译时间和软件栈成熟度——论文性能数字和实际能拿到的性能之间，往往隔着一个不成熟的编译器/软件栈。

论文里"最优硬件随 workload 变化"这句话，拆开看是三个维度共同决定的：

- **输入输出比例**（Prefill 与 Decode 谁占大头）——长文档摘要几乎全是 Prefill，compute-bound 硬件吃香；创意写作/聊天续写几乎全是 Decode，内存带宽型硬件优势巨大；Agent 多步任务最复杂，是"反复的短 Decode + 频繁的小 Prefill"交替出现，对硬件的要求最挑剔
- **延迟容忍度（SLA 要求）**——离线批处理没人在等，要的是吞吐量（tokens/$）；实时交互（用户在等，或 Agent 在做实时决策）每一秒延迟都会被感知到，要的是低延迟，哪怕成本贵一点
- **请求到达模式**——稳定可预测 vs 突发不规律，决定硬件在低利用率时段会不会"空转浪费"

对 Agent 开发者最实用的推论：为 Agent 系统选择底层模型/API 服务商时，第一件要搞清楚的不是"哪家最快最便宜"，而是"我的 Agent 任务的 workload 形状是什么样"——是频繁小步骤的交互式 Agent，还是偶尔跑一次的长文档处理？这个答案直接决定哪家的解构式推理架构最适合。

## 产业格局：从同构走向异构，但还没到位

过去十几年 AI 计算的默认答案是"买更多 GPU、堆更大集群"——单一垂直供应链，NVIDIA 设计芯片，云厂商买卡，护城河建立在"通用计算 + 规模优势"上。解构式推理这条路一旦成立，意味着推理这个环节从"整块蛋糕归 NVIDIA"变成"每个阶段可以分给不同专长的玩家"——更像是从"垂直整合"走向"分层竞争"。

几个具体在被撬动的地方：

- **NVIDIA 的护城河变窄，但不会消失**——训练侧的优势短期内很难被替代，但推理侧（现在已经是更大的收入池，因为模型训练一次、被查询数十亿次）会出现真正的多强格局。NVIDIA 自己收购 Groq，本质上也是在为异构化做准备
- **云厂商的角色在变化**——把不同厂商的芯片拼在一起卖，本质上是云厂商在做"混合基础设施编排"，这个能力本身会成为新的竞争壁垒
- **Agent 应用开发者的选型会更专业化**——以前"用哪个模型"是唯一要决策的事；未来"用哪个模型 + 跑在哪种基础设施上 + 针对我的 workload 形状怎么配"会变成一个组合决策

但这个判断需要一点限定：与其说"AI 基础设施正在从同构走向异构"（听起来像既成事实），不如说**"AI 基础设施的架构共识正在从同构转向异构，但真正的异构化落地还处于头部玩家的早期试点阶段"**。几个现实的坎：

1. **规模还小**——真正跑在解构式/异构架构上的推理流量，占全球 AI 推理总量的比例还很小，大部分企业负载依然老老实实跑在同构 GPU 集群上
2. **软件栈没跟上**——vLLM、SGLang、Dynamo 这些框架才刚开始支持解构式部署，生态还在早期，异构硬件之间的调度、路由、KV cache 跨设备传输如果不够成熟，反而会带来额外复杂度和故障点
3. **"异构"目前更多是巨头间的定制合作**，不是中小开发者今天就能拿到的标准化产品——大多数开发者实际接触到的依然是"调用某个模型的 API"，底层是不是异构，很大程度上被云厂商屏蔽掉了

一句话概括：AI 计算的未来可能不是寻找一块更强的万能芯片，而是让不同计算架构在最适合自己的 workload 上协同工作——不过这个协同目前更多停留在少数头部厂商的早期试点，软件栈和调度生态能不能跟上，会决定这个转变走多快、多深。

## 仍然没弄懂的问题

- KV cache 在跨设备（Prefill 硬件 → Decode 硬件）传递时，网络延迟和带宽开销具体有多大？这会不会成为解构式架构自己的新瓶颈？
- 软件栈（vLLM、SGLang、Dynamo）目前对解构式部署的支持程度到底到哪一步了，是"能跑但不成熟"还是已经有生产级案例？
- 除了 Prefill/Decode 拆分，未来会不会出现更细粒度的拆分（比如把 Attention 和 FFN 拆到不同硬件）？
- 一个中小型 Agent 开发者（不是巨头）今天有没有办法真正用上解构式推理的红利，还是这个阶段只有头部玩家能享受到？

## 心智模型

**"计算特性决定硬件分工"**——一个任务该交给哪种硬件，不取决于这块芯片有多强，而取决于任务本身的数学结构（并行 or 串行、算力密集 or 内存密集）跟硬件的设计取向是否匹配。这个心智模型可以脱离 AI 硬件本身迁移使用：任何"选工具/选架构"的决策，先问"这个任务的内在结构是什么样"，再去匹配"什么工具的强项刚好对上这个结构"，而不是先问"哪个工具最厉害"。
