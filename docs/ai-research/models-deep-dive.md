# Models 深挖：MoE 架构和压缩技术

**核心概念**: MoE 通过"路由器+多个专家 FFN"把知识容量和计算成本解耦，让模型能做到万亿参数级别但推理成本可控。专家专业化和负载均衡之间存在真实矛盾。

**学习来源**: Claude AI Apprenticeship + 网络搜索验证  
**最大收获**: MoE 的负载均衡不是天生的，需要特殊的损失函数来训练。

## 稀疏模型（MoE）

### 核心问题

```
参数越多越聪明
但计算成本和参数量成正比
→ 爆炸！
```

**例子**：
```
传统模型（稠密）：
  1000 亿参数
  推理 = 1000 亿次计算
  成本很高

MoE 模型（稀疏）：
  6710 亿个"参数"（但大多数不激活）
  推理只激活 370 亿
  → 实际成本反而更低！
```

### MoE 的工作原理

**结构**：
```
一个 Transformer Block 的 FFN 层
正常情况：
  输入 → [单个大 FFN] → 输出

MoE 情况：
  输入 → 路由器 → 选择 K 个专家
             ↓
         [Expert 1]
         [Expert 2]
         ...
         [Expert 256]
             ↓
          融合输出
```

**具体过程**：
```
假设 256 个专家，每次激活 2 个

第 1 个 Token：
  路由器看这个 Token
  决定："这个 Token 应该去专家 5 和专家 128"
  Token 过 Expert 5 和 Expert 128
  结果融合

第 2 个 Token：
  路由器看这个 Token
  决定："这个 Token 应该去专家 42 和专家 200"
  Token 过 Expert 42 和 Expert 200
  结果融合

...
```

### 参数量 vs 计算量

```
参数量大：
  ✓ 知识容量大
  ✓ "聪明"
  ✗ 但不激活不消耗计算

计算量小：
  ✓ 推理快
  ✓ 成本低
  ✓ 这就是 MoE 的目标
```

**数字例子**：
```
GPT-3：
  参数: 1750 亿
  激活: 1750 亿（全部激活）

某个 MoE 模型：
  参数: 6710 亿
  激活: 370 亿（只激活少数）
  
实际效果：
  MoE 比 GPT-3 更聪明
  但计算量只有 1/4
```

## MoE 的核心矛盾

### 问题 1：路由器一开始什么都不懂

```
初始状态：
  路由器 = 随机初始化
  完全不知道怎么分配 Token

结果：
  可能所有 Token 都去同一个专家
  其他专家被闲置
  → 这叫"专家坍塌"（Expert Collapse）
```

### 问题 2：负载均衡很难

```
理想情况：
  256 个专家平均分配 Token
  每个专家都有活干

现实情况：
  某些专家很受欢迎（被选中率 80%）
  某些专家很冷门（被选中率 5%）
  → 资源浪费，而且热门专家可能过载
```

### 解决方案：负载均衡损失

**机制**：
```
训练时添加一个额外的损失函数
目标：惩罚"不均衡"的选择

损失 = Σ(路由器给某专家的平均概率) × (实际分给这个专家的 Token 比例)

效果：
  越"热门"的专家受到越重的惩罚
  梯度会自动压低它的路由概率
  强制均衡
```

**具体例子**：
```
假设 4 个专家：

理想情况（完全均衡）：
  Expert 1: 25%
  Expert 2: 25%
  Expert 3: 25%
  Expert 4: 25%
  损失 = 0（没有惩罚）

现实情况（不均衡）：
  Expert 1: 70% ← 很受欢迎
  Expert 2: 15%
  Expert 3: 10%
  Expert 4: 5%  ← 被冷落
  
  损失函数会给 Expert 1 很重的梯度
  下一轮训练会降低它的选中概率
```

### 问题 3：副作用——专家趋同

```
负载均衡强制均衡
但也可能导致：
  所有专家学得差不多
  → "专家趋同"
  
  为什么会这样？
  因为每个专家都被强制处理各种 Token
  没机会专精某个领域
  结果都变成"万能型"而不是"专家型"
```

**这是 2026 年仍在研究的开放问题**

## 负载均衡机制

### 损失函数详解

```
Loss_balance = Σ_i ( P_i × F_i )

P_i = 路由器给专家 i 的平均概率
     （这个专家"被看中"的概率）

F_i = 实际分给专家 i 的 Token 比例
     （这个专家实际处理了多少）

乘积大 = 这个专家既受欢迎又有活干
      = 不需要惩罚

乘积小 = 这个专家不受欢迎或活不多
      = 不需要惩罚

但如果：
  P_i 很大（很受欢迎）+ F_i 很大（活也多）
  = 乘积最大
  = 受罚最重
  = 下次梯度会降低它的概率
```

### 为什么这个机制有效

```
自我修正循环：

第 1 轮：
  Expert 1 太受欢迎（P=0.7, F=0.7）
  损失很大

第 2 轮：
  梯度调整路由器参数
  Expert 1 的选中概率下降

第 3 轮：
  Expert 1 没那么受欢迎了
  其他专家的概率上升
  更均衡了

继续迭代 → 最终接近均衡
```

## 为什么只用在 FFN

### Attention 不适合拆成专家

```
Attention 的特性：
  ✗ 高度交互（每个词看所有词）
  ✗ 难以独立分工
  ✗ 如果拆成多个独立的 Attention
     他们无法有效协作
```

### FFN 天然适合拆成专家

```
FFN 的特性：
  ✓ 每个词独立处理
  ✓ 可以按"领域"分类
  ✓ 某个专家可以专门处理"代词指代"
     另一个专家专门处理"数学推理"
  ✓ 容易分工
```

**比喻**：
```
Attention = 整个团队在讨论
  必须所有人都参与，无法独立

FFN = 分工处理任务
  某人负责数学，某人负责文学，某人负责代码
  完全可以独立，最后融合
```

## 模型压缩技术

### 四大技术

#### 技术 1：知识蒸馏（Knowledge Distillation）

**原理**：
```
大模型（教师）教小模型（学生）

硬标签（错误的方式）：
  "正确答案是 A"
  学生只学到"A"是对的，其他都是错的

软标签（正确的方式）：
  教师给出完整概率分布
  "A 有 45% 把握、B 有 20% 把握、C 有 15% 把握"
  学生学到"哪些选择也不错"，不只是"正确答案"
```

**效果**：
```
压缩比：学生模型只有教师的 1/10 到 1/20
能力保留：85-90% 的性能
```

#### 技术 2：剪枝（Pruning）

**非结构化剪枝**：
```
直接把不重要的权重清零

优点：
  ✓ 简单
  ✓ 压缩比高（可以达到 50%+）

缺点：
  ✗ 矩阵形状不变
  ✗ 需要专门硬件支持
  ✗ 不一定真的快
```

**结构化剪枝**：
```
直接删掉整个神经元或注意力头

优点：
  ✓ 矩阵真的变小
  ✓ 不需要特殊硬件
  ✓ 推理真的变快

缺点：
  ✗ 压缩比受限（超过 30% 时性能明显下降）
```

#### 技术 3：量化（Quantization）

> 这里讲的是量化对**准确率**的影响；量化为什么能直接**提速**（同样宽的硬件通道能塞下更多数字），见 [FLOPS 与精度：为什么降精度能提速](../computing-foundations/flops-and-precision.md)。

**概念**：
```
降低数字精度来减小体积

8-bit 量化：
  原来：32-bit 浮点数
  量化后：8-bit 整数
  体积：1/4
  精度：几乎无损

4-bit 量化：
  体积：1/8
  精度：开始有明显下降
  但仍然可用

更激进（2-bit、1-bit）：
  体积极小
  精度损失严重
```

**8-bit 量化结论**：
```
✓ 几乎无损
✓ 被广泛应用
✓ 是"标准做法"
```

#### 技术 4：混合精度（Mixed Precision）

```
不是所有权重都等价

关键权重：用高精度（16-bit 或 32-bit）
不关键权重：用低精度（8-bit 或 4-bit）

效果：
  ✓ 体积和计算速度改善明显
  ✓ 精度损失较小
```

## 压缩技术组合

### 流水线：剪枝 → 蒸馏 → 量化

```
原始模型（大而慢）
  ↓
Step 1: 剪枝（删除 30% 不重要的参数）
  体积：-30%
  能力：-5%
  ↓
Step 2: 蒸馏（用原始模型教压缩后的模型）
  体积：已经 -30%
  能力：恢复到 -2%
  ↓
Step 3: 量化（转换成 8-bit）
  体积：额外 -75%（从 70% 变成 17.5%）
  能力：维持 -2%
  ↓
最终模型（小而快）
  体积：原来的 17.5%（减少 82.5%）
  能力：原来的 98%（只损失 2%）
```

### 为什么组合有效

```
单独剪枝：
  删了 30% → 能力 -5%
  
剪枝+蒸馏：
  删了 30% + 老师教 → 能力 -2%
  （蒸馏补偿了一部分）

剪枝+蒸馏+量化：
  删+教+压缩 → 能力 -2%（体积 -82.5%）
  （三个技术互相补偿）
```

### 实战例子

```
假设要把 Claude 7B 压缩到手机上：

Step 1: 剪枝 30%
  7B → 4.9B
  能力：98%

Step 2: 蒸馏
  4.9B 被大 Claude 教
  能力：99%

Step 3: 8-bit 量化
  4.9B (4.9GB) → 1.2GB
  能力：99%

Step 4: 4-bit 量化（可选）
  1.2GB → 600MB
  能力：97%

结果：
  原来：7B 模型（7GB）在服务器上
  现在：600MB 模型能在手机上跑
  能力保留：97%
  推理速度：快 10+ 倍
```

## 关键洞察

### MoE 的真实困境

```
理想：
  所有专家都专精某个领域
  负载均匀
  高效率

现实：
  如果强制负载均衡
  专家无法专精（趋同）
  
  如果让专家自由发展
  会出现过载（不均衡）

这是一个开放问题
2026 年仍在研究如何平衡
```

### 压缩不是一次性的

```
不是"压缩后就定了"
而是"压缩是一个持续的过程"

比如：
  最新 Claude Opus 可能 8-bit 量化
  下个版本可能 4-bit 量化 + 更激进的剪枝
  不断优化"最小能完成任务的模型大小"
```
