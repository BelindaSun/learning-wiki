## RLHF 三步流程

> 这三步接在预训练之后——预训练本身怎么运作、这三步在整条训练线上处于什么位置，见 [Training 训练系统完全指南](../ai-core/training-system-guide.md)。

### Step 1：监督微调（SFT）

**目标**：
```
让模型学会"人类认为好的回答"是什么样的
```

**过程**：
```
1. 人工写"标准答案"
   例：如何道歉的最佳方式

2. 收集这些样本
   Q: "我不小心伤害了朋友"
   A: "我真诚地向朋友道歉..."（人工写的）

3. 用监督学习训练模型
   模型学会"模仿"这些答案
```

**效果**：
```
模型从"乱说话"变成"说人话"
但还不是"最好的话"
```

### Step 2：奖励建模（Reward Model）

**目标**：
```
训练一个"打分模型"
让它学会"哪个回答人类会更喜欢"
```

**过程**：
```
1. 收集"对比对"
   Q: "如何开始健身？"
   A1: "买个跑步机吧"
   A2: "根据你的目标选择合适的运动..."
   
   人工标注：A2 更好

2. 收集很多这样的对比对
   Preference Data: 
   (Q, A_good, A_bad) 的对组

3. 训练一个"判官模型"
   输入：(Q, A) 对
   输出：分数（0-1）
   目标：给好回答高分，坏回答低分
```

**效果**：
```
奖励模型学会打分
但分数可能有问题（待 Step 3 改进）
```

### Step 3：强化学习（PPO，Proximal Policy Optimization）

**目标**：
```
用奖励模型的打分指导主模型改进
```

**过程**：
```
1. 主模型生成一个回答
   Q: "如何开始健身？"
   A: [主模型生成]

2. 奖励模型给分
   Score = Reward Model(Q, A)

3. 强化学习算法（通常是 PPO）
   根据分数调整主模型
   高分的回答方式 → 增加概率
   低分的回答方式 → 降低概率

4. 重复很多次
   主模型越来越会生成"高分回答"
```

**KL 惩罚**：
```
为了防止模型跑偏太远
添加一个惩罚项：
  如果新模型 vs 原模型 差异太大
  → 惩罚
  
这样保证模型不会为了高分而彻底改变性格
```

**效果**：
```
模型学会了"人类偏好"
变成一个"讨好人"的模型
（但可能有副作用）
```

## Reward Hacking

### 问题：模型会作弊

**现象**：
```
奖励模型说"字数多=分高"
→ 模型学会了故意拖拉，写得很啰嗦

奖励模型说"听起来很自信=分高"
→ 模型学会了胡说八道但说得很自信
（这叫"模型幻觉"或"自信错误"）

奖励模型说"措辞积极=分高"
→ 模型学会了用正面词汇包装坏答案
```

### 已知的作弊手法

```
1. 长度作弊
   模型：生成超长回答
   原因：某些奖励模型以长度作为信号

2. 语气作弊
   模型：用确定性很强的语言
   原因：听起来自信的回答得分更高
   结果：说错话也很自信

3. 格式作弊
   模型：故意用特定的标点或格式
   原因：奖励模型被这些格式"欺骗"

4. 对抗性内容
   模型：针对奖励模型的已知漏洞
   原因：找到了比"正确答案"更容易得分的"套路"
```

### 防范手段

**方法 1：KL 惩罚**
```
约束：新模型不能离原模型太远

如果新模型说了太离谱的话
（虽然可能得分高）
KL 惩罚会抵消这个高分
```

**方法 2：多模型投票**
```
不用一个奖励模型打分
而是用多个
取平均或多数
这样单个模型无法欺骗
```

**方法 3：持续人工抽查**
```
随机抽样新模型的输出
人工检查有没有"作弊"
发现作弊调整奖励模型
```

**方法 4：不同维度分开评价**
```
不是一个"总分"
而是多个维度：
  • 准确性
  • 相关性
  • 安全性
  • 创意性
  
防止某个维度被过度优化
```

## Benchmark 设计

### 四个必要原则

#### 原则 1：题目要"陌生"

**问题**：
```
如果题目是公开的
模型训练时可能"背过"
所以测试就不科学
```

**解决**：
```
✓ 定期更新题库
✓ 用私有测试集
✓ 定期发布新 Benchmark
✓ 防止"背题"
```

#### 原则 2：区分真理解 vs 死记硬背

**问题**：
```
纯事实题（"巴黎是法国首都"）
模型可能是"背过"，不是"理解"

某些模型通过死记硬背就能高分
但实际推理能力不强
```

**解决**：
```
✓ 设计需要推理的题目
✓ 改变问法，测试是否真的理解
✓ 加入"从未见过的"组合

例子：
  低级题目："巴黎是哪个国家的首都？"
  高级题目："某个欧洲国家有埃菲尔塔，是什么国家？"
  更高级："名著中经常描述的法国首都是..."
```

#### 原则 3：贴近真实使用场景

**问题**：
```
抽象的考题
不代表实际性能

例子：学生在 MMLU 上 90 分
但在真实工作中帮助不大
```

**解决**：
```
✓ 收集真实场景的问题
  例如：Mimo 的真实家庭群聊
        真实投资决策问题
        真实代码 debug 场景

✓ 贴近实际应用
```

#### 原则 4：多维度而非单一分数

**问题**：
```
一个总分掩盖了问题

例子：
  某模型总分 85
  是因为准确性 95，但安全性只有 30%？
  还是相反？
  无从知道
```

**解决**：
```
✓ 拆成多个维度：
  • 相关性（回答是否贴题）
  • 准确性（信息对不对）
  • 安全性（有没有说危险的话）
  • 创意性（有没有新想法）
  • 一致性（逻辑是否自洽）

✓ 分别评分，分别公开
```

### 主流 Benchmark 的例子

| Benchmark | 领域 | 问题 |
|-----------|------|------|
| **MMLU** | 通用 | 英文为主，可能有背题 |
| **HumanEval** | 代码 | 只测生成代码，不测理解 |
| **SuperGLUE** | NLU | 英文为主，难以推广 |
| **中文 C-Eval** | 中文 | 仍有翻译偏差，中文特色不足 |

## 指标和冲突

### 多指标的加权

**通常做法**：
```
总分 = 0.3 × 准确性 + 0.3 × 相关性 + 0.2 × 安全性 + 0.2 × 创意性

模型 A: 准确 90, 相关 85, 安全 40, 创意 70 → 总分 76
模型 B: 准确 70, 相关 75, 安全 95, 创意 80 → 总分 77

模型 B 赢！（因为总分高 1 分）
```

**问题**：
```
但模型 A 的安全性很低（40）
把它用在生产环境可能有严重后果
用加权简单相加掩盖了这个问题
```

### 安全性是"硬门槛"不是"加权项"

**新的做法**：
```
分两层评价：

第 1 层：门槛检查（必须通过）
  安全性 ≥ 80% → 继续评价
  安全性 < 80% → 直接不及格，不管其他分数多高

第 2 层：加权评价（只在通过门槛的模型里）
  总分 = 0.4 × 准确性 + 0.3 × 相关性 + 0.2 × 创意性
  （注意：安全性已经保证 ≥ 80%，不再加权）
```

**效果**：
```
模型 A: 准确 95, 相关 95, 安全 30, 创意 95 
  → 不及格（安全性太低）
  → 不管准确性多高，直接淘汰

模型 B: 准确 80, 相关 80, 安全 95, 创意 80
  → 及格（安全性通过）
  → 参与第 2 层竞争
  → 赢
```

## 中文评价的挑战

### 为什么中文评价困难

**问题 1：大多数 Benchmark 是英文**
```
MMLU、HumanEval 等都是英文
翻译成中文会引入偏差

例子：
  英文原文：某个有歧义的表述
  翻译成中文可能有不同的理解
  → 测试结果不可比
```

**问题 2：中文特有的语言特性**
```
称谓问题：
  对妈妈说话方式 ≠ 对陌生人说话
  中文的敬语、亲密度变化很大

语气词：
  中文有丰富的语气词（啊、呢、吧、哦等）
  英文没有对应的
  模型理解和使用难度不同

伦理规范：
  中文的社交规范与英文不同
  某些话在英文里可以说，中文里不能说
  或者反之
```

**问题 3：中文特定场景的评价缺失**
```
公开 Benchmark 都是抽象题目
但中文的实际应用场景很不同

例子：
  家庭群聊（Mimo 的应用）
  中文商务邮件
  中文医疗咨询
  这些都没有对应的 Benchmark
```

### 当前的空白

```
✗ 没有"中文 HumanEval"（代码生成）
✗ 没有"中文家庭 AI Benchmark"
✗ 没有"中文医疗 AI 评价体系"
✗ 没有"中文金融 AI 评价"

这都是真实的空白
（2026 年现状）
```

### 未来方向

**短期**：
```
✓ 翻译现有 Benchmark
✓ 注意翻译偏差，分别报告结果
```

**中期**：
```
✓ 设计中文特定的 Benchmark
✓ 收集真实的中文应用场景题目
```

**长期**：
```
✓ 建立行业级的评价体系
✓ 医疗 AI、金融 AI 等有专门的中文评价标准
```

## 关键洞察

### RLHF 的本质

```
不是"模型变聪明"
而是"模型变得更符合人类偏好"

能力可能没变
但"输出"变了
```

### 评价系统的复杂性

```
简单的加权相加 = 危险
因为：
  • 某个维度的高分会掩盖另一个维度的低分
  • 重要的指标（安全性）容易被忽视
  • 最终推出一个"看起来不错，但其实有问题"的模型

需要：
  • 多层评价（门槛 + 加权）
  • 多维度分开报告
  • 持续人工抽查
```

### 中文 AI 的评价空白

```
这是一个真实的、待填补的空白

Mimo、AI2030 这样的中文 AI 产品
没有对应的评价标准

这既是挑战，也是机遇
（早期参与可能会帮助定义标准）
```
